# 第九课：SQLite 备份、恢复与完整性检查

> MySQL 课程已经介绍了全量备份、binlog、时间点恢复和主从复制。本课不重复服务器数据库的复制体系，而是专门学习 SQLite 文件数据库如何安全备份、验证和恢复。
>
> 完整可运行代码见 `code/database-sqlite/database_lesson09.py`。本课所有操作都使用独立练习数据库，不对真实业务文件执行覆盖或删除。

## 一、SQLite 的备份为什么特殊

SQLite 的数据库主要保存在文件中，因此最直觉的备份方式是复制文件：

```text
复制 app.sqlite3
    -> 得到 backup.sqlite3
```

但数据库文件可能正在被写入，或者 WAL 模式下还有一部分提交内容位于 `-wal` 文件中。此时简单复制主文件可能得到不完整或无法反映最新状态的备份。

所以要区分：

```text
文件副本：操作简单，但必须确认文件状态和 WAL 状态
逻辑导出：得到 SQL 或数据内容，迁移方便但恢复较慢
Online Backup API：在数据库仍被使用时按 SQLite 机制复制
VACUUM INTO：生成一个整理后的数据库副本
```

## 二、直接复制文件的边界

### 1. 数据库没有并发写入时

如果应用已经安全关闭连接、没有进程继续写入，复制数据库文件通常比较直接：

```text
停止使用数据库
    -> 确认没有活动连接和未完成事务
    -> 复制 .sqlite3 文件
```

这种方式适合本地工具关闭后的备份，但仍应验证备份文件可以打开和读取。

### 2. 数据库正在使用时

如果有写事务正在进行，直接复制文件可能遇到：

- 复制到事务提交前的状态；
- 文件和 WAL 内容不一致；
- 备份结果缺少最近提交的数据；
- 正在复制时文件发生变化。

不要把“文件可以复制”理解成“任何时刻复制都一定是安全备份”。需要在线备份时，应使用 SQLite 提供的备份机制，或先设计清晰的停写窗口。

## 三、WAL 模式下的备份

WAL 模式下，部分最新修改可能先写到：

```text
database.sqlite3-wal
database.sqlite3-shm
```

主数据库文件和 WAL 文件共同反映当前数据库状态。只复制 `database.sqlite3` 而忽略相关状态，可能无法得到完整的最新备份。

WAL 模式下应注意：

- 不要只凭主文件大小判断数据是否完整；
- 备份工具需要理解 WAL；
- 备份前要确认连接和事务状态；
- 长时间读事务可能阻止 checkpoint，导致 WAL 文件变大；
- 恢复时要让 SQLite 以完整数据库方式打开副本。

检查当前 journal 模式：

```sql
PRAGMA journal_mode;
```

WAL 不是备份方案，也不是把主库和 WAL 文件随便打包就完成了备份。它是事务日志模式，备份仍然需要使用正确的流程。

## 四、使用 VACUUM INTO

SQLite 可以把当前数据库整理并写入一个新的数据库文件：

```sql
VACUUM INTO 'backup.sqlite3';
```

它的特点：

- 生成一个新的数据库副本；
- 可以整理空闲页；
- 适合生成相对紧凑的备份文件；
- 需要目标路径不存在或满足 SQLite 的要求；
- 执行会产生 IO 和额外空间消耗。

在 Python 中：

```python
connection.execute("VACUUM INTO ?", (str(backup_path),))
```

执行前要注意路径处理和文件权限。不要把用户输入直接作为任意文件路径执行。

## 五、Online Backup API

Python 标准库 `sqlite3` 提供了备份接口：

```python
source = sqlite3.connect(source_path)
backup = sqlite3.connect(backup_path)

with backup:
    source.backup(backup)
```

它由 SQLite 参与复制过程，比简单复制正在使用的文件更可靠。可以配合参数控制每次复制的页数和进度：

```python
def progress(status, remaining, total):
    print(f"remaining={remaining}, total={total}")

with backup:
    source.backup(backup, pages=100, progress=progress)
```

大型数据库备份时，分批复制可以降低一次性占用，但仍需评估对读写和磁盘 IO 的影响。

## 六、完整性检查

备份完成后不能只看文件是否存在，还要验证 SQLite 能否打开和读取。

### 1. integrity_check

```sql
PRAGMA integrity_check;
```

正常情况下通常返回：

```text
ok
```

它会执行较完整的数据库结构一致性检查，可能需要一定时间。

### 2. quick_check

```sql
PRAGMA quick_check;
```

它通常比 `integrity_check` 更快，但检查范围和完整程度不同。日常快速检查可以使用它，重要备份和恢复演练仍应安排更完整的校验。

### 3. 业务级校验

结构完整不等于业务数据正确。恢复后还要检查：

- 关键表是否存在；
- 记录数量是否在预期范围；
- 关键用户、订单和配置是否存在；
- 外键关系是否仍然满足；
- 应用能否正常打开；
- 时间和文件版本是否正确。

```text
数据库完整性检查：文件结构能否读取
业务校验：数据是否符合应用预期
```

两者都需要。

## 七、恢复数据库文件

恢复到临时路径时，步骤可以是：

```text
停止或隔离使用旧数据库的应用
    -> 准备恢复出的副本
    -> 执行 integrity_check
    -> 校验关键业务数据
    -> 修改应用配置指向恢复文件
    -> 进行只读或小范围验证
    -> 再恢复正式流量
```

不要直接覆盖唯一的生产文件进行“现场试恢复”。更安全的方式是先恢复到新路径或临时实例，确认可用后再切换。

恢复时还要检查：

- 文件所有者和权限；
- 应用进程是否能够访问；
- WAL 和 journal 的残留状态；
- 数据库版本和应用版本是否匹配；
- 备份时是否包含所有需要的附属文件或通过备份工具已正确合并。

## 八、SQLite 没有 binlog 和主从复制

SQLite 的备份恢复不能照搬 MySQL：

```text
MySQL：全量备份 + binlog，可做时间点恢复
SQLite：文件副本、Online Backup API、VACUUM INTO 等
```

SQLite 没有 MySQL 那样的内置 binlog 主从复制体系。需要跨设备同步时，通常由应用层、文件同步系统或专门的同步方案负责，但必须处理并发修改、冲突和版本合并。

把 SQLite 文件直接放在普通网盘或共享文件系统中同步，可能造成锁、延迟和文件一致性问题，不能当作可靠的数据库复制方案。

## 九、备份保留策略

本地应用也应该考虑：

- 保留多少个历史副本；
- 备份放在哪里；
- 是否加密；
- 是否包含敏感数据；
- 旧备份何时清理；
- 设备损坏时是否还有异地副本；
- 恢复操作是否有人能够执行。

常见的简单策略：

```text
保留最近若干个本地备份
定期复制一份到独立存储
恢复前先复制当前文件
定期自动执行完整性和恢复检查
```

备份文件本身包含数据库中的敏感数据，必须使用合适的文件权限和加密措施保护。

## 十、常见错误

- 数据库仍在写入时直接复制主文件；
- WAL 模式下只复制 `.sqlite3`，忽略 WAL 状态；
- 只确认备份文件存在，不执行完整性检查；
- 只执行 `integrity_check`，不做业务数据校验；
- 直接覆盖唯一生产文件进行恢复测试；
- 把 WAL 当作备份；
- 把文件同步工具当成 SQLite 主从复制；
- 备份从未进行恢复演练；
- 不限制备份文件权限，导致敏感数据泄露。

## 十一、面试回答模板

### 题目：SQLite 如何备份？

> 如果数据库已经安全停止使用，可以复制数据库文件；如果数据库正在使用，应优先使用 SQLite 的 Online Backup API 或 `VACUUM INTO` 等理解 SQLite 状态的方式。WAL 模式下不能只关注主文件，还要考虑 WAL 状态。备份后要执行完整性检查和恢复验证。

### 题目：为什么不能随便复制正在使用的 SQLite 文件？

> SQLite 可能正在写入事务，WAL 模式下最新修改还可能位于 WAL 文件中。直接复制主文件可能缺少最近提交的数据或得到状态不一致的副本。应该使用正确的在线备份机制，或先停止写入后再复制。

### 题目：SQLite 有没有类似 MySQL binlog 的恢复方式？

> SQLite 没有 MySQL 那样的内置 binlog 主从复制体系。它通常通过数据库文件备份、Online Backup API 或 `VACUUM INTO` 恢复到某个备份时间点。如果需要持续同步和时间点能力，需要额外的应用层或外部同步方案。
