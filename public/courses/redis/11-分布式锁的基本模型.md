# 第11课:Redis 分布式锁的基本模型

> 这一课学习多个 Worker 如何避免同时执行同一个任务。
>
> 重点理解 Redis 分布式锁的基本流程和边界，不把它当成数据库事务或万能并发方案。

## 一、这一课要解决什么问题

先明确一个词：**Worker 是执行后台任务的服务端进程**，可以理解成服务端代码跑起来的一个实例。同一套代码可以启动多个 Worker——同一台机器上开多个进程，或者多台机器各跑一个。它们共享同一个任务来源，所以可能同时领取同一个任务。

假设两个 Worker 同时领取同一个任务：

```text
Worker A：读取任务，准备执行
Worker B：读取同一个任务，也准备执行
Worker A：发送邮件
Worker B：再次发送邮件
```

如果同一时间只能允许一个 Worker 执行，就需要一个共享的执行标记：

```text
Worker A -> 获取锁 -> 执行任务 -> 释放锁
Worker B -> 获取失败 -> 等待或退出
```

本课回答四个问题：

1. 幂等键和分布式锁有什么区别？
2. 如何使用 Redis 获取一把基础分布式锁？
3. 为什么锁需要过期时间和持有者标识？
4. 为什么释放锁时不能直接 `DEL`？

## 二、获取分布式锁

先说明一点：Redis 并没有内置的"锁"命令。分布式锁是**用 Redis 的通用命令组合出来的设计模式**——Redis 只提供 `SET NX EX`、原子脚本这些"积木"，锁、限流、消息队列这类业务模式都需要应用自己搭（或使用现成库，例如 Java 的 Redisson、Python 的 redlock）。本课先讲裸实现，目的是理解原理；生产环境通常直接用成熟库，而不是从零造锁。

### 1. 使用 `SET NX EX`

```redis
SET lock:task:9001 worker-a NX EX 30
```

这条命令表示：

```text
只有 Key 不存在时才写入
值为 worker-a
30 秒后自动过期
```

返回 `OK` 表示获取成功，返回空值表示锁已经被其他执行者持有。

它和第 10 课的幂等键都用 `SET NX EX`，容易混淆，但解决的问题不同：

```text
幂等键：同一个请求重复到达时，只产生一次业务效果（时间维度）
分布式锁：同一时刻只允许一个执行者进入临界区（并发维度）
```

两者可以一起使用：幂等键防止重复业务结果，锁减少并发执行。锁不能替代幂等，幂等也不能替代锁（面试中常追问这一点，见面试回答模板）。

### 2. 为什么需要过期时间

如果 Worker 获取锁后崩溃：

```text
Worker A 获取锁
    -> 进程崩溃
    -> 没有机会释放锁
```

没有过期时间时，其他 Worker 可能永远无法执行任务。过期时间可以让锁最终自动释放。

但过期时间也带来问题：

```text
任务执行时间超过锁的 TTL
    -> 锁自动过期
    -> Worker B 获取同一把锁
    -> A 和 B 同时执行
```

因此 TTL 必须覆盖正常任务时间；执行时间不确定时，需要续期机制或采用更可靠的任务协调方案。

### 3. 为什么需要唯一持有者

不能只把锁的值写成固定字符串：

```text
lock:task:9001 = "locked"
```

应该为每次获取生成唯一标识：

```text
lock:task:9001 = "worker-a-token-123"
```

这样释放时可以确认：

```text
只有当前持有者才能删除这把锁
```

## 三、释放分布式锁

### 1. 不能直接删除

下面的流程有风险：

```text
Worker A 获取锁
    -> A 执行时间过长
    -> 锁自动过期
    -> Worker B 获取新锁
    -> A 执行结束并 DEL
    -> A 删除了 B 的锁
```

所以释放前必须检查锁的值是否仍然是自己的持有者标识。

### 2. 检查和删除需要一起完成

不能简单写成两条独立命令：

```python
if client.get(key) == token:
    client.delete(key)
```

因为 `GET` 和 `DELETE` 之间可能发生过期或被其他 Worker 重新获取。

实际释放时通常使用 Lua 脚本，让“检查持有者并删除”作为一个原子操作。Lua 脚本是**运行在 Redis 内部的一段小脚本**，Redis 会把整个脚本当作一条命令原子执行——执行过程中不会被其他请求插入。可以把它理解成"给 Redis 定义一个自定义原子命令"。

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

脚本用到的三个东西：

```text
KEYS[1]        ：调用脚本时传入的第 1 个 Key 名（锁的名字）
ARGV[1]        ：调用脚本时传入的第 1 个参数（我们自己的 token）
redis.call(...) ：在脚本里执行一条 Redis 命令
```

逐行看：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then   -- 锁的值是否还是我的 token？
    return redis.call("DEL", KEYS[1])          -- 是：删除锁，返回 1
end
return 0                                        -- 不是：不删除，返回 0
```

返回 `1` 表示删除成功；返回 `0` 表示锁已经不是自己的（已经过期，或已被其他 Worker 重新获取）。

在 Python 客户端中调用这段脚本：

```python
released = client.eval(script, 1, lock_key, token)
```

```text
client.eval(脚本, 1, lock_key, token)
    script    ：Lua 脚本内容
    1         ：后面有 1 个 Key 名
    lock_key  ：对应脚本里的 KEYS[1]
    token     ：对应脚本里的 ARGV[1]
```

本课只要求理解这段脚本的目的和含义，不深入 Lua 语言本身。

## 四、锁的边界和风险

### 1. 锁不是事务

Redis 锁不能自动保证：
- 数据库操作和 Redis 操作同时成功；
- 进程崩溃后业务一定回滚；
- 任务一定只执行一次；
- 网络分区时所有节点看到相同状态。

重要业务仍然需要数据库事务、唯一约束和幂等设计。

### 2. 锁的粒度

锁太粗：

```text
lock:all-tasks
```

所有任务互相阻塞。

锁太细：

```text
lock:task:9001
```

可能产生大量 Key 和复杂的锁管理。

通常应该按照实际竞争资源选择粒度，例如按任务 ID、用户 ID 或账户 ID 加锁。

### 3. 锁的持有时间

锁应该只覆盖必要的临界区：

```text
获取锁
    -> 执行必须互斥的操作
    -> 尽快释放锁
```

不要在持有锁时执行不必要的网络调用或长时间等待。

## 六、常见错误

### 1. 使用 `SETNX` 后再单独设置过期时间

如果两步之间进程崩溃，锁可能没有 TTL：

```text
SETNX 成功
    -> 进程崩溃
    -> EXPIRE 没有执行
    -> 锁永久存在
```

优先使用带过期时间的单条命令：

```redis
SET key value NX EX 30
```

### 2. 释放时无条件 `DEL`

锁可能已经过期并被其他 Worker 重新获取。释放者必须校验 token，不能只看 Key 名称。

### 3. 锁的 TTL 小于任务执行时间

任务还没有执行完，锁已经过期，其他 Worker 就可能进入。需要根据任务耗时设置 TTL，或设计安全续期。

### 4. 把锁当成幂等方案

锁只能减少并发执行，不能处理请求已经成功但响应丢失后的重复提交。重复请求仍然需要幂等键和数据库约束。

### 5. 获取锁失败后无限等待

无限等待会占用请求和 Worker 资源。应该设置最大等待时间、重试次数和退避策略。

## 七、面试回答模板

### 题目：Redis 分布式锁怎么实现？

> 可以使用 `SET key token NX EX seconds`，只有 Key 不存在时才能获取锁，同时设置过期时间，并把唯一 token 作为持有者标识。释放时要用原子脚本确认 Key 的值仍然是自己的 token，再删除 Key，避免误删其他执行者的新锁。

### 题目：分布式锁为什么需要过期时间？

> 进程可能在获取锁后崩溃，如果没有过期时间，锁可能永久存在，其他执行者无法继续。TTL 可以提供自动释放，但 TTL 过短又会导致任务执行期间锁提前失效，因此需要结合任务耗时或续期机制设计。

### 题目：分布式锁和幂等有什么区别？

> 分布式锁限制同一时刻只有一个执行者进入临界区，幂等保证同一个请求重复执行不会产生重复业务效果。锁不能替代幂等，重要业务还需要数据库事务和唯一约束。
