# Cache Aside 缓存模式

> 这一课开始把 Redis 和数据库放到同一个请求流程中。
>
> 目标是理解最常见的缓存模式：读取时先查缓存，未命中再查数据库；写入数据库后删除对应缓存。

## 一、这一课要解决什么问题

假设一个接口每次都直接查询数据库：

```text
请求
    -> 查询数据库
    -> 返回结果
```

当多个请求反复读取同一份数据时，数据库会承担大量重复查询。加入 Redis 后，流程变成：

```text
请求
    -> 查询 Redis
    -> 命中：直接返回
    -> 未命中：查询数据库
    -> 写入 Redis
    -> 返回结果
```

这种模式叫 Cache Aside，也叫旁路缓存。

本课回答四个问题：

1. 为什么读取时要先查缓存？
2. 缓存未命中时如何回填？
3. 数据更新后为什么通常删除缓存？
4. Redis 和数据库分别谁负责保存真实数据？

---

## 二、Cache Aside 的读取流程

### 1. 先查缓存

以文章详情为例：

```text
Key：life:article:42:detail
```

读取流程：

```text
1. 根据文章 ID 生成 Redis Key
2. 使用 GET 查询 Redis
3. 如果查到值，直接返回
4. 如果没有查到，查询数据库
5. 将数据库结果写入 Redis
6. 返回结果
```

伪代码：

```python
def get_article(article_id: int):
    key = f"article:{article_id}"
    cached = redis_client.get(key)
    if cached is not None:
        return cached

    article = database.get_article(article_id)
    if article is None:
        return None

    redis_client.set(key, article, ex=300)
    return article
```

### 2. 缓存命中

如果 Redis 中有数据：

```text
请求 article/42
    -> GET life:article:42:detail
    -> 查到文章
    -> 直接返回
```

这次请求不需要访问数据库。

缓存命中通常具有这些特点：

- 响应更快；
- 减少数据库查询；
- 多个应用实例可以共享缓存；
- 结果的有效性取决于缓存更新策略。

### 3. 缓存未命中

如果 Redis 返回空值：

```text
请求 article/42
    -> GET life:article:42:detail
    -> 没有数据
    -> 查询数据库
    -> SET life:article:42:detail ...
    -> 返回结果
```

缓存未命中不是错误，而是正常流程。第一次访问某个数据、缓存过期或缓存被清理时，都可能发生未命中。

### 4. 设置过期时间

回填缓存时应该设置过期时间：

```redis
SET life:article:42:detail "{...}" EX 300
```

这样缓存不会永久保存旧数据。缓存时间需要根据业务决定，不能简单地认为越长越好。

## 三、Cache Aside 的写入流程

### 1. 更新数据库后删除缓存

常见的写入流程是：

```text
1. 更新数据库
2. 删除 Redis 中对应的缓存
3. 下一次读取时重新查询数据库并回填缓存
```

伪代码：

```python
def update_article(article_id: int, title: str):
    database.update_article(article_id, title)
    redis_client.delete(f"article:{article_id}")
```

下一次读取：

```text
查询 Redis
    -> 缓存不存在
    -> 查询数据库中的新数据
    -> 写入缓存
    -> 返回
```

### 2. 为什么通常删除而不是直接更新缓存

也可以在更新数据库后直接更新 Redis，但删除缓存通常更简单：

- 缓存格式可能和数据库格式不同；
- 更新缓存时还可能失败；
- 一个数据库记录可能对应多个缓存 Key；
- 删除后可以由下一次读取统一重建；
- 不需要在写入流程中重复组装完整缓存对象。

这不是绝对规则。对于明确知道所有相关 Key、并且缓存更新可靠的场景，也可以主动更新缓存。当前阶段先掌握“更新数据库后删除缓存”这一常见模式。

### 3. 删除缓存不是删除数据库

下面两条操作含义完全不同：

```text
删除数据库记录：业务数据不存在了
删除 Redis Key：缓存失效，真实数据可能仍然存在
```

缓存删除通常只是让下一次读取重新访问数据库。

## 四、数据库和 Redis 的职责

### 1. 数据库通常是事实来源

对用户、订单和文章等长期业务数据，可以先这样理解：

```text
数据库：保存真实业务数据
Redis：保存访问加速数据
```

当 Redis 没有数据时，应用应该能够回到数据库查询并重新构建缓存。这样的缓存称为可重建缓存。

### 2. 不是所有数据都适合缓存

适合缓存的数据通常具有以下特点：

- 读取多、写入少；
- 查询成本较高；
- 可以接受短时间的数据延迟；
- 数据能够从数据库或其他来源重建。

不一定适合缓存的数据包括：

- 每次都必须读取最新值；
- 数据变化非常频繁；
- 结果很大但命中率很低；
- 缓存后会带来严重的一致性问题。

### 3. 缓存失败时如何处理

如果 Redis 暂时不可用，可以根据业务决定：

```text
非核心缓存：
    -> 记录错误
    -> 直接查询数据库

必须依赖 Redis 的状态：
    -> 快速失败
    -> 返回明确错误
```

不能把所有 Redis 异常都静默吞掉，否则会很难知道系统已经失去缓存能力。

## 六、常见错误

### 1. 只写缓存，不保存数据库

如果业务数据只写入 Redis：

```text
Redis 重启或数据过期
    -> 数据可能无法恢复
```

除非业务明确设计为纯临时状态，否则长期业务数据应该有可靠的数据来源。

### 2. 数据库更新后不处理缓存

```text
数据库：新标题
Redis：旧标题
```

之后的请求可能一直读到旧缓存，直到缓存自然过期。更新数据库后，至少要考虑删除或更新相关缓存。

### 3. 把缓存未命中当成系统错误

缓存未命中是正常情况，尤其是：

- 第一次访问；
- Key 已过期；
- Redis 被清理；
- 服务刚刚重启。

应用应该有明确的回源数据库逻辑。

### 4. 回填缓存时忘记过期时间

```python
redis_client.set(key, value)
```

如果这是缓存数据，通常应该写成：

```python
redis_client.set(key, value, ex=300)
```

### 5. 只删除一个 Key，但实际存在多个缓存

一个业务对象可能有多个缓存视图：

```text
article:42:detail
article:list:homepage
article:list:latest
```

更新文章后只删除详情缓存，列表缓存仍然可能保存旧数据。实际项目需要明确缓存 Key 之间的关系。

## 七、面试回答模板

### 题目：什么是 Cache Aside？

> Cache Aside 是一种旁路缓存模式。读取时先查询缓存，命中就直接返回；未命中时查询数据库，将结果写入缓存后返回。写入时通常先更新数据库，再删除对应缓存，让下一次读取从数据库获取新数据并重新回填。

### 题目：为什么更新数据库后通常删除缓存？

> 直接更新缓存需要重新组装缓存对象，还可能遗漏其他相关缓存 Key。删除缓存的流程更简单，下一次读取时可以从数据库读取最新数据并重建缓存。不过删除和数据库更新也可能出现失败或并发问题，复杂场景还需要进一步设计一致性策略。

### 题目：Redis 和数据库谁是真实数据来源？

> 对用户、订单、文章等长期业务数据，通常由数据库作为事实来源，Redis 作为缓存或短期状态存储。缓存应该能够在失效后从数据库重建。只有经过专门设计并满足持久化和恢复要求的场景，才考虑让 Redis 承担更核心的数据存储职责。
