## 二、Redis 为什么快：先记住框架

面试中回答"Redis 为什么快"，建议按四个层面展开：

```text
1. 数据在内存：省掉磁盘 IO
2. 数据结构高效：SDS、跳表、压缩结构，为常见操作设计
3. 单线程 + 事件驱动：避免锁竞争和上下文切换
4. 网络处理高效：IO 多路复用，一个线程管理大量连接
```

不要只回答"因为它把数据放在内存里"——内存只是第一层，面试官通常会继续追问。下面逐层展开。

---

## 三、单线程模型与 IO 多路复用

### 1. "单线程"指的是什么

```text
Redis 的命令执行是单线程的
    -> 同一时刻只有一个命令在被执行
    -> 命令之间天然不会并发冲突
    -> 这正是第 9 课说的"单条命令是原子的"的底层原因
```

注意 6.0 之后的细节：**网络 IO 部分引入了多线程**（处理读写系统调用），但**命令执行仍然是单线程**。面试时说"Redis 是单线程的"，指的就是命令执行。

### 2. 单线程为什么不慢

两个原因：

```text
没有锁：不需要处理多线程并发修改同一结构（如哈希表扩容竞争）
没有上下文切换：不会频繁切换线程，CPU 缓存命中率高
```

而单线程的瓶颈在网络等待。解决方式：IO 多路复用。

### 3. IO 多路复用（概念级）

可以理解成"一个前台同时接待很多顾客"：

```text
传统方式：一个连接一个线程
    连接多了 -> 线程多了 -> 切换和锁变多

多路复用：一个线程监听大量连接
    哪个连接来数据了，就处理哪个
    等待时不需要一直占着 CPU
```

Linux 上实现多路复用的核心是 epoll：内核帮你盯着所有连接，有数据到达时通知 Redis 处理。Redis 的事件驱动模型就建立在这上面。

### 4. 常见误解

```text
"单线程 = 性能弱"
    -> 不是。单线程避免了锁和切换，内存操作本身足够快

"Redis 完全没有多线程"
    -> 6.0 起网络 IO 有多线程，但命令执行仍是单线程
```

## 四、String 的底层：SDS

String 不是直接用 C 语言的字符串，而是用 Redis 自己实现的 **SDS**（Simple Dynamic String，简单动态字符串）。

```text
C 字符串的问题：
    获取长度要遍历，O(n)
    中间不能有 \0，不是二进制安全
    每次修改可能重新分配内存

SDS 的做法：
    额外记录长度 -> 获取长度 O(1)
    按字节保存 -> 二进制安全（可以存图片、序列化数据）
    预分配空间 -> 减少频繁分配
```

对应到使用层面：Redis 的 String 可以安全地存 JSON、二进制数据，不用担心 C 字符串的"截断"问题。

补充一个观察点：同一个 String，值不同，底层编码也不同：

```text
整数       -> int 编码
短字符串   -> embstr
长字符串   -> raw
```

这是 Redis 的"按值选择编码"的自动优化，使用者不需要干预。

## 五、List 的底层：quicklist 与 listpack

List 的底层在 Redis 版本间有过演进，是面试常考的点：

```text
旧方案：ziplist（压缩列表）
    -> 连续内存、省空间
    -> 但大列表的插入删除需要移动大量数据

Redis 7 现状：quicklist（快表）
    -> 本质是双向链表
    -> 每个节点存一个 listpack
    -> （listpack 在 Redis 7 取代了 ziplist）
```

一句话概括：

```text
quicklist = 双向链表 + 节点内用压缩结构（listpack）
```

这样既保留压缩结构的省内存，又避免单个大结构插入删除时的大量移动。

面试提示：如果被问到 ziplist，可以接一句"ziplist 在 Redis 7 已被 listpack 取代"，体现你了解版本演进。

---

## 六、Set 的底层：intset 与哈希表

Set 的底层按内容自动选择：

```text
全部是整数且数量少：intset（整数集合）
    -> 连续内存、省空间、查找快

其他情况：哈希表（hashtable）
    -> 支持任意字符串成员
```

```text
intset 是排序的整数数组
    -> 二分查找 O(log n)
    -> 元素全是小整数时非常高效
```

使用影响：全整数的 ID 集合（例如 `user:1001:followed_ids`）天然走 intset；一旦加入字符串成员，自动切换到哈希表。

---

## 七、Sorted Set 的底层：跳表与哈希表

Sorted Set 是"既要按分数排序、又要按成员查找"：

```text
跳表（skiplist）：按分数有序，支持范围查询（ZRANGE）
哈希表：按成员 O(1) 查找分数（ZSCORE）
```

为什么用跳表而不是平衡树：

```text
跳表：多层链表，随机提升层级
    -> 查询 O(log n)，与平衡树同量级
    -> 实现简单，插入删除的调整成本低
```

```text
小规模时（成员少）：直接用 listpack 保存，不建跳表
规模变大后：listpack -> 跳表 + 哈希表
```

一句话概括：

```text
Sorted Set = 跳表（排序）+ 哈希表（查找）
```

## 八、哈希表与渐进式 rehash

Redis 的 dict（哈希表）在元素变多时需要扩容，但**不能一次性完成**（会阻塞服务），所以采用**渐进式 rehash**：

```text
扩容时
    -> 准备一个新的大哈希表
    -> 每次操作顺带搬一部分数据
    -> 分多次搬完，中间查询先看旧表再看新表
    -> 整个过程不阻塞
```

```text
一次性 rehash：数据多时可能阻塞 Redis 几十毫秒甚至更久
渐进式 rehash：把工作分摊到每次操作里，避免卡顿
```

这也解释了工程上的一个直觉：要避免某一次操作突然让 Redis 做大动作（例如一次性写入大量 Key 触发扩容）。

## 九、用 OBJECT ENCODING 观察底层编码

不用背，可以用命令直接看某个 Key 的底层编码：

```redis
SET n 123
OBJECT ENCODING n              # int

SET s "hello"
OBJECT ENCODING s              # embstr

LPUSH small-list a b c
OBJECT ENCODING small-list     # listpack（Redis 7 小列表）

LPUSH big-list a b c ...（插入大量元素）
OBJECT ENCODING big-list       # quicklist

SADD int-set 1 2 3
OBJECT ENCODING int-set        # intset

ZADD zs 1 a 2 b 3 c
OBJECT ENCODING zs             # 小规模是 listpack，变大后是 skiplist
```

```text
OBJECT ENCODING key：查看 Key 当前的底层编码
```

观察时注意：编码会随数据规模、内容自动变化，这是 Redis 自动做的优化，不需要手动指定。

## 十、面试回答模板

### 题目：Redis 为什么快？

> 可以从四个层面回答：第一，数据在内存中，避免了磁盘 IO；第二，为常见操作设计了高效的数据结构，比如 SDS、跳表、压缩结构；第三，命令执行是单线程的，避免了锁竞争和上下文切换；第四，用 IO 多路复用（epoll）让一个线程管理大量连接。单线程不等于性能弱，6.0 之后网络 IO 引入了多线程，但命令执行仍然是单线程。

### 题目：List 的底层结构是什么？

> Redis 7 中 List 使用 quicklist 实现，它是双向链表，每个节点保存一个 listpack 压缩结构。小的列表直接使用 listpack，数据变大后升级为 quicklist。早期的 ziplist 在 Redis 7 已被 listpack 取代。

### 题目：Redis 单线程为什么还能支撑高并发？

> Redis 的性能瓶颈主要在网络等待而不是 CPU 计算。单线程执行命令避免了锁竞争和上下文切换，再通过 IO 多路复用（epoll）监听大量连接，连接有数据到达时才处理。内存操作本身很快，所以单线程足够。

### 题目：Sorted Set 的底层为什么用跳表？

> Sorted Set 需要按分数有序，同时需要按成员快速查找，因此用跳表负责排序和范围查询、哈希表负责按成员查找。跳表查询复杂度是 O(log n)，与平衡树同量级，但实现更简单、插入删除的调整成本更低。
