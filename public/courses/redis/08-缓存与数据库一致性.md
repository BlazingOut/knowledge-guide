# 缓存与数据库一致性

> 这一课学习数据库和 Redis 同时保存一份业务数据时，为什么可能出现不一致。
>
> 重点掌握常见的更新策略和最终一致性，不把缓存删除误认为数据库事务。

## 一、这一课要解决什么问题

使用 Cache Aside 时，数据通常同时出现在两个地方：

```text
数据库：真实业务数据
Redis：访问加速数据
```

更新数据时，如果两个操作没有按照合适的顺序执行，就可能出现：

```text
数据库：新数据
Redis：旧数据
```

本课回答四个问题：

1. 为什么数据库和缓存会不一致？
2. 更新数据库和删除缓存哪个应该先做？
3. 什么是延迟双删？
4. 缓存删除失败时应该怎么办？

---

## 二、为什么会不一致

### 1. 写入数据库成功，删除缓存失败

```text
更新数据库成功
    -> Redis 删除失败
    -> Redis 仍然返回旧数据
```

这时数据库已经是新值，但缓存仍然是旧值。

### 2. 删除缓存成功，数据库更新失败

```text
删除缓存成功
    -> 数据库更新失败
    -> 下一次读取从数据库加载旧值
    -> 缓存又被写回旧值
```

这不一定造成长期错误，但会多一次缓存重建。

### 3. 并发读写交错

假设一个请求正在更新，另一个请求正在读取：

```text
线程 A：更新数据库
线程 B：读取数据库旧值
线程 A：删除缓存
线程 B：把旧值写回缓存
```

即使每一步单独看都成功，最后 Redis 仍然可能保存旧值。

缓存和数据库是两个独立系统，普通的 `SET`、`DELETE` 和 SQL 提交不会自动组成一个跨系统事务。

---

## 三、常见更新策略

### 1. 先更新数据库，再删除缓存

这是 Cache Aside 中最常见的基本策略：

```text
1. 更新数据库
2. 删除缓存
```

伪代码：

```python
database.update(article_id, title)
redis.delete(article_key(article_id))
```

下一次读取时：

```text
缓存不存在
    -> 查询数据库中的新值
    -> 回填缓存
```

这种方式的优点是逻辑简单，数据库仍然是事实来源。

### 2. 先删除缓存，再更新数据库

另一种顺序是：

```text
1. 删除缓存
2. 更新数据库
```

它存在一个明显风险：

```text
删除缓存
    -> 读请求查询数据库旧值
    -> 读请求把旧值写回缓存
    -> 写请求更新数据库
```

最后缓存可能保存旧值。因此通常不把它作为最简单的默认方案。

### 3. 直接更新缓存

也可以采用：

```text
1. 更新数据库
2. 更新缓存
```

但需要知道所有相关缓存，并确保缓存对象和数据库更新保持一致。如果同一条数据有详情缓存、列表缓存和统计缓存，直接更新所有缓存容易遗漏。

因此，在大多数简单的 Cache Aside 场景中，“更新数据库后删除缓存”更容易维护。

---

## 四、延迟双删

### 1. 基本思路

延迟双删通常表示：

```text
1. 先删除缓存
2. 更新数据库
3. 等待一小段时间
4. 再删除一次缓存
```

它试图处理并发读请求把旧数据重新写回缓存的问题：

```text
删除缓存
    -> 更新数据库
    -> 等待可能正在进行的读请求结束
    -> 再删除缓存
```

### 2. 延迟双删不是万能方案

它仍然有局限：

- 延迟时间很难精确选择；
- 删除动作仍然可能失败；
- 不能替代事务；
- 不能解决所有并发交错；
- 需要额外的异步任务或重试机制。

因此，延迟双删只能作为降低风险的一种策略，不能保证绝对强一致。

### 3. 当前阶段的结论

先掌握下面的默认思路：

```text
更新数据库
    -> 删除缓存
    -> 删除失败则记录并重试
    -> 下一次读取重新回填
```

如果业务对一致性要求更高，再引入消息、重试表、订阅数据库变更或专门的一致性方案。

## 五、缓存删除失败怎么办

缓存删除失败时不能静默忽略：

```python
try:
    redis.delete(key)
except RedisError:
    logger.exception("failed to delete cache", extra={"key": key})
```

常见处理方式：

- 记录错误日志；
- 短时间重试；
- 写入待处理任务；
- 由后台任务补偿删除；
- 使用较短 TTL 让旧值最终失效；
- 对关键数据触发告警。

选择哪种方式要看业务：

```text
普通查询缓存：
    删除失败后记录日志并等待过期，通常可以接受

权限、库存或重要状态：
    需要更可靠的补偿、版本或一致性方案
```

不要为了“缓存删除成功”无限重试。无限重试可能阻塞请求，并进一步增加 Redis 和数据库压力。

## 六、最终一致性

很多缓存系统追求的不是任何时刻都完全相同，而是：

```text
经过有限时间和补偿处理后，
缓存最终会与数据库保持一致。
```

这叫最终一致性。

例如：

```text
数据库已经更新
    -> 第一次删除缓存失败
    -> 后台重试删除成功
    -> 后续请求重新回源数据库
    -> 缓存恢复为新值
```

是否可以接受最终一致性，要看业务：

- 文章阅读数：通常可以接受短暂延迟；
- 用户头像：通常可以接受短暂旧值；
- 账户余额：不能只依赖普通缓存；
- 库存扣减：需要数据库事务和并发控制。

缓存一致性设计必须从业务可接受的错误范围出发。

## 八、常见错误

### 1. 认为删除缓存和更新数据库是一个事务

Redis 和 MySQL 是两个独立系统。数据库事务回滚时，不会自动回滚已经执行的 Redis 删除；Redis 删除失败也不会自动回滚数据库更新。

### 2. 只更新数据库，不处理缓存

这样旧缓存会一直存在，直到自然过期。对于允许短暂旧数据的缓存，可以接受有限延迟，但必须明确过期时间和更新策略。

### 3. 看到延迟双删就认为绝对一致

延迟双删只是降低并发旧值回填的概率，仍然可能遇到删除失败、延迟选择不合适和新的并发请求。

### 4. 失败后无限重试

无限重试会让请求一直阻塞，也可能形成重试风暴。应该设置最大次数、退避时间和失败后的补偿路径。

### 5. 给所有数据使用同一种一致性策略

文章详情和账户余额的容忍程度不同。缓存策略应该由业务数据的正确性要求决定。

## 九、面试回答模板

### 题目：更新数据库后为什么通常删除缓存？

> 数据库是事实来源，更新数据库后删除缓存，可以让下一次读取从数据库获得新值并重新回填。相比直接更新多个缓存，删除缓存通常更简单，也不容易遗漏相关 Key。但删除失败和并发读写仍然可能造成短暂不一致，需要结合重试、补偿和 TTL 处理。

### 题目：先删除缓存还是先更新数据库？

> 常见的基本方案是先更新数据库，再删除缓存。先删除缓存再更新数据库时，可能出现读请求在数据库更新前读到旧值并把旧值重新写回缓存。具体方案还要结合并发模型、一致性要求和补偿机制判断。

### 题目：什么是最终一致性？

> 最终一致性表示数据在某个短时间内可能不一致，但通过重试、补偿、过期或重新读取，经过有限时间后最终恢复一致。它适合能够容忍短暂旧数据的缓存场景，不适合直接替代余额、库存等强一致业务逻辑。
