# 第12课:Redis List、Stream 与异步任务

> 这一课学习如何把耗时工作从 HTTP 请求中取出来，交给后台 Worker 执行。
>
> 重点理解生产者、消费者、任务状态和失败重试，不把 List 或 Stream 直接等同于完整消息队列产品。

## 一、这一课要解决什么问题

有些操作不适合在 HTTP 请求中同步完成：

```text
发送邮件
生成报告
调用耗时模型
处理上传文件
```

如果接口一直等待任务完成：

```text
请求
    -> 执行耗时任务
    -> 等待很久
    -> 返回结果
```

可能导致请求超时，也会占用 Web Worker。异步任务的基本流程是：

```text
客户端
    -> API 创建任务
    -> 任务进入队列
    -> API 立即返回任务 ID
    -> Worker 从队列取任务
    -> Worker 执行并保存状态
    -> 客户端查询任务结果
```

本课回答四个问题：

1. 生产者和消费者分别做什么？
2. 如何使用 List 实现一个简单任务队列？
3. Redis Stream 解决了哪些 List 不方便处理的问题？
4. 任务失败时如何保存状态并进行有限重试？

---

## 二、生产者和消费者

### 1. 生产者

生产者负责创建任务并放入队列：

```text
API 服务
    -> 创建任务记录
    -> 把任务 ID 放入队列
    -> 返回任务 ID
```

生产者不负责完成耗时任务，只负责可靠地提交任务。

### 2. 消费者

消费者通常是独立的 Worker 进程：

```text
Worker
    -> 从队列取出任务
    -> 执行业务逻辑
    -> 更新任务状态
```

消费者可以有多个，但多个消费者同时处理同一个任务时，需要结合任务状态、幂等键或分布式锁避免重复业务效果。

### 3. 任务状态

一个简单任务可以使用：

```text
pending   等待处理
running   正在处理
succeeded 处理成功
failed    处理失败
retrying  等待重试
```

状态应该保存任务 ID、创建时间、重试次数、结果和最后一次错误：

```json
{
  "task_id": "task-9001",
  "status": "running",
  "retry_count": 0,
  "error": null
}
```

队列只负责传递待处理任务，任务状态需要单独保存。

## 三、使用 List 实现简单任务队列

### 1. 入队和出队

生产者可以使用：

```redis
LPUSH tasks '{"task_id":"task-9001"}'
```

消费者可以使用阻塞读取：

```redis
BRPOP tasks 5
```

`5` 表示最多等待 5 秒。如果队列为空，消费者不会一直占用 CPU 轮询。

### 2. List 的优点

- 结构简单；
- 命令容易理解；
- 适合单一队列和简单消费者；
- 可以使用阻塞读取等待任务。

### 3. List 的局限

使用 List 实现任务队列时，需要额外考虑：

- 消费者取出任务后崩溃怎么办；
- 任务是否已经成功处理；
- 如何重新投递失败任务；
- 多个消费者如何查看处理记录；
- 消息是否重复。

如果直接使用 `BRPOP`，任务从队列中取出后就不再存在于原队列：

```text
BRPOP 成功取出
    -> Worker 崩溃
    -> 任务可能丢失
```

更可靠的 List 队列通常会使用“待处理队列”和“处理中队列”，或者直接使用支持消息确认的模型。

## 四、Redis Stream 的基本认识

### 1. Stream 保存带 ID 的消息

写入一条 Stream 消息：

```redis
XADD tasks:stream * task_id task-9001 type report
```

Redis 会为消息生成一个 ID，并保存字段和值。

读取消息：

```redis
XREAD COUNT 10 STREAMS tasks:stream 0
```

Stream 中的消息可以被记录和按 ID 读取，比简单 List 更适合观察消息历史。

### 2. 消费者组

多个消费者可以加入同一个消费者组：

```redis
XGROUP CREATE tasks:stream workers $
```

消费者从组中读取：

```redis
XREADGROUP GROUP workers worker-1 COUNT 1 BLOCK 5000 STREAMS tasks:stream >
```

处理成功后确认：

```redis
XACK tasks:stream workers 1690000000000-0
```

这里只需要先理解几个角色：

```text
Stream：消息流
消费者组：共同消费一组消息的消费者
消费者名称：组内区分不同 Worker
确认：告诉 Redis 这条消息已经处理完成
```

### 3. Stream 也不是自动可靠

即使使用 Stream，仍然需要业务代码处理：

- 消费者处理失败；
- 未确认消息；
- 消息重试；
- 重复消费；
- 死信；
- 消息保留时间和清理。

Redis 提供数据结构和读取机制，不会自动替你决定业务失败后的处理方式。

## 五、任务失败与重试

### 1. 有限重试

任务失败时可以按次数重试：

```text
第一次失败 -> retry_count=1
第二次失败 -> retry_count=2
超过最大次数 -> failed 或 dead-letter
```

重试必须有上限：

```text
最大重试次数：3
```

不能无限重试，因为下游永久失败时，无限重试会持续消耗 Worker 和网络资源。

### 2. 失败状态

失败任务至少记录：

- 任务 ID；
- 当前状态；
- 重试次数；
- 最后一次错误；
- 下一次重试时间；
- 创建和更新时间。

这样才能回答：

```text
任务是否处理过？
失败了几次？
为什么失败？
是否还会重试？
```

### 3. 重复消费

Worker 可能在业务操作成功后、确认消息前崩溃：

```text
业务操作成功
    -> Worker 尚未 ACK
    -> Worker 崩溃
    -> 消息再次投递
```

因此消费者必须设计成幂等的，可以使用任务 ID、请求号、数据库唯一约束或状态检查避免重复产生业务效果。

## 七、常见错误

### 1. 在 HTTP 请求中同步执行所有耗时任务

耗时任务会占用请求处理资源，增加超时和重试概率。适合异步处理的任务应该尽快入队并返回任务 ID。

### 2. `BRPOP` 后直接认为任务已经完成

`BRPOP` 只表示任务从队列中取出，不代表业务处理成功。任务状态必须在业务完成后更新。

### 3. 失败后无限重试

应设置最大次数和退避时间。超过次数后进入失败或死信状态，等待人工处理或单独补偿。

### 4. 认为 Stream 自动避免重复消费

Stream 的确认机制可以帮助管理消息，但业务处理可能在确认前成功，因此仍然可能重复消费。消费者必须保持幂等。

### 5. 只保存队列消息，不保存任务状态

没有任务状态时，客户端无法查询任务是否完成，运维人员也无法知道任务为什么失败。

## 八、面试回答模板

### 题目：为什么要使用异步任务？

> 对发送邮件、生成报告或调用耗时模型等操作，如果在 HTTP 请求中同步执行，会增加响应时间和超时概率。异步任务让 API 快速创建任务并返回任务 ID，由后台 Worker 执行，客户端再查询任务状态或接收结果。

### 题目：List 和 Stream 有什么区别？

> List 更像简单的有序队列，适合基础入队和阻塞出队；Stream 为消息提供 ID 和历史记录，并支持消费者组和确认，更适合需要跟踪消费进度的场景。但两者都不会自动解决重复消费、失败重试和业务幂等。

### 题目：为什么消息确认后还可能重复消费？

> Worker 可能已经完成业务操作，但在确认消息前崩溃。消息系统会认为它没有处理完成并再次投递，因此消费者必须设计成幂等，使用任务 ID、请求号或数据库约束避免重复业务效果。
