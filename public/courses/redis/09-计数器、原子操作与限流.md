# 第9课:Redis 计数器、原子操作与限流

> 这一课学习 Redis 如何记录访问次数，并限制一段时间内的请求数量。
>
> 重点理解 `INCR` 的原子性和固定窗口限流，不深入复杂的限流算法。

## 一、这一课要解决什么问题

很多后端功能都需要记录次数：

```text
某个用户今天调用了多少次接口？
某篇文章被访问了多少次？
某个 IP 在一分钟内发了多少个请求？
```

如果多个请求同时修改一个数字，应用自己读改写可能产生竞争：

```text
请求 A：读取 10
请求 B：读取 10
请求 A：写入 11
请求 B：写入 11
```

实际发生了两次增加，但结果只增加了 1。Redis 提供的 `INCR` 可以把增加操作作为一个原子操作完成。

本课回答三个问题：

1. 为什么 Redis 适合做计数器？
2. 什么是固定窗口限流？
3. 多条 Redis 命令为什么可能需要进一步的原子化处理？

## 二、Redis 计数器

### 1. 使用 `INCR`

```redis
SET article:42:views 0        # 写入计数器初始值 0
INCR article:42:views         # 数值自增 1
INCR article:42:views         # 再自增 1，累计为 2
GET article:42:views          # 读取当前计数
```

结果是：

```text
2
```

这里故意写了两次 `INCR`，是为了演示**每次调用都会 +1**：值从 0 变成 1，再变成 2。真实场景中是每次请求调用一次 `INCR`，多次请求自然累加。

一个常见的误解是把 `INCR` 当成"设置命令"，以为执行一次后这个 Key 就变成了"自增类型"，以后每次 `GET` 都会自动 +1。不是这样。Redis 的 String 没有"自增类型"；`INCR` 是一条**操作命令**，每调用一次就对当前值 +1，`GET` 永远只读取、不改变值。想 +1 就必须再调用一次 `INCR`。这和 MySQL 里声明 `AUTO_INCREMENT` 列、写入时自动生成是不同的机制。

如果 Key 不存在，`INCR` 会把它当作 `0` 再增加：

```redis
DEL counter          # 删除 Key，让它"不存在"
INCR counter         # Key 不存在时当作 0，自增后为 1
GET counter          # 结果是 1
```

结果是：

```text
1
```

常见命令：

| 命令 | 含义 | 参数说明 |
|---|---|---|
| `INCR key` | 数值自增 1 | Key 不存在时当作 0 处理 |
| `DECR key` | 数值自减 1 | 自增的逆向操作 |
| `INCRBY key increment` | 数值增加指定数值 | `increment` 可以为负数 |
| `DECRBY key decrement` | 数值减少指定数值 | `decrement` 可以为负数 |

### 2. 计数器的常见用途

- 文章浏览次数；
- 用户接口调用次数；
- 任务重试次数；
- 在线人数的近似统计；
- 某个时间窗口内的请求数。

计数器只是一个数字。它不会自动解释这个数字的业务含义，也不会自动保证统计结果永久可靠。重要统计数据通常还需要异步落库或定期汇总。

### 3. 给计数器设置过期时间

统计固定时间窗口时，可以给计数器设置过期时间：

```redis
SET rate:user:1001:minute 1 EX 60 NX   # 只在 Key 不存在时写入：值 1，60 秒过期
INCR rate:user:1001:minute             # 后续请求：只增加计数，不刷新过期时间
```

这里的 `NX`（Not eXists）表示只在 Key 不存在时写入，`EX 60` 表示 60 秒过期。第一次创建时设置过期时间，后续增加不应该反复刷新过期时间（`NX` 的完整讲解见幂等键一课）。

如果使用 Python：

```python
created = client.set(key, 1, ex=60, nx=True)   # 只在 Key 不存在时创建：值 1，60 秒过期
if not created:
    client.incr(key)                            # 已存在：只增加计数
```

这里的关键是：窗口开始时设置过期时间，后续请求只增加计数。

## 三、原子操作

### 1. 什么是原子操作

原子操作可以先简单理解为：

```text
执行过程中不会被另一个请求插入到中间
```

多个请求同时执行 `INCR` 时，Redis 会依次处理这些增加操作，不会因为两个请求同时读取旧值而丢失一次增加。

### 2. `INCR` 和 Python 读改写的区别

不推荐这样实现计数：

```python
current = int(client.get(key) or 0)   # 反例：读取当前值
client.set(key, current + 1)          # 反例：写回，中间可能被其他请求插入
```

并发时可能发生：

```text
请求 A 读取 10
请求 B 读取 10
请求 A 写入 11
请求 B 写入 11
```

更适合使用：

```python
client.incr(key)   # 原子操作：读取、增加、写回由 Redis 一次完成
```

把“读取、增加、写回”交给 Redis 的单个命令完成。

### 3. 多条命令不是一个整体

下面两条命令分别执行时，中间可能有其他请求插入：

```python
client.incr(key)        # 两条命令不是整体
client.expire(key, 60)  # 中间可能被其他请求插入
```

如果程序在两条命令之间崩溃，计数器可能有值但没有过期时间。可以在第一次创建时使用 `SET NX EX`，或者在需要时使用事务或 Lua 脚本把多步操作组织起来。

本课先掌握基本原则：

```text
一个 Redis 命令通常是原子的
多条命令组合起来不一定是原子的
```

## 四、固定窗口限流

### 1. 什么是限流

限流是限制请求进入系统的速度或数量：

```text
同一个用户
一分钟最多调用 60 次
```

超过限制后，接口可以返回：

```text
HTTP 429 Too Many Requests
```

限流可以保护：

- 数据库；
- 模型服务；
- 第三方 API；
- Redis 自身；
- 业务接口的处理能力。

### 2. 固定窗口的思路

固定窗口把时间划分为一段一段的区间：

```text
12:00:00 - 12:00:59
12:01:00 - 12:01:59
```

以用户和当前分钟组成 Key：

```text
rate:user:1001:202610181230
```

每收到一次请求，就增加计数：

```text
INCR rate:user:1001:202610181230
```

如果计数超过限制，就拒绝请求。

### 3. 固定窗口的基本流程

```text
1. 根据用户和当前时间生成 Key
2. 增加这个窗口的计数
3. 第一次创建时设置过期时间
4. 读取计数
5. 小于等于限制：允许请求
6. 超过限制：返回 429
```

固定窗口简单易懂，但窗口边界处可能出现突发流量：

```text
12:00:59 发送 60 次
12:01:00 再发送 60 次
```

短时间内可能通过 120 次请求。更平滑的滑动窗口和令牌桶会在后续需要时再学习。

## 六、常见错误

### 1. 用 Python 读改写实现并发计数

并发场景下，`GET`、Python 加法和 `SET` 不是一个整体，可能丢失更新。优先使用 `INCR` 或 `INCRBY`。

### 2. 每次请求都刷新窗口

如果每次 `INCR` 后都执行：

```python
client.expire(key, 60)
```

那么窗口会不断向后延长，实际变成“最近 60 秒没有请求才过期”，不再是固定窗口。通常只在 Key 第一次创建时设置过期时间。

### 3. 把计数器当成永久统计

设置了 TTL 的计数器会自动消失。如果需要长期统计，应在合适的时机汇总到数据库或专门的统计系统。

### 4. 把固定窗口当成平滑限流

固定窗口在边界处可能出现突发请求。它适合简单接口保护，不适合所有高精度流量控制场景。

### 5. 超过限制后仍然执行业务逻辑

限流判断应该发生在昂贵操作之前：

```text
检查限流
    -> 超过限制：立即返回
    -> 未超过：调用数据库或模型服务
```

不能先调用模型，再判断是否超过次数。

## 七、面试回答模板

### 题目：为什么 Redis 适合做计数器？

> Redis 提供 `INCR` 和 `INCRBY` 等原子操作，可以在并发请求下安全地增加数字，避免应用层读改写造成丢失更新。同时可以为计数器设置过期时间，适合访问次数、重试次数和时间窗口限流。

### 题目：固定窗口限流怎么实现？

> 根据用户、接口和当前时间窗口生成 Redis Key，每次请求使用 `INCR` 增加计数，第一次创建时设置窗口过期时间。如果计数超过限制，就返回 429。固定窗口实现简单，但在窗口边界可能出现突发流量。

### 题目：为什么 `INCR` 后还要考虑原子性？

> 单独的 `INCR` 是原子的，但如果还需要设置过期时间、读取计数和做其他判断，多条命令之间可能被其他请求插入。简单场景可以用 `SET NX EX` 初始化，复杂场景需要事务或 Lua 脚本把多步操作组织起来。
