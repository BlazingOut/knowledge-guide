# 第10课:Redis 幂等键与重复请求

> 这一课学习如何防止网络重试造成重复创建、重复扣款或重复提交。
>
> 重点是理解幂等键和请求状态，不在本课深入分布式锁。

## 一、这一课要解决什么问题

客户端发送请求后，可能遇到这些情况：

```text
客户端发送请求
    -> 服务端已经处理成功
    -> 响应在网络中丢失
    -> 客户端认为失败并重试
```

如果服务端把重试当成新请求，就可能出现：

```text
创建两个任务
扣款两次
发送两封邮件
生成两条相同记录
```

幂等的目标是：

```text
同一个业务请求执行一次或多次，
最终结果保持一致。
```

本课回答三个问题：

1. 为什么网络重试会造成重复执行？
2. 如何使用唯一请求号识别重复请求？
3. Redis 应该保存什么状态，数据库还需要做什么？

---

## 二、什么是幂等

### 1. 幂等的含义

如果同一个请求重复提交，系统最终只产生一次业务效果，就可以认为这个操作具有幂等性。

例如，设置用户昵称：

```text
PUT /users/1001/name = Alice
```

执行一次或执行多次，最终昵称都是 `Alice`，通常是幂等的。

而创建订单：

```text
POST /orders
```

每次都可能创建新订单，默认不是幂等的。

### 2. 幂等不是“请求只能到达一次”

网络系统无法保证客户端只发送一次请求。幂等设计解决的是：

```text
请求可能重复到达
    -> 服务端能够识别重复请求
    -> 不重复产生业务效果
```

它不能阻止网络重试，只能让重复执行变得安全。

## 三、幂等键

幂等键解决重复请求的完整链路是：

```text
客户端生成唯一键
    -> 服务端用这个键保存请求状态
    -> 第一个请求用原子命令登记，获得处理权
    -> 重复请求查状态、直接复用结果
```

下面按这条链路的顺序展开。

### 1. 什么是幂等键

幂等键（idempotency key）是**客户端为一次业务操作生成的唯一标识**，随请求一起发送给服务端。服务端靠它判断两个请求是否属于同一次操作。

类比快递单号：

```text
同一个包裹，不管寄几次通知
    -> 都靠同一个单号识别
    -> 换一个单号，就变成了另一个包裹
```

```text
request_id = 8f2b...   # 一次业务操作的唯一标识
```

之后的重试必须使用同一个请求号：

```text
第一次请求：request_id=8f2b...
重试请求：  request_id=8f2b...
```

如果每次重试都生成新的请求号，服务端无法判断它们属于同一次业务操作，幂等机制就失效了。

### 2. 幂等键怎么用：把请求状态存进 Redis

服务端把幂等键当作 Redis 的 Key 名，保存这个请求的处理状态：

```text
idempotency:request:8f2b...
```

状态可以简单分为：

```text
processing：正在处理
succeeded：处理成功
failed：处理失败
```

成功时还可以保存业务结果：

```json
{
  "status": "succeeded",
  "task_id": "task-9001"
}
```

重复请求到达时，按状态处理：

```text
已成功：
    -> 直接返回之前的结果

正在处理：
    -> 返回处理中，或让客户端稍后查询

已失败：
    -> 根据业务决定返回失败，还是允许重新处理
```

### 3. 第一个请求怎么抢到处理权：`SET NX EX`

两个相同的请求可能**同时**到达。如果都开始执行业务，就会重复创建。所以第一步必须保证：只有一个请求能登记成功。

第一次收到请求时，使用一条命令完成"检查 + 写入"：

```redis
SET idempotency:request:8f2b... processing NX EX 300
```

这里用到的是 `SET` 的完整形式，可以带可选参数：

```text
SET key value [EX 秒数] [NX]
    key value：写入的 Key 和值
    EX 秒数：写入后多少秒自动过期
    NX：只在 Key 不存在时写入（Not eXists 的缩写）
```

`NX` 和 `EX` 可以一起用，也可以单独用。上面的命令表示：**只有这个 Key 还不存在时才写入，写入后 300 秒过期**。

结果有两种：

```text
OK    写入成功：当前请求第一个登记，获得了处理权
(nil) 没有写入：Key 已存在，说明这个请求号已经被其他请求登记
```

为什么不写成"先 `EXISTS` 再 `SET`"两步？因为两条命令之间可能被其他请求插入，两个请求可能同时通过检查。`SET NX` 把"检查不存在 + 写入"放在一条命令里完成，天然没有这个竞争——这和第 9 课说的"单条命令通常是原子的"是同一件事。

这一步的作用是防止两个相同请求同时开始处理。它是幂等登记的一部分，本课不把它扩展成通用分布式锁。

## 四、幂等处理流程

以"创建任务接口"为例，把客户端和服务端两方的交互分开看。

### 1. 第一次请求

```text
客户端                        服务端                            Redis
  |                            |                                |
  | 1. 发送请求                 |                                |
  |    (request_id + 参数)      |                                |
  | -------------------------->|                                |
  |                            | 2. 用 request_id 生成幂等 Key  |
  |                            | 3. SET NX EX 写入 processing   |
  |                            | ------------------------------->|
  |                            |                                | 返回 OK（第一次）
  |                            | <-------------------------------|
  |                            | 4. 执行业务操作（创建任务）       |
  |                            | 5. 保存业务结果（task_id）      |
  |                            | 6. 将状态改为 succeeded         |
  |                            | 7. 返回结果                     |
  | <--------------------------|                                |
```

要点：**客户端只做一件事——发请求**。登记、执行业务、保存结果、改状态全部由**服务端**完成，Redis 是服务端用来保存状态的组件。

### 2. 重复请求

```text
客户端                        服务端                            Redis
  |                            |                                |
  | 1. 重试请求                 |                                |
  |    (相同的 request_id)      |                                |
  | -------------------------->|                                |
  |                            | 2. 查询请求状态                 |
  |                            | ------------------------------->|
  |                            |                                | 返回状态
  |                            | <-------------------------------|
  |                            | 3. 按状态处理                   |
  |                            |    succeeded：直接返回已保存结果 |
  |                            |    processing：返回处理中        |
  |                            |    failed：按业务规则处理        |
  | <--------------------------|                                |
```

客户端仍然只负责发送（重试时用同一个 `request_id`）；是否继续执行、返回什么，由服务端根据 Redis 里的状态决定。

### 3. 业务操作成功但状态更新失败

仍然可能出现：

```text
服务端：业务操作已经成功
    -> 服务端更新 Redis 状态失败
    -> 客户端重试，请求再次到达
    -> 服务端可能再次执行业务
```

因此，重要业务不能只依赖 Redis 的状态记录。还应该使用数据库唯一约束或业务表保存最终事实：

```text
Redis：快速识别重复请求
数据库：保存不可重复的业务事实
```

### 4. 请求状态需要过期

幂等记录不能永久增长：

```redis
SET idempotency:request:8f2b... processing NX EX 300   # 同第三节：第一次登记时设置过期时间
```

过期时间要覆盖正常处理时间，并结合客户端允许重试的时间决定。过期太短，正在执行的请求可能被重复登记；过期太长，会占用更多内存并延长请求号不可复用的时间。

## 六、常见错误

### 1. 每次重试都生成新的请求号

这样服务端会认为是多个不同业务请求，幂等机制无法发挥作用。

### 2. 只在内存字典中保存幂等状态

单进程内存状态在进程重启后会丢失，多实例部署时不同实例也看不到彼此的状态。共享状态需要放在 Redis 或数据库中。

### 3. 只用 Redis，不使用数据库约束

Redis 记录可能过期、丢失或更新失败。对于订单、支付和任务记录等重要数据，数据库仍然应该通过唯一约束或业务状态保证最终不重复。

### 4. `processing` 状态永久不变

如果 Worker（执行后台任务的服务端进程）崩溃后状态永远停留在 `processing`，后续请求可能永远无法处理。状态必须有 TTL，并且需要设计超时恢复或人工处理方式。

### 5. 不检查请求参数是否一致

同一个 `request_id` 再次提交时，如果请求体完全不同，不能直接返回原结果而不做检查：

```text
第一次：request_id=A, amount=10
第二次：request_id=A, amount=100
```

服务端应该保存关键参数摘要，发现不一致时返回参数冲突。

## 七、面试回答模板

### 题目：什么是接口幂等？

> 幂等是指同一个业务请求执行一次或多次，最终业务结果一致。它主要用来处理网络超时、客户端重试和消息重复投递。常见做法是让客户端提供唯一请求号，服务端保存请求状态和处理结果，重复请求直接复用已有结果。

### 题目：Redis 如何实现幂等？

> 可以使用请求号生成幂等 Key，第一次请求通过 `SET NX EX` 登记处理状态，后续请求根据状态判断是返回已有结果、提示处理中，还是允许重试。Redis 适合做快速状态判断，但重要业务事实还需要数据库唯一约束或业务状态保证。

### 题目：为什么幂等记录需要过期时间？

> 幂等记录如果永久保存会持续占用内存，也可能阻止请求号长期复用。过期时间需要覆盖正常处理和客户端重试周期；如果处理时间较长，还要设计状态续期或超时恢复。
