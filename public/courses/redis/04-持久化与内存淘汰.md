Redis 的数据主要放在内存中，两个问题随之而来：

```text

    -> 不同配置会丢多少数据？

    -> 是拒绝写入，还是淘汰旧数据？
    -> 淘汰哪些数据？
```

## 二、RDB 持久化：定期拍快照

### 1. 原理

RDB 把内存中的数据**定期保存成一份二进制快照文件**（默认 dump.rdb）：

```text
每隔一段时间
    -> 把当前所有数据写进一个快照文件
    -> Redis 重启时直接加载这个文件
```

触发方式：

```text
SAVE：阻塞当前进程保存（不推荐）
BGSAVE：fork 子进程后台保存（推荐）
自动触发：满足配置的保存条件时（例如 60 秒内改动 10000 次）
```

### 2. 优点和缺点

```text
优点
    - 文件紧凑，适合备份和迁移
    - 恢复快：直接加载快照

缺点
    - 两次快照之间的数据可能丢失
    - 数据量大时，fork 子进程有额外开销
```

## 三、AOF 持久化：追加写命令

### 1. 原理

AOF 把**每一条写命令追加到日志文件**里，重启时重放这些命令恢复数据：

```text
SET greeting "hello"
    -> 追加进 AOF 文件
    -> 重启时按顺序重放所有写命令
```

控制落盘频率的 appendfsync 策略：

```text
always：每条命令都立即刷盘（最安全，最慢）
everysec：每秒刷一次盘（默认，最多丢 1 秒数据）
no：交给操作系统决定（最快，可能丢更多数据）
```

### 2. 文件膨胀与重写

AOF 会越来越大，需要重写压缩：

```text
写命令越来越多 -> AOF 文件膨胀
    -> BGREWRITEAOF 重写
    -> 只保留能恢复当前数据的最短命令序列
```

### 3. 优点和缺点

```text
优点
    - 丢数据少（取决于 fsync 策略）
    - 文件可读，方便排查

缺点
    - 文件通常比 RDB 大
    - 恢复时重放命令，比加载快照慢
```

## 四、混合持久化

Redis 4.0 起支持混合持久化（默认开启）：

```text
AOF 文件开头存一份 RDB 快照
    -> 快照之后的新命令继续以 AOF 追加
    -> 重启时：加载快照（快）+ 重放少量命令（丢得少）
```

```text
只开 AOF：恢复慢，丢得少
混合持久化：恢复快，丢得少
```

## 五、RDB 和 AOF 怎么选

| | RDB | AOF |
|---|---|---|
| 保存内容 | 定期快照 | 追加写命令 |
| 文件大小 | 小 | 大（可重写） |
| 丢数据 | 两次快照之间 | 取决于 fsync（默认最多 1 秒） |
| 恢复速度 | 快 | 慢（重放命令） |
| 典型场景 | 备份、迁移、可接受定期丢失 | 尽量少丢数据的缓存和状态 |

```text
选择原则：
    能接受周期性丢失 -> RDB
    尽量少丢数据 -> AOF 或混合持久化
    重要业务事实 -> 仍然放在数据库，Redis 只是加速
```

不要因为 Redis 开了持久化，就把订单、账单等不可重算的数据只放在 Redis。持久化降低丢失概率，不等于数据库的事务保证。

## 六、过期 Key 是怎么被删除的

### 1. 两种删除方式

```text
惰性删除：读取时检查
    -> GET 一个 Key 时发现已过期，顺手删除并返回 nil
    -> 不读就不删，可能暂时占用内存

定期删除：主动抽检
    -> Redis 每隔一段时间随机抽一批 Key 检查
    -> 删掉其中已过期的，避免过期 Key 长期堆积
```

两者配合：惰性删除保证"过期数据读不到"，定期删除保证"过期数据不长期占内存"。

### 2. 为什么不是"到点就删"

```text
每个 Key 都挂一个定时器
    -> 大量 Key 时开销很大
    -> Redis 选择惰性 + 定期，用较小的代价保证语义
```

## 七、内存满了之后：淘汰策略

### 1. maxmemory 与淘汰

设置 `maxmemory` 后，内存达到上限时按 `maxmemory-policy` 处理：

```text
noeviction：不淘汰，新写入返回错误（默认）
allkeys-lru：从所有 Key 里淘汰最近最少使用的
allkeys-lfu：从所有 Key 里淘汰使用频率最低的
volatile-lru / volatile-lfu：只从设置了 TTL 的 Key 里淘汰
allkeys-random / volatile-random：随机淘汰
volatile-ttl：优先淘汰剩余时间最短的 Key
```

### 2. LRU 和 LFU 是"近似"实现

```text
精确 LRU 需要记录每个 Key 的访问时间并排序
    -> 内存和 CPU 开销大

Redis 的实现：
    对 Key 做采样（每轮抽少量 Key）
    -> 从样本里选最久未使用的淘汰
    -> 是近似 LRU，不是精确 LRU
```

LFU 与 LRU 的区别：

```text
LRU：看"多久没被访问"
LFU：看"单位时间内访问了多少次"
    -> 热点数据即使刚被访问过，也可能因为访问频率低被淘汰
```

### 3. 怎么选

```text
缓存类数据：allkeys-lru（或 lfu，看热点模式）
带过期时间的缓存：volatile-lru / volatile-ttl
不能丢的写入：noeviction + 报警扩容
```

注意：淘汰策略是内存不够时的兜底，不能替代"给数据设置合理 TTL"和"容量规划"。

## 八、面试回答模板

### 题目：RDB 和 AOF 有什么区别？

> RDB 定期把内存数据保存成二进制快照，文件小、恢复快，但两次快照之间的数据可能丢失。AOF 追加每一条写命令，丢数据少（取决于 fsync 策略），但文件大、恢复慢。Redis 4.0 起支持混合持久化：AOF 文件开头是 RDB 快照，之后追加命令，兼顾恢复速度和丢数据量。

### 题目：过期的 Key 是怎么被删除的？

> Redis 使用惰性删除和定期删除结合的方式：读取时发现过期就删除并返回 nil；同时定时抽检一批 Key 清理已过期的。这样既保证过期数据读不到，又避免过期 Key 长期占用内存。不会为每个 Key 单独挂定时器。

### 题目：Redis 内存满了怎么办？

> 设置 maxmemory 后，达到上限时按 maxmemory-policy 处理：默认 noeviction 拒绝新写入，也可以选择 allkeys-lru / allkeys-lfu 等淘汰策略。Redis 的 LRU 是近似实现（采样淘汰）。淘汰是兜底，正常使用应设置合理 TTL 和容量规划。
