# 第13课:Redis 消息可靠性与综合练习

> 这一课把前面学习的缓存、限流、幂等、分布式锁和异步任务串起来。
>
> 重点不是追求“消息绝不丢失”，而是知道消息可能在哪些环节失败，并为失败、重试和重复消费设计业务处理方式。

## 一、这一课要解决什么问题

一个异步任务通常经过多个步骤：

```text
API 接收请求
    -> 创建任务
    -> 写入队列
    -> Worker 读取消息
    -> 调用下游服务
    -> 更新任务状态
    -> 确认消息
```

每一步都可能失败：

```text
任务没有成功入队
Worker 取出后崩溃
下游服务超时
业务操作成功但消息确认失败
消息被重复投递
```

本课回答四个问题：

1. 消息失败后应该如何重试？
2. 什么时候应该进入死信？
3. 如何处理重复消费？
4. 如何把 Redis、数据库和 Worker 组成一个可排查的任务流程？

---

## 二、消息处理的几个结果

### 1. 成功

```text
读取消息
    -> 业务处理成功
    -> 保存成功状态
    -> 确认消息
```

成功状态至少应该包含：

- 任务 ID；
- 处理结果；
- 完成时间；
- 消费者名称或执行记录。

### 2. 临时失败

临时失败可能由以下原因造成：

- 下游服务暂时超时；
- 网络短暂不可用；
- 数据库连接暂时失败；
- 外部 API 返回 503。

这类错误可以有限重试：

```text
第一次失败 -> retry_count=1
第二次失败 -> retry_count=2
超过上限 -> failed 或 dead-letter
```

重试不能无限进行，也不能没有等待地快速循环。

### 3. 永久失败

以下问题通常不适合反复重试：

- 请求参数不合法；
- 资源不存在；
- 权限不足；
- 数据格式无法解析；
- 业务规则明确拒绝。

这类消息应该直接标记为失败，或者进入死信队列等待人工检查。

## 三、重试与死信

### 1. 重试记录

任务状态中应该保存：

```text
task_id
status
retry_count
last_error
next_retry_at
```

这样可以知道：

```text
失败了几次？
上一次为什么失败？
什么时候再次尝试？
是否已经超过最大次数？
```

### 2. 退避

失败后不要立刻高速重试：

```text
第 1 次失败：等待 1 秒
第 2 次失败：等待 2 秒
第 3 次失败：等待 4 秒
```

实际等待时间可以加入随机抖动，避免大量任务同时再次请求下游。

本课只要求理解退避的目的：

```text
给暂时失败的系统恢复时间，
避免重试请求继续放大故障。
```

### 3. 死信

超过最大重试次数，或者遇到确定的永久错误后，可以将消息放入死信队列：

```text
正常队列
    -> 处理失败
    -> 达到重试上限
    -> 死信队列
```

死信不是“把错误藏起来”，而是保存待处理的问题。死信记录应包含原始任务、失败原因、重试次数和最后更新时间。

## 四、重复消费与业务幂等

### 1. 为什么会重复消费

```text
Worker 读取消息
    -> 业务操作成功
    -> Worker 在确认消息前崩溃
    -> 消息再次被投递
```

因此，消息系统通常更容易保证：

```text
消息至少被处理一次
```

而不是保证：

```text
消息严格只被处理一次
```

### 2. 消费者必须幂等

消费者可以使用任务 ID 或业务请求号判断是否已经处理：

```text
第一次消费 task-9001
    -> 执行业务
    -> 保存 task-9001 已完成

再次消费 task-9001
    -> 发现已完成
    -> 不重复执行
```

重要业务还应由数据库唯一约束和事务提供最后保护。

### 3. 不要只依赖消息确认

消息确认只说明消息处理状态，不等于业务数据库已经正确提交：

```text
ACK 成功不代表所有业务操作都可以忽略
```

业务结果、任务状态和消息确认之间需要明确顺序，并为中间失败设计补偿。

## 五、综合 API 流程

一个完整的任务 API 可以按下面的方式设计：

```text
客户端
    -> 携带 request_id 请求 API
    -> 限流检查
    -> 幂等检查
    -> 创建数据库任务记录
    -> 写入 Redis 队列
    -> 返回 task_id

Worker
    -> 读取任务
    -> 使用任务 ID 检查重复消费
    -> 更新任务为 running
    -> 调用下游服务
    -> 成功：保存结果并更新 succeeded
    -> 临时失败：增加重试次数
    -> 超过上限：更新 failed 或写入死信
```

每个组件的职责可以先这样划分：

```text
数据库：保存长期任务事实和最终结果
Redis：缓存、幂等状态、队列和短期任务状态
API：接收请求、校验和快速返回
Worker：执行耗时任务
下游服务：提供外部能力
```

## 六、故障排查方法

排查任务失败时，先根据任务 ID 追踪：

```text
请求日志
    -> 幂等记录
    -> 数据库任务记录
    -> 队列消息
    -> Worker 日志
    -> 下游调用日志
    -> 最终任务状态
```

重点观察：

- request_id 和 task_id 是否一致；
- 是否通过了限流；
- 是否已经存在相同请求；
- 任务是否成功入队；
- Worker 是否取到任务；
- 任务状态是否从 pending 变成 running；
- 下游调用耗时和错误类型；
- retry_count 是否超过上限；
- 是否产生重复业务结果。

不要只看最后一条错误日志。异步任务的故障通常需要把多个组件的日志按任务 ID 串起来。

## 八、常见错误

### 1. 失败后无限重试

永久错误不会因为重试自动变好。必须区分临时错误和永久错误，并设置最大重试次数。

### 2. 重试没有退避

任务失败后立即重新入队，可能形成：

```text
下游变慢
    -> 请求失败
    -> 立即重试
    -> 下游更慢
    -> 更多请求失败
```

这就是重试放大故障。需要等待、退避和最大次数。

### 3. 只更新 Redis，不保存长期任务结果

Redis 中的任务状态可能过期或丢失。需要查询历史和审计的任务，应把最终状态和结果保存到数据库。

### 4. 把消息确认当成业务成功

只有在业务操作和必要的状态更新完成后，才应该确认消息。即便如此，仍要考虑确认前崩溃导致的重复消费。

### 5. 没有任务 ID 和请求 ID

没有稳定的 ID，就很难把 API 请求、队列消息、Worker 日志和数据库记录关联起来，也无法实现可靠幂等。

## 九、面试回答模板

### 题目：消息失败后如何处理？

> 先区分临时错误和永久错误。临时错误可以进行有限次数重试，并使用指数退避和随机抖动；永久错误不应无限重试，可以直接标记失败或进入死信队列。任务状态需要记录重试次数和最后一次错误。

### 题目：为什么消息会重复消费？

> Worker 可能在业务操作成功后、确认消息前崩溃，消息系统会再次投递未确认消息。因此消费者必须在业务层保证幂等，使用任务 ID、请求号、数据库唯一约束或状态检查避免重复产生业务效果。

### 题目：Redis 队列和数据库如何分工？

> Redis 适合保存短期队列、消费状态、幂等记录和快速访问的数据；数据库适合保存长期任务事实、最终结果和需要事务约束的数据。不能只因为消息放在 Redis 中，就把长期业务记录也完全交给 Redis。
