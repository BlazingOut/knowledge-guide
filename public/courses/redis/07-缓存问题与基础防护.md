# 缓存问题与基础防护

> 这一课学习缓存没有按预期发挥作用时，为什么可能反而给数据库带来更大压力。
>
> 重点掌握缓存穿透、缓存击穿、缓存雪崩和热点 Key，并了解它们的基础防护方式。

## 一、这一课要解决什么问题

正常的 Cache Aside 流程是：

```text
请求
    -> 查缓存
    -> 未命中
    -> 查数据库
    -> 回填缓存
```

如果大量请求同时未命中，就会出现：

```text
大量请求
    -> 同时绕过缓存
    -> 同时访问数据库
    -> 数据库压力突然增加
```

本课回答四个问题：

1. 什么是缓存穿透？
2. 什么是缓存击穿？
3. 什么是缓存雪崩？
4. 如何使用空值缓存、随机过期时间和基础保护措施降低风险？

---

## 二、缓存穿透

### 1. 问题是什么

缓存穿透指请求查询一个数据库中也不存在的数据：

```text
请求 ID=999999
    -> Redis 没有
    -> 数据库也没有
    -> 不回填缓存
```

如果攻击者或错误客户端不断请求大量不存在的 ID，每次请求都会访问数据库：

```text
请求 1：缓存没有 -> 数据库没有
请求 2：缓存没有 -> 数据库没有
请求 3：缓存没有 -> 数据库没有
```

### 2. 空值缓存

一种简单做法是把“不存在”也短暂缓存：

```text
查询不存在的 ID
    -> Redis 没有
    -> 数据库没有
    -> Redis 写入一个短期空值
```

例如：

```redis
SET article:999999 "__missing__" EX 30
```

下次查询时：

```text
Redis 返回 "__missing__"
    -> 直接返回资源不存在
    -> 不访问数据库
```

空值缓存的过期时间通常较短，因为一个原本不存在的资源以后可能被创建。

### 3. 参数校验

空值缓存不是唯一措施。接口还应该先做基本参数校验：

- ID 必须是正整数；
- 分页大小不能过大；
- 查询字符串不能超过合理长度；
- 用户只能查询有权限访问的资源。

无效请求不应该直接进入缓存和数据库查询流程。

## 三、缓存击穿

### 1. 问题是什么

缓存击穿通常指一个访问量很高的热点 Key 恰好过期：

```text
热点 Key 过期
    -> 大量请求同时发现缓存未命中
    -> 大量请求同时查询数据库
    -> 数据库出现瞬时压力
```

它和缓存穿透的区别是：

```text
穿透：查询的数据本来就不存在
击穿：查询的是存在的热点数据，但缓存刚好失效
```

### 2. 基础防护方式

可以采用这些方式：

- 给热点 Key 设置合理的过期时间；
- 使用随机过期时间，避免多个热点同时失效；
- 缓存重建时只允许一个请求执行；
- 其他请求等待重建结果或暂时返回旧值；
- 对热点数据进行预热；
- 使用本地缓存减少请求直接到 Redis 和数据库。

“只允许一个请求重建缓存”通常需要并发控制或分布式锁。本课只理解问题，分布式锁会在后续课程单独学习。

### 3. 旧值和新值

对于允许短时间陈旧的数据，可以考虑：

```text
缓存仍然保存旧值
    -> 先返回旧值
    -> 后台异步刷新
```

这能降低热点 Key 同时失效带来的压力，但会增加数据状态和刷新逻辑的复杂度，不能对所有业务直接使用。

## 四、缓存雪崩

### 1. 问题是什么

缓存雪崩通常指大量缓存 Key 在同一时间失效，或者 Redis 整体不可用：

```text
大量 Key 同时过期
    -> 大量请求同时访问数据库
    -> 数据库压力突然升高
```

也可能是：

```text
Redis 服务不可用
    -> 所有请求绕过缓存或直接失败
    -> 数据库和应用同时承压
```

### 2. 随机过期时间

不要让大量 Key 使用完全相同的过期时间：

```python
ttl = 300 + random.randint(0, 60)
```

这样可以把过期时间分散到一个时间范围内，降低同时失效的概率。

随机过期时间不能解决 Redis 整体宕机，也不能保证所有 Key 永远不会同时失效。它只是降低一种常见的集中失效风险。

### 3. 服务降级

当 Redis 暂时不可用时，可以根据业务选择：

```text
非核心缓存：
    -> 记录错误
    -> 回源数据库

数据库压力已经过高：
    -> 返回降级结果
    -> 限制请求
    -> 快速失败
```

降级必须有边界。无限制地绕过 Redis 查询数据库，可能把缓存故障扩大成数据库故障。

## 五、热点 Key 和大 Key

### 1. 热点 Key

热点 Key 是在短时间内被大量请求访问的 Key：

```text
article:42
```

它本身不一定是错误。问题在于：

- 所有请求都集中访问同一份数据；
- Key 失效时容易触发缓存击穿；
- Redis 单个实例可能承受过高访问量；
- 集群中可能出现请求集中到一个节点。

基础处理方式包括：

- 缓存预热；
- 延长合理的缓存时间；
- 随机过期；
- 本地缓存；
- 分散 Key；
- 控制单个接口的访问频率。

### 2. 大 Key

大 Key 是保存了大量数据的单个 Key，例如一个超大的 List、Hash 或很长的 String。

大 Key 可能带来：

- 占用过多内存；
- 读取和删除耗时较长；
- 网络传输量过大；
- 阻塞其他请求。

解决思路是按业务拆分数据，并控制单个集合的大小。不要为了减少 Key 数量，把所有数据都塞进一个大 Key。

## 七、常见错误

### 1. 只缓存存在的数据

如果不存在的数据永远不缓存，大量无效请求会反复访问数据库。可以对“不存在”设置较短的空值缓存。

### 2. 所有 Key 使用相同过期时间

批量加载数据时，如果所有 Key 都设置为同一个过期时间，可能在同一时刻集中失效。可以加入小范围随机值。

### 3. 把随机 TTL 当成完整防护

随机过期时间只能降低集中失效概率，不能解决：

- Redis 整体不可用；
- 热点 Key 被大量访问；
- 数据库本身查询过慢；
- 请求没有限流。

### 4. Redis 失败后无限回源数据库

如果 Redis 故障时所有请求都直接查询数据库，数据库可能很快被打满。需要结合超时、限流、降级和数据库容量处理。

### 5. 用永久缓存解决所有问题

永久缓存可能减少过期导致的未命中，但会带来：

- 数据长期不更新；
- 内存持续增长；
- 发布和更新时难以清理。

缓存时间应由业务数据的变化频率和一致性要求决定。

## 八、面试回答模板

### 题目：什么是缓存穿透？

> 缓存穿透是请求查询一个缓存中没有、数据库中也不存在的数据，导致每次请求都绕过缓存访问数据库。常见防护包括参数校验、缓存空值，以及在数据规模和风险允许时使用布隆过滤器。

### 题目：什么是缓存击穿？

> 缓存击穿通常指一个热点 Key 过期，很多请求同时发现缓存未命中并访问数据库。可以通过热点预热、随机过期、互斥重建、返回短时间旧值或本地缓存等方式降低影响。

### 题目：什么是缓存雪崩？

> 缓存雪崩通常指大量 Key 同时失效，或者 Redis 整体不可用，导致大量请求集中访问数据库。可以使用随机 TTL、分批过期、服务降级、限流、超时和多级缓存等方式防护。

### 题目：随机过期时间解决什么问题？

> 随机过期时间可以把原本同时失效的一批 Key 分散到不同时间，降低集中回源数据库的概率。但它不能解决 Redis 整体故障，也不能替代限流、降级和并发控制。
