# 第1课:单机、集群与分布式系统

前面的课程里，你已经写过这样的程序：一个 FastAPI 进程，连着一个 SQLite 文件（或者一个 MySQL），需要缓存或限流时再用一个 Redis。这一课要回答的问题是：**如果把这个程序从一台机器扩展到多台机器，会发生什么？**

很多"分布式"的坑，并不是多台机器本身造成的，而是**从一份状态变成多份状态、从一个进程变成多个进程**之后才出现的新问题。理解这些问题的来源，比记住术语重要得多。

这一课是概念课，重点是建立下面三个心智模型：

1. 单进程应用为什么活不久、扩展不动；
2. 网络调用和函数调用到底差在哪；
3. 为什么"部分失败"在分布式系统里是常态，而不是异常。

**学习目标：**

1. 能画出单进程应用的组件图，并指出每个组件的状态存放在哪里；
2. 能说出单点故障的含义，以及水平扩展、垂直扩展的区别；
3. 能用自己的话区分"集群"和"分布式系统"；
4. 能列出网络调用与函数调用的至少三个不同点；
5. 能解释为什么多实例之后，内存状态、文件写入和请求路由都会出问题；
6. 能说出"部分失败"的含义，并举例说明它如何导致重复执行。

## 1. 单进程应用的状态

你目前的 FastAPI 应用大致长这样：

```text
客户端（浏览器 / curl）
    |
    v
FastAPI 进程（127.0.0.1:8000）
    |           |
    |           +----> SQLite 文件（tasks.db）
    |
    +----------------> Redis（可选：缓存 / 限流）
```

在"单进程"的视角下，这个应用的所有状态都在一个地方：

- **进程内内存**：全局变量、缓存、登录用户字典——进程活着就在，进程重启就没了；
- **SQLite 文件**：持久数据——但只有一个进程能方便地写它；
- **Redis**：独立进程的共享内存——已经是一份"多个进程可以访问"的状态了。

这种形态的特点非常朴素：

```text
一个进程处理所有请求
    -> 内存状态天然只有一份
    -> 数据库只有一个写者（基本）
    -> API 调用就是函数调用，要么成功要么抛异常
    -> 部署 = 停掉进程 -> 换新代码 -> 启动
```

它完全能工作，而且很容易理解。**但"能工作"和"扛得住生产流量"是两回事**，接下来看它的问题。

## 2. 单点故障与扩展极限

### 2.1 单点故障

如果这个进程崩溃了、被 OOM 杀了、或者被运维误停，会发生什么？

```text
FastAPI 进程退出
    -> 端口 8000 没有人监听
    -> 所有请求失败（Connection Refused）
    -> 在恢复之前，整个服务不可用
```

更麻烦的是**升级**：任何一次代码发布，都要停掉进程。停掉的这几秒到几分钟里，用户一直在报错。单实例应用不存在"灰度发布"，只有"全量不可用"。

这就是**单点故障（Single Point of Failure）**：整个系统中，只要这一个点挂了，系统就不可用。

### 2.2 处理不过来

单核 CPU 每秒能处理的请求数有上限。假设一个模型调用要 2 秒，而你每秒钟收到 10 个这样的请求，单进程的请求队列会不断变长，最终：

```text
请求积压 -> 内存升高 -> 响应变慢 -> 更多请求堆积 -> 进程崩溃（级联）
```

程序本身没有错，是**单机的处理能力到了天花板**。

### 2.3 两条出路：垂直扩展与水平扩展

| 方案 | 做法 | 优点 | 局限 |
| --- | --- | --- | --- |
| 垂直扩展 | 换更强的机器：更多 CPU、更大内存 | 不需要改代码 | 有物理上限；昂贵；强机器也要重启维护 |
| 水平扩展 | 多加几台普通机器，组成多实例 | 理论可无限加；机器便宜；可以逐个升级 | **引入了一堆新问题**（本课剩余内容） |

垂直扩展是"把一个人的工位变大"，水平扩展是"多招几个人一起干活"。分布式系统关心的主要是后者：**人多了以后，怎么协调？**

## 3. 多实例的三类新问题

假设我们把 FastAPI 启动两个实例，前面放一个负载均衡器（Nginx、或云厂商的 LB）负责把请求轮流分给两个实例：

```text
客户端
    |
    v
负载均衡器
    |            |
    v            v
实例 A      实例 B
(8001)     (8002)
    \         /
     \       /
      v     v
    共享数据库 + Redis
```

架构图看起来很简单，但下面三个问题立刻出现。

### 3.1 问题一：内存状态不再共享

假设你在实例 A 的内存里保存了一个 `current_user` 字典，登录后用户能看到自己的信息：

```python
# 注意：这是演示，真实项目不要这么做
current_user = {}

@app.post("/login")
def login(name: str):
    current_user["name"] = name
    return "ok"

@app.get("/me")
def me():
    return {"user": current_user.get("name")}
```

单实例时，登录后 `/me` 必然能读到。**两个实例后，请求可能这样走：**

```text
POST /login  -> 负载均衡器 -> 实例 A（current_user 被写入 A 的内存）
GET  /me     -> 负载均衡器 -> 实例 B（B 的内存里什么都没有！）
```

同样的代码，行为却时好时坏，而且**很难复现**——这就是"状态放错地方"的典型症状。结论：

> 多实例下，进程内内存只属于单个实例。**要跨实例共享的状态，必须放到所有实例都能访问的地方**（数据库、Redis、共享文件系统），或者用 Session 粘性一类的手段——但后者只是把问题推迟。

### 3.2 问题二：同一个文件的并发写

如果数据库还是单文件 SQLite，两个实例同时写：

```text
实例 A: BEGIN; INSERT INTO tasks ...;
实例 B: BEGIN; INSERT INTO tasks ...;   -- 文件锁冲突 / database is locked
```

SQLite 的定位是单机嵌入式数据库，多个进程同时写会频繁遇到锁等待（还记得 `database-sqlite` 课程里"使用边界"那一课吗？这就是它被归类为"教学和单机工具"的原因）。多实例场景下，通常要换成**服务端数据库（MySQL / PostgreSQL）**，由它来管理并发写。这个问题不是"SQLite 不好"，而是**"单机文件"和"多进程共享"本来就互斥**——文件只能有一个写者，数据库服务可以有很多客户端。

### 3.3 问题三：请求到底发给谁

负载均衡器每来一个请求要决定交给谁，这会带来两个衍生问题：

- **实例间负载不均**：有的请求快有的慢，简单轮询可能导致某个实例忙死、另一个闲死；
- **某实例故障时的处理**：负载均衡器把请求发给 8002，但实例 B 已经挂了——请求是重试、返回错误，还是等实例 B 恢复？

第二个问题就是下一节的引子：**在多个节点组成的系统里，你永远无法确定自己面对的是一个"正常的节点"还是"刚挂掉还没来得及通知你的节点"。**

## 4. 集群与分布式系统

这两个词经常被混用，但场景不同：

### 4.1 集群（Cluster）

**同一角色的多个实例共同对外提供服务。** 我们上面的两个 FastAPI 实例就是一个集群：

```text
多台 FastAPI 实例（同一份代码）
    -> 共享一个数据库
    -> 外面看起来是"一个服务"
```

核心思路是**分身**：一个应用不够用，就复制出多个一模一样的。程序员脑中的模型还是"一个应用"，只是它被部署了多次。

### 4.2 分布式系统（Distributed System）

**多个不同角色的服务协作完成一件事。** 例如你的 Agent 系统：

```text
FastAPI 服务  ->  模型服务（LLM）  ->  Embedding 服务  ->  向量数据库  ->  Redis 缓存
```

每一个服务职责不同，组合起来才是一个完整应用。核心思路是**分工**：把一件事拆成多个部分，分给不同的服务。

| 对比 | 集群 | 分布式系统 |
| --- | --- | --- |
| 节点关系 | 同角色、同代码 | 不同角色、不同职责 |
| 解决的问题 | 一台机器不够用（容量） | 一件事需要多种能力（拆分） |
| 典型例子 | 多个 FastAPI 实例 | FastAPI + 模型服务 + 向量库 |
| 常见组合 | 集群内部还可以是分布的 | 分布式系统的每个服务往往也开多实例（形成集群） |

**实际生产中两者几乎总是同时出现**，不需要纠结"我这算不算分布式"，而要能说清楚：**"我的系统里有几个节点、各自什么职责、状态存在哪、谁挂了对谁有影响"**。

## 5. 网络调用与函数调用

这一节是整门课最重要的基础。所有后面的超时、重试、熔断、幂等，都源于"网络调用和函数调用不一样"。

### 5.1 函数调用

```python
result = calculate_total(order)
```

发生在**同一个进程内部**：调用时参数入栈，函数执行完把结果放回调用方。这个调用有以下性质：

- **要么成功返回，要么抛异常**——没有第三种情况；
- 没有网络延迟，耗时基本可预测；
- 调用方和被调用方**必然同时活着**（它们本来就是同一个进程）；
- 不会"重复执行"——同一行代码最多执行一次。

### 5.2 网络调用

```text
客户端  --请求-->  网络  -->  服务端
   |                                |
   +<------ 超时 / 错误 / 响应 -------+
```

假设客户端向"模型服务"发一个 HTTP 请求，可能的结果比函数调用多得多：

| 现象 | 说明 |
| --- | --- |
| 正常响应 | 服务端处理完，结果在超时前返回 |
| 连接超时 | 服务端根本没响应（挂了 / 网络不通） |
| 读取超时 | 连上了但一直没有数据（服务端卡住） |
| 响应丢失 | 服务端处理完了，响应在网络上丢了（客户端以为失败） |
| 客户端超时重发 | 客户端以为失败、重试，但第一次其实已经成功了 |

注意最后两种：**作为调用方，你永远分不清"失败了"和"成功了但没收到结果"**。这是分布式系统里最反直觉、也最重要的事实。

### 5.3 一个类比

函数调用像在办公室开会：你一说话，对面的人必然听见，因为你们在同一间屋子里（同一个进程），他没有第二个选择。

网络调用像打电话：你拨号，对方可能关机（连接失败）、可能在通话中（占有率满）、可能听到了但你手机没信号（响应丢失）。**打电话时你能确定的只是"我没听到回答"，而不是"对方没听到我"。**

### 5.4 推论：从"要么成功要么失败"到"三种结果"

单机程序里，一次操作是二元的结果：

```text
成功
失败（抛异常）—— 可以确定地认为没有发生任何副作用
```

网络世界里，一次调用是三元的结果：

```text
确认成功    —— 副作用发生了
确认失败    —— 副作用大概率没发生（但小概率发生了，不保证）
结果未知    —— 超时了！副作用可能发生、可能没有（最危险）
```

**"结果未知"是分布式系统独有的状态。** 它意味着：为了确定性，你必须在设计上考虑"同一个操作可能被执行了两次"（幂等、去重、唯一约束），这将在第 5、7 课展开。这一课只需要记住：

> 只要跨了进程，任何一次调用都不能假设"要么成功要么没发生"。**可能成功、可能失败、可能成功但你没收到。**

## 6. 部分失败：分布式系统的常态

把上面的结论放大到整个系统。单机系统出故障时，通常是整体性的：

```text
单机：进程崩溃 = 整个应用不可用（"要么全有，要么全无"）
```

多节点系统完全相反——**故障往往是局部的**：

```text
实例 A 正常，实例 B 崩溃
数据库正常，Redis 宕机
Agent A 的模型调用超时，Agent B 的调用成功
```

这就是**部分失败（Partial Failure）**：系统的一部分挂了，另一部分还在跑。它不是罕见事故，而是**常态**。

### 6.1 一个具体的例子

看一个最常见的悲剧顺序：

```text
1. 用户点"提交任务"
2. 请求被负载均衡器发给实例 A
3. 实例 A 写入数据库成功（任务已创建）
4. 实例 A 在返回成功响应前崩溃了
5. 客户端没收到响应，超时后重试
6. 重试请求被发给实例 B
7. 实例 B 再次写入数据库 —— 任务创建了两次！
```

**每个环节都是"正确"的，但组合起来就是错的。** 问题出在：第 4-5 步之间，系统处于"结果未知"状态——数据库里已经有任务了，但客户端（和实例 B）都不知道。

### 6.2 部分失败带来的三个设计原则

从上面的例子，可以概括出分布式设计的三条铁律（本课程后续所有内容都在围着它们转）：

```text
1. 一切操作都要假定"可能被重复执行" -> 幂等（第 5 课、第 7 课）
2. 一切调用都要有超时     -> 不能无限等（第 4 课）
3. 一切失败都要有明确状态  -> 状态机 + 日志 + 补偿（第 7 课）
```

注意：**这一课不要求你会实现它们**，只要求你能从"部分失败"这个事实出发，解释为什么它们存在。

## 7. 运行课程代码

这一节用一个最小实验，把 3.1 节的"内存状态不共享"变成你亲眼看到的现象。需要 `fastapi` 和 `uvicorn`（前面课程已装过）。

### 7.1 启动两个实例

把下面的代码保存为 `two_instances.py`（模拟两个实例）：

```python
from fastapi import FastAPI

app = FastAPI()

# 两个实例分别改成 8001 / 8002（只用于在返回里区分是哪个实例）
PORT = 8001

# 注意：这就是"进程内存状态"，每个进程各有一份
counter = {"value": 0}


@app.post("/hit")
def hit() -> dict:
    counter["value"] += 1
    return {"instance_port": PORT, "counter": counter["value"]}


@app.get("/counter")
def get_counter() -> dict:
    return {"counter": counter["value"]}
```

分别用不同端口启动两个实例（两个终端各执行一条）：

```bash
uvicorn two_instances:app --port 8001
uvicorn two_instances:app --port 8002
```

然后连续请求：

```bash
curl -X POST http://127.0.0.1:8001/hit
curl -X POST http://127.0.0.1:8002/hit
curl -X POST http://127.0.0.1:8001/hit
```

观察输出：

```text
第一次（8001）：counter = 1
第二次（8002）：counter = 1      ← 不是 2！两个进程各有一份 counter
第三次（8001）：counter = 2
```

**结论：两个进程各自维护自己的 `counter`，互不可见。** 这在单实例时不可能出现。如果这个 `counter` 是"用户当天任务数"这类业务状态，就已经错了——你实际需要的是让两个实例共享 **Redis 的 `INCR`**（见 Redis 第 9 课）。

> 示例说明：这里没有真实网络故障，`counter` 不同步是**真实的进程行为**，不涉及负载均衡器——我们只是手动分别访问两个端口，效果等同。

### 7.2 模拟一次"部分失败"

启动一个实例（比如 8001），向它发起一个会持续几秒的请求，然后把进程**手动杀掉**（`Ctrl+C`，或任务管理器结束进程）。再请求时会得到 `Connection Refused`：

```text
curl: (7) Failed to connect to 127.0.0.1 port 8001: Connection refused
```

这时如果还有 8002 在跑，**8002 依然正常服务**——这就是部分失败：一部分节点挂了，另一部分照常工作。而如果整个系统只有一个实例（第 2 节的单点故障），就是全体不可用。

> 示例说明：这里的"故障"是**模拟**的（手动杀进程），但 `Connection Refused`、端口无人监听是**真实的操作系统行为**。

## 10. 面试高频考点

- 单点故障：单实例部署的风险，以及为什么生产环境通常要开多实例。
- 水平扩展 vs 垂直扩展：各自的取舍；"多实例后状态放哪"（共享存储 / 会话粘性 / 无状态化）。
- 集群 vs 分布式：能举例（多个相同 FastAPI 实例 vs FastAPI + 模型服务 + 向量库）。
- 网络调用与函数调用的区别：**"调用方无法区分失败与成功但没收到响应"**——这是超时、重试、幂等等一切分布式话题的出发点。
- 部分失败：能举"写库成功、响应丢失、重试导致重复"的时序例子。
- 常见追问："多实例后为什么用户登录会掉？"（内存会话不共享）或"计数器为什么会不准确？"（各实例独立状态）。

## 11. 过关清单

如果现在能回答"多实例后会出现哪三类新问题"（内存状态不共享、共享存储的并发写、请求路由与失败处理），并且能用自己的话解释"结果未知"为什么导出幂等和超时，就可以进入第 2 课：CAP、BASE 与最终一致性。
