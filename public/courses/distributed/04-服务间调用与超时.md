# 第4课:服务间调用与超时

第 1 课你已经看到，网络调用和函数调用最大的不同是：网络调用有"结果未知"这种第三种状态。这一课讲的是这个结论的第一个工程落地——**给每一次服务间调用设超时**。没有超时的网络请求，会让一个慢下游拖垮整个服务。

这一课是机制课，重点是建立两个心智模型：

1. 超时不是一个数字，而是三种：连接超时、读取超时、整体超时；
2. 多级调用链上，每一跳都要有超时，且要受"超时预算"约束。

**学习目标：**

1. 能区分同步调用和异步调用，说明各自适用场景；
2. 能描述一条服务调用链，指出每一跳的耗时；
3. 能区分连接超时、读取超时、整体请求超时；
4. 能解释超时预算如何在多级调用中分配；
5. 能解释为什么没有超时的网络请求会拖垮线程或协程；
6. 能说明超时后的返回、取消和资源释放；
7. 会配置 HTTP 客户端的连接超时和读取超时。

## 1. 同步调用与异步调用

先分清两种调用方式，这是后面所有超时讨论的前提。

### 1.1 同步调用

调用方发出请求后，**一直等，直到拿到响应才继续往下走**：

```python
result = client.get("http://下游/slow")   # 阻塞在这里，直到响应返回
print(result)                              # 这行要等上面拿到结果才执行
```

调用方在这段时间里**什么事也干不了**，被"卡住"了。这就是**同步调用**。

### 1.2 异步调用

调用方发出请求后，**不傻等，先去干别的，响应到了再回来处理**：

```python
async def main():
    task = asyncio.create_task(client.get("http://下游/slow"))  # 发起请求，不等待
    # 这里可以去处理别的请求、做别的计算
    result = await task   # 到这里才真正等待结果
```

调用方在等待期间可以做别的事，这就是**异步调用**（async/await，见 Python 第 8 课）。

### 1.3 一张对比表

| 维度 | 同步调用 | 异步调用 |
| --- | --- | --- |
| 等待期间 | 阻塞，干不了别的 | 可以干别的 |
| 实现 | 简单（普通函数） | 复杂（async/await） |
| 适用 | 简单场景、调用少 | 高并发、大量 IO 等待 |

> 注意一个易混点：这里的"异步调用"指的是**不阻塞等待**，和第 7 课要讲的"异步任务队列"（把任务丢给 Worker 后台执行）不是一回事。本课先只讲"一次调用的等待方式"。

## 2. 服务调用链

一次用户请求，很少只调一个服务，往往是**一跳接一跳**：

```text
用户请求
    -> API 服务（FastAPI）
        -> 业务服务（校验、查配置）
            -> 模型服务（LLM，可能 2 秒）
            -> 向量库（检索，可能 0.3 秒）
        -> 数据库（查询，可能 0.1 秒）
```

这就是**服务调用链**。它的两个关键事实：

- **串行时，总耗时 = 每一跳耗时之和**；
- **任何一跳变慢，整条链都慢**。

```text
API(0.1s) + 业务(0.2s) + 模型(2s) + 向量库(0.3s) + 数据库(0.1s)
    = 总耗时约 2.7 秒
```

如果模型服务从 2 秒变成 10 秒，整条链就从 2.7 秒变成 10.7 秒——**下游一慢，上游全慢**。这就是为什么每一跳都要有超时：不能让某个慢下游无限拖住整条链。

## 3. 三种超时

"设个超时"听起来简单，实际有三种，它们卡的是**不同阶段**。

### 3.1 连接超时（Connect Timeout）

**建立 TCP 连接的最大等待时间。** 卡在"能不能连上"：

```text
客户端 --TCP 三次握手--> 服务端
        ↑ 这一步没完成，就是连接超时
```

典型原因：对方没监听这个端口、网络不通、防火墙拦截。

### 3.2 读取超时（Read Timeout）

**连接建立后，等待响应数据的最大时间。** 卡在"连上了，但对方一直不给数据"：

```text
客户端 --请求已发出--> 服务端
        ↑ 连接是通的，但对方迟迟不响应，就是读取超时
```

典型原因：对方处理太慢、对方卡死、响应数据在网络里丢了。

### 3.3 整体请求超时（Overall Timeout）

**整个请求从发起到完成的总上限。** 兜住连接、读取之外的所有时间：

```text
整体超时 = 连接 + 发送 + 读取 + 重定向 + TLS 握手 + ... 的总和上限
```

即使连接和读取各自没超，但中间有重定向、多次重试，总时间也可能失控，所以需要整体上限。

### 3.4 一张对比表（面试必考）

| 超时类型 | 卡在哪一步 | 典型原因 |
| --- | --- | --- |
| 连接超时 | 建立连接 | 对方没监听、网络不通 |
| 读取超时 | 等响应数据 | 对方处理慢、卡死 |
| 整体超时 | 全流程总时间 | 重定向、多次重试累积 |

> 一个高频追问："对方没启动"和"对方启动了但很慢"，分别对应哪种超时？——前者是连接超时（连不上），后者是读取超时（连上了但没数据）。

## 4. 超时预算

多级调用链上，不能每一跳都随便设超时。要有一个**超时预算（Timeout Budget）**：把整体预算分配到每一跳。

### 4.1 为什么要预算

```text
API 对外承诺 3 秒内返回
    -> 它调下游 A、下游 B
    -> 如果 A 设 3 秒、B 也设 3 秒
    -> 最坏情况 A + B = 6 秒，早就超了对外承诺
```

没有预算，上游的"整体超时"承诺就是空的。

### 4.2 怎么分配

```text
API 整体超时 3 秒
    ├─ 下游 A：1.0 秒
    ├─ 下游 B：1.5 秒
    └─ 留 0.5 秒余量（自己处理、序列化、返回）
```

原则：**每一跳的超时之和 + 余量 ≤ 整体超时**。谁更重要、更慢，就多给谁一点。

## 5. 没有超时的后果

如果没有超时，会发生什么？答案是**资源被无限占用，最终拖垮整个服务**。

### 5.1 同步场景：线程被占满

```text
下游服务挂了（不响应）
    -> 上游每个请求都在傻等下游
    -> 线程被占用，不释放
    -> 新请求进来，没有空闲线程可用
    -> 线程池耗尽，整个上游服务不可用
```

### 5.2 异步场景：协程和连接被占满

```text
下游服务挂了
    -> 每个协程都在 await 下游，占用一个连接槽位
    -> 连接池耗尽
    -> 新请求拿不到连接，也卡住
```

**无论是线程还是协程，本质都是：没有超时 = 资源只进不出 = 最终耗尽。** 一个下游挂了，会通过"无超时的调用"把上游也拖死——这就是第 6 课要讲的级联失败的前奏。

## 6. 超时后的处理

超时之后，不是"报个错"就完了。要做三件事：

### 6.1 返回明确结果

超时后要**返回一个明确的错误**（如 504 Gateway Timeout，或业务错误码），而不是让请求继续挂起：

```python
except httpx.ReadTimeout:
    return {"error": "下游读取超时"}
```

### 6.2 取消底层请求、释放资源

超时后要**取消还在进行的底层请求，把连接还回连接池**，避免连接泄漏：

```text
httpx 等现代客户端在超时时会自动关闭底层连接
    -> 显式使用 with 上下文 / close()，确保资源释放
```

### 6.3 记住：超时 ≠ 失败

这是第 1 课"结果未知"的延续。**超时只代表"我没拿到结果"，不代表"下游没处理"。** 下游可能已经处理成功了：

```text
你超时了，以为失败，于是重试
    -> 但下游第一次其实已经成功了
    -> 重试导致重复执行（重复下单、重复扣款）
```

所以：**超时之后如果要重试，必须配合幂等（第 5 课展开）**。这一课先记住这个提醒。

## 7. 运行课程代码

这一节用一个最小实验，亲眼看到"读取超时"和"连接超时"的区别。需要 `httpx`（fastapi 课程已装过）；慢服务用 Python 标准库 `http.server` 起，不额外装东西。

把下面的代码保存为 `code/distributed/lesson04_timeout.py`：

```python
# code/distributed/lesson04_timeout.py
# 演示服务间调用的两种超时：读取超时 vs 连接超时。
#  # 后是注释，实际执行时不输入。

import threading
import time
import httpx
from http.server import BaseHTTPRequestHandler, HTTPServer


class SlowHandler(BaseHTTPRequestHandler):
    """一个本地慢服务：收到请求后 sleep 5 秒才响应。"""

    def do_GET(self):
        time.sleep(5)  # 模拟慢下游：处理要 5 秒
        body = b'{"status": "ok"}'
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):
        pass  # 关掉默认访问日志，让输出干净


def start_slow_server(port=8001):
    """后台起一个慢服务，返回 server 对象（用完 shutdown）。"""
    server = HTTPServer(("127.0.0.1", port), SlowHandler)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    return server


def call(url, timeout):
    """用 httpx 调一个 URL，带超时配置，把异常翻译成可读结果。"""
    try:
        with httpx.Client(timeout=timeout) as client:
            resp = client.get(url)
        return {"result": resp.json()}
    except httpx.ReadTimeout:
        return {"error": "读取超时：连接通了，但一直没等到响应"}
    except httpx.ConnectTimeout:
        return {"error": "连接超时：根本连不上（对方没监听 / 网络不通）"}


if __name__ == "__main__":
    server = start_slow_server()
    print("已启动慢服务 http://127.0.0.1:8001（每个请求 sleep 5 秒）\n")

    # 实验一：读取超时（连得上，但下游 5 秒才回，读超时只等 1 秒）
    print("实验一：调用慢服务，读取超时设为 1 秒")
    t0 = time.time()
    print("  ", call("http://127.0.0.1:8001/slow",
                     httpx.Timeout(connect=1.0, read=1.0)))
    print(f"   实际耗时 {time.time() - t0:.1f} 秒（没傻等 5 秒）\n")

    # 实验二：连接超时（调一个没人监听的端口 9999）
    print("实验二：调用一个没人监听的端口 9999，连接超时设为 1 秒")
    t0 = time.time()
    print("  ", call("http://127.0.0.1:9999/x",
                     httpx.Timeout(connect=1.0, read=1.0)))
    print(f"   实际耗时 {time.time() - t0:.1f} 秒\n")

    server.shutdown()
```

运行：

```bash
python code/distributed/lesson04_timeout.py
```

观察输出：

```text
已启动慢服务 http://127.0.0.1:8001（每个请求 sleep 5 秒）

实验一：调用慢服务，读取超时设为 1 秒
   {'error': '读取超时：连接通了，但一直没等到响应'}
   实际耗时 1.0 秒（没傻等 5 秒）

实验二：调用一个没人监听的端口 9999，连接超时设为 1 秒
   {'error': '连接超时：根本连不上（对方没监听 / 网络不通）'}
   实际耗时 1.0 秒
```

**结论：实验一下游 5 秒才响应，上游 1 秒就读取超时返回，没有傻等；实验二端口没监听，连接超时立即返回。** 这就是"连接超时"和"读取超时"卡在不同阶段的直接体现。

> 示例说明：慢服务是我们用 `time.sleep(5)` **模拟**的，但 `ReadTimeout` / `ConnectTimeout` 是 httpx 的**真实异常**，"1 秒就返回"是真实的超时行为。真实系统里，下游变慢对应实验一，下游宕机对应实验二。

## 10. 面试高频考点

- **三种超时**：连接超时（连不上）、读取超时（连上了没数据）、整体超时（全流程上限），能说清各自卡在哪、对应什么故障。
- **超时预算**：多级调用链每一跳都要设超时，且之和 + 余量 ≤ 整体超时。
- **没有超时的后果**：线程/协程/连接被无限占用 → 资源耗尽 → 上游被下游拖死。
- **超时后的处理**：返回明确错误、取消底层请求释放资源、记住"超时 ≠ 失败"（重试要幂等）。
- **常见追问**：
  - "读取超时和连接超时怎么区分？"（卡在握手 vs 卡在等数据。）
  - "你项目里模型调用设了多少超时？为什么？"（结合模型耗时给一个具体值，说明是读超时为主。）
  - "下游挂了，你的服务会怎样？"（无超时会拖垮；有超时则快速失败，见下一课的熔断。）
