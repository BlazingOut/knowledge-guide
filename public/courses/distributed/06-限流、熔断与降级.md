# 第6课:限流、熔断与降级

第 5 课的重试，解决的是"偶发失败再试一次"。但当下游真的变慢、甚至挂掉时，重试只会火上浇油。这一课讲三种主动"限制影响范围"的手段——**限流、熔断、降级**。它们是分布式后端面试里最高频的一组对比题。

这一课是机制课，重点是建立三个心智模型：

1. 一个慢下游会像多米诺骨牌一样，逐级拖垮整条调用链（级联失败）；
2. 限流防的是"过载"，熔断防的是"连续失败拖垮自己"，降级保的是"还有兜底可用"；
3. 三者常组合使用，但职责不同，不能混为一谈。

**学习目标：**

1. 能解释级联失败和雪崩效应是怎么发生的；
2. 能解释限流保护什么，区分客户端限流和服务端限流、并发数限制和速率限制；
3. 能描述熔断器的关闭、打开、半开三种状态及转换条件；
4. 能解释降级的常见形式（降级数据、默认结果、快速失败）；
5. 能说清限流、熔断、降级三者的区别；
6. 能说明 429、503 状态码的使用场景。

## 1. 级联失败与雪崩

先理解这三样东西要防的"敌人"是什么。

### 1.1 级联失败（Cascading Failure）

```text
下游模型服务变慢（2 秒 -> 10 秒）
    -> 上游 API 调模型，线程被占满
    -> API 自己也开始变慢
    -> 再上层的网关、前端，也被 API 拖慢
    -> 一个服务的故障，像多米诺骨牌一样逐级传染
```

**级联失败：一个服务的故障，通过调用链逐级传染，最终拖垮整个系统。**

### 1.2 雪崩效应（Avalanche）

当级联失败蔓延到一定程度，就是**雪崩**：

```text
缓存雪崩：大量缓存同时失效，请求瞬间全打到数据库，数据库被打挂
服务雪崩：一个下游挂了，所有依赖它的上游也接连挂掉
```

雪崩是级联失败的最终形态——**小故障被逐级放大，变成系统性的崩溃**。

### 1.3 为什么要"在源头掐断"

既然故障会传染，那么**唯一的办法是在传染之前把它掐断**：

```text
下游一慢 -> 立刻停止/限制对它的调用（熔断）
         -> 或者限制进入的请求量（限流）
         -> 或者返回兜底，不让它传染（降级）
```

这就是限流、熔断、降级存在的意义。

## 2. 限流

**限流（Rate Limiting）**：控制请求进来的速率，防止系统被过量的请求打垮。

### 2.1 限流保护什么

```text
限流保护的是"被调用方"
    -> 请求太多，处理不过来，就先拒绝一部分
    -> 保证剩下的请求能正常处理
    -> 宁可拒绝，不可一起死
```

### 2.2 客户端限流 vs 服务端限流

| 位置 | 谁来做 | 保护谁 | 例子 |
| --- | --- | --- | --- |
| 客户端限流 | 调用方自己控制发请求的速率 | 保护下游 | 调用方限制每秒最多发 100 个请求 |
| 服务端限流 | 被调用方控制接收请求的速率 | 保护自己 | API 网关限制每个用户每秒 10 个请求 |

### 2.3 并发数限制 vs 请求速率限制

这是两种不同维度的"限制"：

```text
并发数限制：同一时刻最多同时处理 N 个请求（看"同时"）
请求速率限制：每秒最多处理 N 个请求（看"单位时间"）
```

- 并发数限制：像餐厅只有 10 张桌子，坐满就排队/拒绝；
- 速率限制：像闸机每秒放 5 个人，不管当前有多少人在等。

具体算法（令牌桶、滑动窗口、漏桶）在 Redis 第 9 课展开，本课只要求能区分这两个维度。

### 2.4 触发后的表现

限流触发时，通常返回 **429 Too Many Requests**：

```text
客户端请求太多
    -> 服务端返回 429
    -> 客户端收到 429，知道"我被限流了"，退避后再试
```

## 3. 熔断

**熔断（Circuit Breaking）**：当下游连续失败时，暂时停止调用它，快速失败。

### 3.1 类比：电路保险丝

熔断器（Circuit Breaker）的名字来自电路：**电流过大时，保险丝熔断，切断电路，保护电器**。软件里的熔断器同理：

```text
下游连续失败 -> 熔断器打开 -> 不再调用下游 -> 保护自己不被拖垮
```

### 3.2 三种状态

```text
        连续失败 N 次
 关闭(closed) ──────────> 打开(open)
    ↑                        │
    │                    过了 open_timeout
    │                        │
    └─────── 试探成功 ─── 半开(half_open)
             试探失败则回到 open
```

| 状态 | 含义 | 行为 |
| --- | --- | --- |
| 关闭（closed） | 正常状态 | 正常调用下游 |
| 打开（open） | 熔断中 | 不再调下游，直接快速失败 |
| 半开（half_open） | 试探 | 放一个请求试探下游是否恢复 |

### 3.3 状态转换逻辑

```text
1. 关闭状态：连续失败 N 次 -> 打开
2. 打开状态：过了一段时间（open_timeout）-> 半开
3. 半开状态：放一个请求试探
    -> 成功：下游恢复了，回到关闭
    -> 失败：下游还没好，回到打开（重新计时）
```

**关键：半开只放一个请求**，用最小的代价试探下游是否恢复，避免"下游刚好又被打爆"。

### 3.4 触发后的表现

熔断打开时，直接快速失败，通常返回 **503 Service Unavailable** 或一个降级响应。

## 4. 降级

**降级（Degradation）**：核心功能保不住时，返回兜底结果，保证服务"还能用"。

### 4.1 三种常见形式

```text
1. 降级数据：返回缓存里的旧数据，而不是实时数据
2. 默认结果：返回一个安全的默认值（如推荐系统返回热门榜单）
3. 快速失败：直接返回错误，不再调下游（配合熔断）
```

### 4.2 降级和熔断的关系

熔断和降级经常一起出现：

```text
下游挂了 -> 熔断打开 -> 不再调下游 -> 返回降级结果
```

**熔断决定"还调不调下游"，降级决定"不调了返回什么"。** 两者配合，才能既保护自己、又不让用户看到空白页。

## 5. 三者的区别

这是面试必考对比题。三者的职责不同：

| 手段 | 解决什么问题 | 保护谁 | 触发时机 | 典型表现 |
| --- | --- | --- | --- | --- |
| 限流 | 请求太多，处理不过来 | 被调用方 | 请求量超阈值 | 429 拒绝一部分 |
| 熔断 | 下游连续失败，别再调了 | 调用方自己 | 连续失败 N 次 | 503 / 快速失败 |
| 降级 | 保不住核心功能，给兜底 | 用户体验 | 依赖不可用 | 返回默认/缓存结果 |

一句话记忆：

```text
限流：防过载（进太多了，拒绝一些）
熔断：防拖垮（下游坏了，先别调）
降级：保可用（核心没了，给兜底）
```

## 6. 运行课程代码

这一节用一个简化版熔断器，观察"连续失败 → 打开 → 半开 → 关闭"的完整状态转换，以及打开期间的降级兜底。只需要 Python 标准库。

把下面的代码保存为 `code/distributed/lesson06_circuit_breaker.py`：

```python
# code/distributed/lesson06_circuit_breaker.py
# 演示熔断器的三种状态：closed（关闭）/ open（打开）/ half_open（半开）。
#  # 后是注释，实际执行时不输入。

import time


class CircuitBreaker:
    """简化版熔断器。

    状态转换：
        closed  --连续失败 failure_threshold 次--> open
        open    --过了 open_timeout 秒--> half_open
        half_open --试探成功--> closed
        half_open --试探失败--> open（重新计时）
    """

    def __init__(self, failure_threshold=3, open_timeout=2.0):
        self.failure_threshold = failure_threshold  # 连续失败 3 次就打开
        self.open_timeout = open_timeout            # 打开 2 秒后半开
        self.failure_count = 0
        self.state = "closed"
        self.opened_at = 0.0

    def call(self, real_call, fallback):
        """执行一次调用。real_call 是真实调用，fallback 是降级兜底。"""
        # 打开且还没到半开时间：快速失败，返回降级
        if self.state == "open" and time.time() - self.opened_at < self.open_timeout:
            print(f"    [状态=open] 快速失败，返回降级兜底")
            return fallback

        # 打开且到了半开时间：转半开，放一个请求试探
        if self.state == "open":
            self.state = "half_open"
            print(f"    [状态 open -> half_open] 放一个请求试探")

        try:
            result = real_call()
        except Exception:
            result = None  # 下游调用失败

        if result is None:
            self.failure_count += 1
            if self.state == "half_open":
                self.state = "open"
                self.opened_at = time.time()
                print(f"    [试探失败] 重新打开熔断")
            elif self.failure_count >= self.failure_threshold:
                self.state = "open"
                self.opened_at = time.time()
                print(f"    [连续失败 {self.failure_count} 次] 打开熔断")
            return fallback
        else:
            if self.state == "half_open":
                self.state = "closed"
                print(f"    [试探成功] 关闭熔断，恢复正常")
            self.failure_count = 0
            return result


# 一个"前 3 次失败、之后恢复"的下游
call_count = {"n": 0}


def downstream():
    """模拟下游：前 3 次抛异常，之后恢复正常。"""
    call_count["n"] += 1
    if call_count["n"] <= 3:
        raise RuntimeError("下游挂了")
    return {"data": "正常数据"}


if __name__ == "__main__":
    cb = CircuitBreaker(failure_threshold=3, open_timeout=2.0)
    fallback = {"data": "降级数据（默认结果）"}

    print("连续调用下游，观察熔断器状态：")
    for i in range(1, 6):
        print(f"  第 {i} 次调用：")
        result = cb.call(downstream, fallback)
        print(f"    -> 返回 {result}")
        time.sleep(0.3)

    print("\n等待熔断打开 2 秒后，再调用（进入半开试探）：")
    time.sleep(2.0)
    result = cb.call(downstream, fallback)  # 此时下游已恢复，试探成功
    print(f"  -> 返回 {result}")
```

运行：

```bash
python code/distributed/lesson06_circuit_breaker.py
```

观察输出（关键部分）：

```text
连续调用下游，观察熔断器状态：
  第 1 次调用：
    -> 返回 {'data': '降级数据（默认结果）'}
  第 2 次调用：
    -> 返回 {'data': '降级数据（默认结果）'}
  第 3 次调用：
    [连续失败 3 次] 打开熔断
    -> 返回 {'data': '降级数据（默认结果）'}
  第 4 次调用：
    [状态=open] 快速失败，返回降级兜底
    -> 返回 {'data': '降级数据（默认结果）'}
  第 5 次调用：
    [状态=open] 快速失败，返回降级兜底
    -> 返回 {'data': '降级数据（默认结果）'}

等待熔断打开 2 秒后，再调用（进入半开试探）：
  [状态 open -> half_open] 放一个请求试探
  [试探成功] 关闭熔断，恢复正常
  -> 返回 {'data': '正常数据'}
```

**结论：连续失败 3 次后熔断打开，后续调用不再真正调下游、直接返回降级兜底；过了 2 秒进入半开，放一个请求试探，下游恢复后关闭熔断、回到正常。** 这就是熔断器"保护自己不被连续失败拖垮"的完整机制。

> 示例说明：下游"前 3 次失败"是**模拟**的，但"打开后快速失败不调下游""半开只放一个请求试探""试探成功关闭"是真实的熔断逻辑。真实框架（如 resilience4j、polly、hystrix）的状态机就是这个模型。

## 9. 面试高频考点

- **级联失败 / 雪崩**：能描述"一个慢下游如何逐级拖垮整条链"，以及为什么要在源头掐断。
- **限流**：并发数限制 vs 速率限制；客户端 vs 服务端限流。
- **熔断器三态**：关闭 / 打开 / 半开，能画状态转换图，能说清"半开为什么只放一个请求"。
- **降级**：降级数据 / 默认结果 / 快速失败，能说清"熔断决定调不调、降级决定返回什么"。
- **三者对比**：限流防过载、熔断防拖垮、降级保可用。
- **常见追问**：
  - "限流和熔断有什么区别？"（限流是主动拒绝超量请求，熔断是下游连续失败后被动停止调用。）
  - "熔断器半开为什么要试探？"（避免下游刚恢复就被重新打爆。）
  - "下游挂了，你返回 503 还是降级数据？"（结合场景：给用户看的降级数据，给系统看的 503。）
