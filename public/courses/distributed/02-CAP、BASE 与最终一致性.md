# 第2课:CAP、BASE 与最终一致性

上一课你已经看到：多实例之后，"一部分挂了、另一部分还在跑"是常态。这一课要回答一个更根本的问题：**当系统的一部分和另一部分失去联系时，你必须在"保证数据一致"和"保证一直可用"之间做选择。这个选择就是 CAP，而绝大多数真实系统选择的是"最终一致"。**

这一课也是概念课，重点是建立三个心智模型：

1. 网络分区不是意外，是分布式系统的"必然"；
2. CAP 不是"三选二"那么简单，真正的取舍只发生在"分区发生的那一瞬间"；
3. 最终一致性不是"放弃一致性"，而是"接受一段短暂的不一致，换取可用性"。

**学习目标：**

1. 能解释网络分区的含义，以及为什么"节点不可达"无法和"节点挂了"区分；
2. 能说出 CAP 三个字母各自的定义；
3. 能解释为什么"CAP 只能三选二"是简化说法，真正的取舍发生在哪里；
4. 能区分强一致性和最终一致性，并各举一个例子；
5. 能用自己的话说出 BASE 三个字母的含义，以及它和 ACID 的对比；
6. 能举例说明缓存、主从副本、消息系统里的最终一致性。

## 1. 网络分区

上一课结尾的"部分失败"，其实都源于一个更底层的事实——**网络会分区**。

### 1.1 什么是网络分区

网络分区（Network Partition）指的是：系统里的节点被网络切成了两半，**互相之间无法通信**，但每一半自己都还活着：

```text
        ┌─────────────┐
        │  节点 A     │
        │  （数据库） │
        └──────┬──────┘
               │
         ✂ 网络断了 ✂
               │
        ┌──────┴──────┐
        │  节点 B     │
        │  （缓存）   │
        └─────────────┘

A 和 B 都活着，但互相 ping 不通。
```

关键在最后一句：**A 和 B 都活着，但互相 ping 不通。** 分区不是"某个节点挂了"，而是"节点之间失去联系"。

### 1.2 节点不可达 ≠ 节点挂了

这是分布式系统里最反直觉的一点。当你（客户端）调用一个服务超时了，你能确定的是：

```text
"我没收到对方的回答"
```

而不是：

```text
"对方挂了"  ← 你无法确定这一点
```

对方可能是这三种情况之一：

| 你的视角 | 真实情况 |
| --- | --- |
| 调用超时 | 对方挂了，确实没处理 |
| 调用超时 | 对方活着，处理完了，但响应在网络里丢了 |
| 调用超时 | 对方活着，还在慢慢处理 |

**你无法区分这三种。** 这一事实是后面所有取舍的起点：既然你永远无法确定"对方到底挂没挂"，那么当网络分区发生时，你就必须在"继续等待/保证一致"和"先响应/保证可用"之间选一个。

### 1.3 分区是物理现实，不是 bug

网络会抖动、网线会断、机房会断电、交换机要重启——**这些都会发生，且你无法阻止**。所以"分区容错"不是一道可选菜，而是一道必答题。理解了这一点，就理解了 CAP 定理里那个"为什么 P 不能放弃"。

## 2. CAP 的三个属性

CAP 定理（Eric Brewer 提出）说：一个分布式系统在发生网络分区时，**一致性、可用性、分区容错这三个属性，最多只能同时满足两个**。

先把三个词定义清楚——这是本课最重要的三个概念，面试必考。

### 2.1 一致性（Consistency）

**任意时刻，所有节点看到的数据都是最新的、一样的。**

```text
写 order_1 = "已支付" 成功后
    -> 任何后续读，都必须读到 "已支付"
    -> 不允许出现"我读到旧值未支付"
```

这里的"一致性"专指**线性一致性（Linearizability）**：一次写操作一旦完成，之后所有读操作都能读到这个新值，就像整个系统只有一台机器一样。

### 2.2 可用性（Availability）

**每个请求都能收到一个非错误的响应，但不保证是最新数据。**

```text
任何读请求，即使有节点挂了 / 分区了
    -> 系统也要返回一个结果（可能是旧数据）
    -> 不允许"我不回应你，让你干等"
```

注意：可用性强调的是"**一定有响应**"，而不是"响应一定正确"。

### 2.3 分区容错（Partition Tolerance）

**当网络分区发生时，系统仍能继续运作。**

```text
A 和 B 失去联系了
    -> 系统不能直接崩溃，得继续干活
    -> 但你必须在 C 和 A 之间选一个
```

### 2.4 为什么 P 不能放弃，所以实际是 CP vs AP

把三个属性放到"分区发生"这个场景里看，就明白了取舍：

```text
分区发生了（A 和 B 失联）
    ├─ 选 C（一致性）：拒绝一部分请求，直到 A 和 B 恢复联系
    │      -> 牺牲可用性，保证数据一致      （CP）
    │
    └─ 选 A（可用性）：先响应请求，哪怕返回旧数据
           -> 牺牲一致性，保证服务可用      （AP）
```

**P 是不能选的**——分区是物理现实，你躲不掉。所以"三选二"落到实处，就是：

> 分区发生时，你在 **C（一致）** 和 **A（可用）** 之间选哪一边。选 C 就是 CP（如 ZooKeeper、etcd、银行转账），选 A 就是 AP（如 Redis 集群、大多数电商系统）。

## 3. CAP 的适用边界

"CAP 只能三选二"这句话被引用得太多了，反而容易误导。它有几个必须澄清的边界：

### 3.1 取舍只发生在"分区发生时"

**在系统正常运行、没有分区的时候，C 和 A 是可以同时满足的。** 只有当网络分区那一刻，你才被迫二选一。分区恢复后，又回到了"既有 C 又有 A"的状态。

```text
正常运行：C 和 A 同时满足
    -> 网络分区发生：被迫在 C、A 之间二选一
    -> 分区恢复：重新回到 C 和 A 同时满足
```

### 3.2 一致性不是非黑即白

CAP 里的 C 指的是**最强的一致性（线性一致）**。但现实里，一致性是一把可以调的尺子：强一致、顺序一致、因果一致、最终一致……**大多数系统放弃的只是"最强的那一档"，而不是"一致性本身"**。

```text
线性一致（最强）────────────────────── 最终一致（最弱）
        ↑ 银行转账、etcd                    ↑ 大多数电商、缓存
```

### 3.3 面试正解：别背"三选二"，要讲"分区那一刻选哪边"

面试官问"说说 CAP"，他想听的不是你背出"一致性、可用性、分区容错"三个词，而是：

> "CAP 说的是分区发生时必须在一致性和可用性之间取舍。因为分区无法避免（P 必须选），所以实际是 CP 和 AP 的选择。而且这个取舍只在分区那一刻成立，正常运行时两者可以兼顾；一致性本身是可调的程度，不是非黑即白。"

## 4. 强一致性与最终一致性

既然大多数系统放弃了强一致，它们到底接受了什么？答案是——**最终一致**。

### 4.1 强一致性（Strong Consistency）

写成功后，**任何后续读都能读到新值**，系统看起来像只有一台机器：

```text
写 order_1 = "已支付"
读 order_1  -> 一定返回 "已支付"（不可能读到旧值）
```

代价：为了实现这个保证，系统在分区或副本落后时，可能要**拒绝读请求**（牺牲可用性），或者**阻塞等待副本同步**（牺牲延迟）。

### 4.2 最终一致性（Eventual Consistency）

写成功后，**如果没有新的写入，系统最终会收敛到一致**；但在收敛之前，可能读到旧值：

```text
写 order_1 = "已支付"
   （主库已写入，但从库还没同步完）
读 order_1  -> 可能读到 "未支付"（旧值）
   （过一会儿，从库同步完了）
读 order_1  -> 读到 "已支付"（最终一致了）
```

关键区别：**强一致"永远读不到旧值"，最终一致"可能短暂读到旧值，但最终会读到新值"。**

### 4.3 一张对比表（面试可直接口述）

| 维度 | 强一致 | 最终一致 |
| --- | --- | --- |
| 读到的数据 | 永远最新 | 可能短暂旧值 |
| 一致性保证 | 强（线性一致） | 弱（最终收敛） |
| 可用性 | 可能为一致而拒绝请求 | 通常更高（先响应） |
| 延迟 | 可能更高（等同步） | 通常更低 |
| 典型场景 | 银行余额、库存扣减、etcd | 商品浏览、点赞数、缓存、主从读 |

**一句话：最终一致不是"数据会错"，而是"数据会晚一点才一致"。** 你放弃的是"立刻读到最新"，换取的是"随时都有响应"。

## 5. BASE 的基本思想

CAP 讲的是理论取舍，BASE 是这个取舍在工程上的落地方式。BASE 是三个词的首字母：

| 字母 | 全称 | 含义 |
| --- | --- | --- |
| BA | Basically Available | **基本可用**：故障时仍提供核心功能，允许降级（如关掉次要功能、返回兜底数据） |
| S | Soft state | **软状态**：系统状态不要求时刻一致，允许中间态（如"正在同步中"） |
| E | Eventually consistent | **最终一致**：不追求立刻一致，最终收敛即可 |

### 5.1 BASE 与 ACID 的对比

这是面试高频对比。ACID 是单机数据库事务的保证（见 database 课第 9 课），BASE 是分布式系统对它的"放松"：

| 维度 | ACID（单机事务） | BASE（分布式） |
| --- | --- | --- |
| 一致性 | 强一致（原子、隔离） | 最终一致 |
| 关注点 | 单库事务的完整性 | 多节点系统的可用性 |
| 典型场景 | 银行转账、下单扣库存（单库内） | 跨库、跨服务、缓存、消息 |
| 核心手段 | 事务 + 锁 + 日志 | 补偿、重试、幂等、过期 |

> 不要理解成"BASE 比 ACID 高级"或者"分布式就不用 ACID 了"。**单库内部仍然用 ACID 事务保证单次操作的原子性；跨节点时才用 BASE 的思路去接受最终一致。** 两者的边界在"有没有跨进程/跨库"。

## 6. 最终一致性的三个场景

抽象地讲"最终一致"很虚，落到三个你已经在用的场景里就具体了。

### 6.1 场景一：缓存与数据库

你的 FastAPI 项目里，读接口通常走"先查缓存、未命中回源数据库"（Cache Aside，见 Redis 第 6 课）：

```text
写请求：更新数据库 -> 删除缓存（或先删缓存再更新）
读请求：查缓存 -> 未命中回源数据库 -> 回填缓存
```

在"更新数据库"和"删除缓存"之间，存在一个**窗口**：数据库已经是新值，但缓存还是旧值。这时读请求会命中缓存、读到旧值——**这就是最终一致的中间态**。等缓存被删掉（或 TTL 过期），下次读回源，才回到一致。

### 6.2 场景二：数据库主从副本

主库负责写，从库负责读（读写分离）：

```text
写 -> 主库（立刻成功）
        |  异步复制（有延迟）
        v
读 <- 从库（可能还没同步到新值）
```

主库写完、从库还没同步完的这段时间，读从库会读到旧数据。这是主从架构里最经典的最终一致场景，也是"刚下单为什么订单列表里还没显示"的原因之一。

### 6.3 场景三：消息系统

生产者发消息、消费者异步消费（见 Redis 第 12、13 课）：

```text
业务写库成功 -> 发送消息 -> 消费者异步处理
                    |           |
                    |     （处理有延迟）
                    v           v
            数据库已更新    消息还没被消费
```

消息发出去、但还没被消费的这段时间，系统的"业务状态"和"消息处理结果"是不一致的。消费者最终消费完，才收敛到一致。

> 三个场景的共同点：**都存在一个"写入发生"到"所有副本/下游都同步"的时间差，这个时间差里的不一致，就是最终一致允许的代价。**

## 7. 运行课程代码

这一节用一个最小脚本，把 6.1 的"短暂不一致"变成你亲眼看到的输出。只需要 Python 标准库，不接真实 MySQL/Redis。

把下面的代码保存为 `code/distributed/lesson02_cache_db.py`：

```python
# code/distributed/lesson02_cache_db.py
# 用两个 dict 模拟"数据库"和"缓存"，观察读请求在写入之后
# 的一小段时间里，可能读到旧值。  # 后是注释，实际执行时不输入。

db = {"order_1": "未支付"}      # 数据库：真实数据
cache = {"order_1": "未支付"}   # 缓存：数据库的一份副本


def read_order(order_id: str) -> str:
    """读请求：先查缓存，未命中再回源数据库并回填缓存。"""
    if order_id in cache:
        print(f"  [读] 命中缓存  -> {order_id} = {cache[order_id]}")
        return cache[order_id]
    if order_id in db:
        value = db[order_id]
        cache[order_id] = value  # 回填缓存
        print(f"  [读] 缓存未命中 -> 回源数据库 {order_id} = {value}（已回填）")
        return value
    print(f"  [读] {order_id} 不存在")
    return None


def update_forget_cache(order_id: str, new_value: str) -> None:
    """反例：只改数据库，忘了删缓存——缓存里还是旧值。"""
    db[order_id] = new_value
    print(f"[写] 更新数据库 {order_id} -> {new_value}（忘了删缓存）")


def update_delete_cache(order_id: str, new_value: str) -> None:
    """正确做法之一：先删缓存，再更新数据库。"""
    cache.pop(order_id, None)
    db[order_id] = new_value
    print(f"[写] 先删缓存，再更新数据库 {order_id} -> {new_value}")


if __name__ == "__main__":
    print("场景一：更新数据库后忘了删缓存")
    update_forget_cache("order_1", "已支付")
    read_order("order_1")  # 命中缓存，读到旧值"未支付"

    print("\n场景二：先删缓存，再更新数据库")
    update_delete_cache("order_1", "已支付")
    read_order("order_1")  # 缓存未命中，回源读到新值"已支付"
```

运行：

```bash
python code/distributed/lesson02_cache_db.py
```

观察输出：

```text
场景一：更新数据库后忘了删缓存
[写] 更新数据库 order_1 -> 已支付（忘了删缓存）
  [读] 命中缓存  -> order_1 = 未支付        ← 数据库已是"已支付"，却读到旧值！

场景二：先删缓存，再更新数据库
[写] 先删缓存，再更新数据库 order_1 -> 已支付
  [读] 缓存未命中 -> 回源数据库 order_1 = 已支付（已回填）  ← 读到新值
```

**结论：场景一就是"最终一致的中间态"被无限拉长——因为缓存永远不失效，不一致就永远不收敛。场景二通过"删缓存"制造了一个短暂窗口，让系统最终回到一致。** 这就是最终一致性在缓存场景里的完整落法：接受"删缓存到回填之间"的短暂不一致，换取读接口的高性能。

> 示例说明：这里没有真实网络分区，两个 dict 的"不一致"是**我们用代码制造出来的**，但"缓存未命中回源、回填"是真实的读缓存逻辑。真实系统里，这个不一致窗口来自"更新数据库"和"删除缓存"两步之间的时间差。

## 10. 面试高频考点

- **CAP 正解**：分区发生时在 C 和 A 之间取舍；P 不可选；取舍只在分区那一刻成立；一致性是可调程度。
- **强一致 vs 最终一致**：能举例（银行余额 vs 商品浏览数/缓存），能说清"最终一致 = 接受短暂旧值换取可用性"。
- **BASE vs ACID**：不是替代关系，ACID 管单库事务，BASE 管跨节点最终一致。
- **三个场景**：缓存与 DB、主从副本、消息系统，各能说清"不一致窗口"在哪。
- **常见追问**：
  - "为什么不能既要强一致又要高可用？"（分区发生时，要强一致就得拒绝请求，可用性就没了。）
  - "先删缓存还是先更新数据库？"（本质是最终一致窗口的不同形态，详细取舍见 Redis 第 8 课，这里只要答出"这是最终一致的取舍"。）
  - "你项目里哪里用了最终一致？为什么可以接受？"（结合自己的缓存/异步任务答。）

如果现在能回答"为什么分区发生时必须在 C 和 A 之间二选一"、能用自己的话讲清"强一致和最终一致的区别并各举一例"、能说清"BASE 和 ACID 是并存不是替代"，并且能指出自己项目里至少一处"最终一致的中间态"，就可以进入第 3 课：负载均衡与一致性哈希。
