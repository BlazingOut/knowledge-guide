# 第5课:重试、退避与幂等

第 4 课结尾留了一个问题：超时不代表失败，所以重试可能造成重复执行。这一课正面展开三件事——**什么时候能重试、怎么重试才不会放大故障、为什么重试必须配合幂等**。这三件事是分布式后端里最常被追问的一组概念。

这一课是机制课，重点是建立三个心智模型：

1. 重试只对"临时错误"有意义，对"永久错误"重试是白费；
2. 无退避、无上限的重试会把故障放大成"重试风暴"；
3. 重试的代价是"可能重复执行"，所以必须靠幂等兜底。

**学习目标：**

1. 能区分临时错误和永久错误，判断哪些请求适合重试；
2. 能解释固定间隔、指数退避、随机抖动三种退避策略；
3. 能解释为什么要设最大重试次数；
4. 能解释"重试风暴"是什么、为什么无上限重试会放大故障；
5. 能解释"超时但服务端已成功"这个问题，以及它为什么需要幂等；
6. 能设计幂等键，并说明重试与事务的关系。

## 1. 临时错误与永久错误

重试的第一条铁律：**不是所有失败都值得重试**。要先分清错误是临时的还是永久的。

### 1.1 两种错误

| 类型 | 含义 | 例子 | 重试有意义吗 |
| --- | --- | --- | --- |
| 临时错误 | 这次失败，重试可能成功 | 网络抖动、连接超时、下游临时过载 | 有 |
| 永久错误 | 重试多少次都一样失败 | 参数非法（400）、没权限（403）、资源不存在（404） | 没有 |

判断标准一句话：**这个错误是不是"暂时的、会自己恢复的"。**

```text
下游返回 500（服务端临时故障）  -> 临时错误，可以重试
下游返回 400（你传的参数错了）  -> 永久错误，重试也是 400
```

### 1.2 对永久错误重试的后果

```text
参数非法的请求，重试 3 次
    -> 还是 400
    -> 白白浪费 3 次请求、3 段等待时间
    -> 还增加了下游负载（它要处理 3 次无效请求）
```

所以正确做法：**永久错误直接放弃，只有临时错误才进重试逻辑。**

## 2. 退避策略

确认是临时错误、要重试了，下一个问题是：**隔多久重试一次？** 这就是退避（backoff）策略。

### 2.1 固定间隔

```text
每次重试都等固定时间：1s -> 1s -> 1s -> 1s
```

最简单，但有隐患：**如果大量客户端同时失败、同时按固定间隔重试，它们会在同一时刻一起涌向下游**（下一节的"重试风暴"）。

### 2.2 指数退避（Exponential Backoff）

```text
等待时间按指数增长：1s -> 2s -> 4s -> 8s
```

第一次重试快一点（希望是偶发抖动，马上就好），越往后等得越久（给下游更长的恢复时间）。**这是生产上最常用的默认策略。**

### 2.3 随机抖动（Jitter）

```text
在退避时间上，再加一个随机量：
    指数退避 2s，实际等待 2s + random(0~1s)
```

解决"惊群"问题：**所有客户端即使退避时间相同，加了随机抖动后也不会在同一毫秒同时重试**，而是错开。

### 2.4 最大重试次数

```text
重试不能无限，必须有上限（比如最多 3 次）
    第 1 次失败 -> 退避 -> 重试
    第 2 次失败 -> 退避 -> 重试
    第 3 次失败 -> 放弃，返回明确失败
```

没有上限的重试，就是下一节的灾难。

### 2.5 一张速查表

| 策略 | 等待方式 | 解决什么 |
| --- | --- | --- |
| 固定间隔 | 每次等固定时间 | 简单，但会惊群 |
| 指数退避 | 时间指数增长 | 给下游越来越长的恢复时间 |
| 随机抖动 | 退避 + 随机量 | 让重试错开，避免同时涌来 |
| 最大次数 | 重试有上限 | 防止无限重试 |

## 3. 重试风暴

如果把"退避"和"上限"都去掉，会发生什么？——**重试风暴（Retry Storm）**。

### 3.1 它怎么发生

```text
下游服务短暂变慢（还没挂，只是慢）
    -> 大量客户端请求超时
    -> 所有客户端立刻同时重试
    -> 下游请求量瞬间翻倍（甚至翻几倍）
    -> 下游被彻底打挂
    -> 更多客户端超时、更多重试……
```

**重试不是缓解了故障，而是放大了故障。** 一个"下游变慢"的小问题，被无节制的重试放大成"下游宕机"的大事故。

### 3.2 怎么防

```text
1. 退避：重试前要等，且越来越久
2. 抖动：让重试错开，别同时涌来
3. 上限：最多重试 N 次就放弃
4. 熔断：连续失败就暂时不再调下游（第 6 课）
```

重试和熔断是配套的：重试负责"偶发失败再试一次"，熔断负责"连续失败先别调了"。

## 4. 超时但已成功

这是重试最反直觉、也最危险的一环，是第 1 课"结果未知"的直接后果。

### 4.1 问题

```text
客户端发起请求
    -> 下游处理成功（比如已经扣款了）
    -> 但响应在网络里丢了 / 太慢
    -> 客户端超时，以为失败
    -> 客户端重试
    -> 下游又处理了一次（又扣了一次款！）
```

**客户端以为的"重试一次"，在下游变成了"执行两次"。**

### 4.2 结论

```text
超时 ≠ 失败
    -> 你无法确定下游到底执行了没有
    -> 重试可能导致重复执行
    -> 所以重试必须配合幂等（下一节）
```

## 5. 幂等与重复提交

既然重试可能重复执行，就必须让"重复执行"变得无害——这就是**幂等（Idempotent）**。

### 5.1 定义

> 幂等：**同一个操作，执行一次和执行多次，最终结果完全一样。**

```text
读操作天然幂等：查 100 次用户信息，结果都一样，没有副作用
写操作不一定幂等：
    - "扣款 100 元" 执行两次 = 扣了 200 元（不幂等，危险）
    - "把余额设为 100 元" 执行两次 = 还是 100 元（幂等）
```

### 5.2 幂等键（Idempotency Key）

让不幂等的写操作变得幂等的常用手段，是给每次请求带一个**唯一请求号**，服务端用它去重：

```text
客户端生成唯一 request_id（比如 UUID）
    -> 第一次提交：服务端记下 request_id，执行扣款
    -> 网络抖动，客户端重试，带同一个 request_id
    -> 服务端发现 request_id 已处理过，直接返回上次结果，不再执行
```

```text
第一次：request_id=abc123 -> 服务端：没见过，执行，记下 abc123
重试  ：request_id=abc123 -> 服务端：见过 abc123，跳过执行
```

这就是为什么支付回调、订单提交这类接口，都要求幂等：**因为调用方一定会因为网络问题重试。**

### 5.3 幂等和去重的关系

幂等键本质是一种**去重**：用 request_id 判断"这个请求是不是已经处理过了"。区别在于范围：

- 幂等键：同一个**业务请求**的重复提交去重；
- 去重：可以更宽泛（比如消息队列里的重复消费去重，见 Redis 第 13 课）。

## 6. 重试与事务

最后理清一个易混点：**事务不能替代幂等。**

### 6.1 事务管的是"一次操作内部"

```text
下单 = 写订单 + 写明细 + 扣库存
    -> 事务保证这三步要么全成功、要么全失败（原子性）
```

事务保证的是**单次操作的原子性**，它不关心"这个操作被执行了几次"。

### 6.2 事务提交后，重试不会自动回滚

```text
第一次：下单事务提交成功
    -> 响应丢失，客户端超时重试
    -> 第二次：又开一个事务，又提交一次
    -> 结果：下了两单
```

**事务已经提交了，重试是"再来一次"，不是"回滚上一次"。** 所以：

```text
事务 + 幂等键 一起用
    -> 事务保证单次操作的原子性
    -> 幂等键保证同一个请求不会被重复执行
    -> 两者各管一段，缺一不可
```

## 7. 运行课程代码

这一节用一个最小脚本，把"临时错误 vs 永久错误""指数退避 + 抖动 + 上限""幂等键"三个点跑成可观察的输出。只需要 Python 标准库。

把下面的代码保存为 `code/distributed/lesson05_retry.py`：

```python
# code/distributed/lesson05_retry.py
# 演示重试的三件事：临时错误才重试、指数退避 + 抖动 + 上限、幂等键去重。
#  # 后是注释，实际执行时不输入。

import random
import time

random.seed(0)  # 固定随机种子，保证每次运行结果一致

processed = set()  # 已处理的 request_id 集合，用于幂等去重


def flaky_call():
    """模拟一个不稳定下游：前 2 次调用超时，第 3 次成功。"""
    state = {"count": 0}

    def call():
        state["count"] += 1
        return "timeout" if state["count"] <= 2 else "ok"

    return call


def invalid_call():
    """模拟一个永久错误下游：无论调几次都返回参数非法。"""
    def call():
        return "invalid"
    return call


def retry_with_backoff(call, max_retries=3, base_delay=0.5):
    """指数退避 + 随机抖动 + 最大次数的重试。

    call：下游调用函数，返回 "ok"（成功）/ "timeout"（临时）/ "invalid"（永久）
    返回：最终结果描述
    """
    for attempt in range(1, max_retries + 1):
        result = call()
        print(f"    第 {attempt} 次调用 -> {result}")

        if result == "ok":
            return "成功"
        if result == "invalid":
            return "永久错误，不重试，直接放弃"

        # 临时错误（timeout）：退避后重试
        if attempt < max_retries:
            jitter = random.uniform(0, base_delay)              # 随机抖动
            wait = base_delay * (2 ** (attempt - 1)) + jitter   # 指数退避
            print(f"    退避等待 {wait:.2f} 秒...")
            time.sleep(wait)

    return "重试次数耗尽，仍失败"


def submit_order(order_id, request_id):
    """带幂等键的下单：同一个 request_id 只执行一次。"""
    if request_id in processed:
        print(f"  [幂等] {request_id} 已处理过，跳过下单 {order_id}")
        return
    processed.add(request_id)
    print(f"  [执行] 下单 {order_id}（request_id={request_id}）")


if __name__ == "__main__":
    print("实验一：临时错误（前 2 次超时），指数退避重试后成功")
    print("  结果：", retry_with_backoff(flaky_call()))

    print("\n实验二：永久错误（参数非法），不重试直接放弃")
    print("  结果：", retry_with_backoff(invalid_call()))

    print("\n实验三：幂等键（重复 request_id 只执行一次）")
    submit_order("order_1", "req_100")
    submit_order("order_1", "req_100")  # 重复的 request_id
    submit_order("order_2", "req_101")
```

运行：

```bash
python code/distributed/lesson05_retry.py
```

观察输出：

```text
实验一：临时错误（前 2 次超时），指数退避重试后成功
    第 1 次调用 -> timeout
    退避等待 0.xx 秒...
    第 2 次调用 -> timeout
    退避等待 1.xx 秒...
    第 3 次调用 -> ok
  结果：成功

实验二：永久错误（参数非法），不重试直接放弃
    第 1 次调用 -> invalid
  结果：永久错误，不重试，直接放弃

实验三：幂等键（重复 request_id 只执行一次）
  [执行] 下单 order_1（request_id=req_100）
  [幂等] req_100 已处理过，跳过下单 order_1
  [执行] 下单 order_2（request_id=req_101）
```

**结论：实验一，临时错误在指数退避下第 3 次成功，且等待时间一次比一次长；实验二，永久错误第一次就放弃，没浪费重试；实验三，重复的 request_id 被幂等键拦下，只执行了一次。** 这三个行为分别对应本课的三个核心结论。

> 示例说明：这里"下游前 2 次超时""参数非法"是**模拟**的，但"指数退避的等待时间一次比一次长""永久错误直接放弃""幂等键去重"是真实的重试逻辑。真实系统里，这些逻辑就嵌在 HTTP 客户端或任务框架里。

## 10. 面试高频考点

- **临时 vs 永久错误**：能判断一个错误是否值得重试（500 重试、400/403/404 不重试）。
- **退避三件套**：固定间隔 / 指数退避 / 随机抖动，各自解决什么。
- **重试风暴**：无退避无上限的重试如何放大故障，怎么防（退避 + 抖动 + 上限 + 熔断）。
- **超时但已成功**：这是"结果未知"的落地，是重试必须配幂等的根本原因。
- **幂等**：定义 + 幂等键去重，能举支付回调、订单提交的例子。
- **重试 vs 事务**：事务管单次原子性，幂等管重复执行，两者互补。
- **常见追问**：
  - "你的重试策略是什么？"（指数退避 + 抖动 + 最大 3 次 + 永久错误不重试。）
  - "重试会不会把下游打挂？"（会，所以要退避、抖动、上限、熔断。）
  - "怎么保证重复请求不重复扣款？"（幂等键：唯一 request_id 去重。）
