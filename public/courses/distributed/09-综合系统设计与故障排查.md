# 第9课:综合系统设计与故障排查

这是本课程的收官课。前面 8 课分别讲了单机/集群/分布式、CAP、负载均衡与一致性哈希、超时、重试与幂等、限流熔断降级、分布式一致性与任务租约、高可用与分布式 ID。这一课把它们**串成一个完整的系统**，并建立一套"遇到故障怎么排查"的框架——这也是面试里"系统设计题"和"故障排查题"的标准打法。

这一课是综合课，重点是建立两个心智模型：

1. 一个生产后端系统 = 入口层 + 应用层 + 依赖层，每一层都有对应的可靠性手段；
2. 排查故障不是乱猜，而是"界定 → 分层 → 定位 → 验证"四步走。

**学习目标：**

1. 能画出一个"接收请求、写库、发异步任务、调模型服务"的后端完整架构图，标出每个组件职责；
2. 能描述一次请求从进入到返回的完整旅程；
3. 能把超时/重试/限流/熔断/幂等/状态机/负载均衡/分布式 ID 落到具体层次；
4. 能按"界定 → 分层 → 定位 → 验证"的框架排查故障；
5. 能针对六类常见故障给出排查路径；
6. 能用系统设计题的答题框架应对面试。

## 1. 完整架构图

综合场景：**设计一个接收用户请求、写入数据库、发送异步任务并调用模型服务的 API**（这就是你简历 Agent 项目的雏形）。

```text
                    用户
                      |
                      v
              负载均衡器（Nginx）        <- 第 3 课：服务端侧负载均衡
                |           |
                v           v
          API 实例 A     API 实例 B      <- 多实例，无状态
                |     \     |
                |      \    |
                v       v   v
              Redis    MySQL(主)         <- 第 8 课：主从 + 读写分离
                         |
                         v
                      MySQL(从)          <- 读请求走这里（读写分离）
                         |
                     PostgreSQL         <- 第 7 课：任务状态落库（状态机 + 租约）
                         ^
                         |
                     Worker(异步任务)     <- 第 7 课：消费任务、调模型
                         |
                         v
                    模型服务(LLM)         <- 第 4 课：调用要设超时
```

各组件的职责一句话：

| 组件 | 职责 | 涉及课程 |
| --- | --- | --- |
| 负载均衡器 | 接请求、分流到多实例、剔除故障实例 | 第 3 课 |
| API 实例 | 处理请求、限流、写库、发任务 | 第 6 课 |
| Redis | 缓存、幂等键、限流计数 | 第 5、7 课 |
| MySQL 主从 | 业务数据持久化、读写分离 | 第 8 课 |
| PostgreSQL | 任务状态、执行步骤、租约 | 第 7 课 |
| Worker | 异步消费任务、调模型 | 第 7 课 |
| 模型服务 | LLM 推理 | 第 4 课 |

## 2. 一次请求的旅程

用户提交一个"让 Agent 生成报告"的任务，完整走一遍：

```text
1. 用户提交任务
     -> 负载均衡器（Nginx）把请求分给 API 实例 A      [第 3 课：负载均衡]
2. API 限流检查                                       [第 6 课：限流]
     -> 超过限额返回 429
3. API 幂等检查（带 request_id）                       [第 5 课：幂等]
     -> 重复请求直接返回上次结果
4. API 写业务数据（MySQL 主库）+ 写任务消息（outbox）   [第 7 课：Outbox，同事务]
5. API 返回"任务已受理"（不等待模型跑完）
6. Worker 从消息队列取任务                              [第 7 课：异步任务]
7. Worker 把任务状态改成 running，设租约               [第 7 课：状态机 + 租约]
8. Worker 调模型服务（带超时 + 重试）                   [第 4、5 课：超时重试]
9. Worker 把任务状态改成 succeeded，记录结果            [第 7 课：状态机]
10. 用户轮询/回调查任务结果
```

**关键设计**：第 4 步到第 5 步之间，API 把"长耗时任务"和"请求响应"解耦了——用户提交后立刻返回，模型在后台跑。这正是你简历里"高并发服务架构"的核心。

## 3. 各层的可靠性设计

把前 8 课的知识点，落到架构的每一层：

| 层 | 可靠性手段 | 对应课程 |
| --- | --- | --- |
| 入口层（Nginx） | 负载均衡、剔除故障实例 | 第 3 课 |
| 应用层（API） | 限流（429）、幂等（request_id）、降级 | 第 5、6 课 |
| 调用层（API → 下游） | 超时、重试、熔断 | 第 4、5、6 课 |
| 数据层（MySQL） | 主从、读写分离、副本 | 第 8 课 |
| 任务层（Worker） | 状态机、租约、心跳、超时扫描 | 第 7 课 |
| 标识层（ID） | 分布式 ID（Snowflake） | 第 8 课 |
| 一致性 | 强一致 vs 最终一致、补偿、幂等 | 第 2、7 课 |

**一句话串讲**：入口用负载均衡分流，应用层用限流和幂等保护，调用层用超时重试熔断兜底，数据层用主从副本保证可用，任务层用状态机 + 租约保证可靠，ID 层用分布式 ID 保证唯一。

## 4. 故障排查框架

排查故障最忌讳"乱猜"。用四步框架：

```text
1. 界定：什么现象？
    -> 慢？报错？挂了？数据不对？——先把现象描述清楚
2. 分层：从哪一层开始查？
    -> 入口（负载均衡）-> 应用（API）-> 依赖（缓存/DB/消息）-> 下游（模型）
3. 定位：用日志/指标/命令，逐层缩小范围
    -> 看接口耗时、错误类型、任务状态、日志串联
4. 验证：修复后复现，确认现象消失
```

```text
接口变慢的例子：
    界定：P95 延迟从 1s 涨到 5s
    分层：入口正常 -> 应用层？-> 发现是"调模型"这一步慢
    定位：看调用耗时日志，模型服务从 2s 涨到 10s
    验证：给模型调用加超时/熔断后，接口不再被拖慢
```

**核心原则：先定位到"哪一层、哪一跳"，再动手修。** 不要一上来就重启服务、加机器。

## 5. 常见故障排查

六个高频故障，每个给"现象 → 假设 → 定位 → 修复"：

### 5.1 下游服务响应变慢

```text
现象：接口整体变慢，P95 延迟升高
假设：某个下游（模型服务）变慢，拖慢了整条链
定位：看调用链各跳耗时，确认是"调模型"这一跳慢
修复：给下游调用设超时（第 4 课）、连续失败熔断（第 6 课）、必要时降级
```

### 5.2 重试导致请求数量增加

```text
现象：下游收到的请求量突然翻倍
假设：上游在大量重试（下游抖动触发重试风暴）
定位：看下游请求日志，发现大量相同 request_id 的重复请求
修复：退避 + 抖动 + 上限（第 5 课）、熔断（第 6 课）
```

### 5.3 缓存与数据库不一致

```text
现象：读到旧数据（比如改了状态，但查出来还是旧的）
假设：更新数据库后忘了删缓存
定位：对比缓存值和数据库值，确认缓存是旧值
修复：删缓存 / 设 TTL / 先删缓存再更新（第 2、7 课）
```

### 5.4 消息重复消费

```text
现象：同一个任务被处理了多次（比如重复扣款）
假设：消费者没做幂等，或消息被重投
定位：看消费日志，发现同一 message_id 被处理了两次
修复：消费幂等（幂等键去重，第 5、7 课）
```

### 5.5 某个服务实例不可用

```text
现象：部分请求失败（Connection Refused），但另一部分正常
假设：某个实例挂了（部分失败，第 1 课）
定位：健康检查 / 探活，确认哪个实例没响应
修复：负载均衡剔除该实例（第 3 课）、故障转移（第 8 课）
```

### 5.6 分布式 ID 重复

```text
现象：插入数据报主键冲突（duplicate key）
假设：Snowflake 遇到时钟回拨，生成了重复 ID
定位：查 ID 生成日志，发现时间戳倒退
修复：检测回拨、拒绝生成、或换 ID 方案（第 8 课）
```

## 6. 系统设计题的答题框架

面试问"设计一个 XX 系统"，用这个框架口述（约 5 分钟）：

```text
1. 需求澄清（30 秒）
    -> 功能是什么？规模多大？一致性要求多高？

2. 架构分层（1 分钟）
    -> 入口（网关/负载均衡）-> 应用（API）-> 依赖（缓存/DB/消息/模型）
    -> 画架构图，标职责

3. 数据流（1 分钟）
    -> 一次请求怎么走：进来 -> 处理 -> 写库/发任务 -> 返回

4. 可靠性（1.5 分钟）
    -> 超时、重试、限流、熔断、幂等、状态机、租约各落在哪

5. 故障与取舍（1 分钟）
    -> 每个组件挂了怎么办；强一致 vs 最终一致、同步 vs 异步怎么选
```

```text
示例："设计一个 Agent 任务系统"
    1. 需求：用户提交任务，后台调 LLM，异步返回结果，要能追踪状态
    2. 架构：Nginx -> FastAPI(多实例) -> Redis + MySQL + PostgreSQL + Worker + LLM
    3. 数据流：提交 -> 限流/幂等 -> 写库 + 发任务 -> Worker 消费 -> 调模型 -> 更新状态
    4. 可靠性：调模型设超时重试熔断；任务用状态机 + 租约；回调/接口幂等
    5. 取舍：模型调用是异步的（最终一致），任务状态强一致（PostgreSQL 落库）
```

**关键：不要只画图，要能说清"每一层的可靠性手段"和"每个组件挂了怎么办"——这才是面试官想听的。**

## 9. 面试高频考点

- **完整架构**：能画出"入口 → 应用 → 依赖"三层，标职责。
- **数据流**：能讲清一次请求的完整旅程，尤其"异步解耦"（API 受理 vs Worker 执行）。
- **可靠性落点**：超时/重试/限流/熔断/幂等/状态机/租约/负载均衡/分布式 ID 各落在哪一层。
- **故障排查**：四步框架（界定 → 分层 → 定位 → 验证），六个常见故障的排查路径。
- **系统设计题**：需求 → 架构 → 数据流 → 可靠性 → 取舍。
- **常见追问**：
  - "你项目里长任务怎么保证可靠？"（状态机 + 租约 + 幂等。）
  - "下游模型服务挂了，用户会看到什么？"（超时/熔断后返回降级结果，而不是无限等。）
  - "怎么定位一次请求失败？"（日志 + 请求 ID 串联 + 逐层查耗时。）
