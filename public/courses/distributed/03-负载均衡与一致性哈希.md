# 第3课:负载均衡与一致性哈希

第 1 课你看到了多实例之后的新问题，其中第 3 个是"请求到底发给谁"。这一课就正面回答它：**用负载均衡把请求分流到多个实例**。同时，分流只是问题的一半，另一半是"数据怎么分布到多台节点，才能在节点增减时不剧烈抖动"——这引出了一致性哈希。

这一课是机制课，重点是建立两个心智模型：

1. 负载均衡解决的是"多实例下请求怎么分"，它的算法各有适用场景；
2. 一致性哈希解决的是"数据怎么稳定地分到节点"，核心是"节点增减时只影响局部"。

**学习目标：**

1. 能解释负载均衡解决什么问题，以及客户端侧 / 服务端侧两种位置的区别；
2. 能说出轮询、随机、加权轮询、最小连接四种算法的适用场景；
3. 能解释为什么取模分片在扩缩容时会让大部分数据重新映射；
4. 能描述一致性哈希的哈希环，并说明虚拟节点解决什么问题；
5. 能说明一致性哈希在缓存、数据库分片、负载均衡中的用法；
6. 能解释负载均衡如何通过健康检查剔除不可用实例。

## 1. 负载均衡的作用

回到第 1 课的架构：两个 FastAPI 实例前面放了一个"负载均衡器"，它负责把每个请求交给某一个实例。这个"分发请求"的动作，就是**负载均衡（Load Balancing）**。

### 1.1 它解决两个问题

```text
多实例之后，如果请求都打到一个实例上：
    -> 那个实例忙死，其他实例闲死          （负载不均）
    -> 那个实例一挂，所有请求就都失败了     （单点故障）
```

负载均衡把流量分摊到多个实例，同时解决这两个问题：

- **负载不均**：把请求轮流（或按某种策略）分给不同实例，避免"一个忙死、其余闲死"；
- **单点故障**：某个实例挂了，负载均衡器不再把请求发给它，流量转到其他实例。

> 注意：负载均衡本身不等于高可用（见第 8 课）。它只是把请求"分散"开；如果负载均衡器自己只有一台、挂了，系统还是不可用。高可用是后面叠加副本、故障转移之后的事。

### 1.2 一个朴素的类比

负载均衡像银行排队的叫号机：多个柜台（实例）同时服务，叫号机（负载均衡器）把每个顾客（请求）叫到某个柜台。柜台忙闲不均、某个柜台临时关闭，都靠叫号机来调度。

## 2. 负载均衡的两种位置

负载均衡的逻辑可以放在两个不同的地方：

| 位置 | 谁来做选择 | 例子 | 特点 |
| --- | --- | --- | --- |
| 客户端侧 | 调用方自己选实例 | 微服务里调用方维护一份实例列表，自己挑一个发请求 | 少了中间一跳，但调用方要知道所有实例 |
| 服务端侧 | 中间放一个网关/代理转发 | Nginx、云厂商的 LB、API 网关 | 调用方只认一个入口，实例列表对调用方透明 |

```text
客户端侧：                    服务端侧：
调用方 ──自己选──> 实例 A      调用方 ──> [负载均衡器] ──> 实例 A / B / C
             └──> 实例 B                        （网关/代理）
             └──> 实例 C
```

你第 1 课画的架构（客户端 → 负载均衡器 → 两个实例）就是**服务端侧**。面试里问"你们怎么负载均衡"，两种都要能说清。

## 3. 四种常见算法

负载均衡器"怎么选实例"，有几种经典算法。它们解决的是**"下一个请求给谁"**这个瞬间决策。

### 3.1 轮询（Round Robin）

```python
# 依次轮流：A -> B -> C -> A -> B -> C ...
def round_robin(nodes, i):
    return nodes[i % len(nodes)]
```

**每个请求依次轮流分配。** 最简单、最均匀（前提是所有实例性能一样）。

### 3.2 随机（Random）

```python
import random
def random_pick(nodes):
    return random.choice(nodes)
```

**每次随机挑一个。** 请求量足够大时，长期看也接近均匀。实现最简单，但没有"顺序"可言。

### 3.3 加权轮询（Weighted Round Robin）

**按权重分配，权重高的实例多分到请求。**

```text
实例 A 权重 3，实例 B 权重 1
    -> 每 4 个请求里，A 分到 3 个，B 分到 1 个
```

适用场景：**实例性能不均**（有的机器 4 核、有的 16 核）。给强机器更高权重，让它多干活。

### 3.4 最小连接（Least Connections）

**把请求发给当前"正在处理的连接数最少"的实例。**

```text
实例 A 当前 5 个连接，实例 B 当前 1 个连接
    -> 下一个请求给 B（它最闲）
```

适用场景：**每个请求的耗时差异大**（比如有的请求是查缓存、有的是调模型）。轮询只看"轮到谁"，不管"谁忙谁闲"；最小连接看的是实时负载，更能避免"慢请求都堆到同一个实例"。

### 3.5 一张对比表（面试直接口述）

| 算法 | 逻辑 | 适用场景 |
| --- | --- | --- |
| 轮询 | 依次轮流 | 实例性能一致、请求耗时相近 |
| 随机 | 随机挑 | 同上，实现最简单 |
| 加权轮询 | 按权重分配 | 实例性能不均 |
| 最小连接 | 发给最闲的 | 请求耗时差异大 |

## 4. 取模分片的问题

负载均衡解决了"请求分流"，但还有一个相关但不完全相同的问题：**数据怎么分到多台节点**。比如缓存有 3 台 Redis，一个 key 该放哪台？

### 4.1 取模是最直觉的做法

```python
node = hash(key) % 3   # 3 台节点，按 key 的哈希值对 3 取模
```

```text
hash(key) % 3 == 0  -> 节点 0
hash(key) % 3 == 1  -> 节点 1
hash(key) % 3 == 2  -> 节点 2
```

逻辑简单：把 key 映射成一个整数，对节点数取模，落到哪个就是哪个节点。

### 4.2 问题：节点数一变，大部分 key 都要搬家

现在节点从 3 台扩到 4 台，算法变成 `hash(key) % 4`：

```text
原来 hash(key) % 3 == 1 的 key，现在 hash(key) % 4 可能是 0、1、2、3 里任意一个
    -> 原来在节点 1 的 key，大部分要搬到别的节点
```

具体算一下（假设哈希值均匀分布）：3 台变 4 台时，**只有约 1/4 的 key 保持不变，约 3/4（75%）的 key 会换节点**。

这个后果是灾难性的：

```text
缓存场景：3 台缓存扩到 4 台
    -> 75% 的缓存 key 全部失效
    -> 大量请求瞬间回源数据库
    -> 数据库被打挂（缓存雪崩，见 Redis 第 7 课）
```

**根因：取模的映射结果和"节点总数"强绑定。节点数一变，映射全局重排。** 这就是取模分片最大的问题。

## 5. 一致性哈希

一致性哈希（Consistent Hashing）就是为了解决"节点增减时大量重映射"而生的。

### 5.1 哈希环：把节点和 key 都放到一个环上

想象一个首尾相接的环，范围是 `0 ~ 2^32-1`。把每个节点（按它的名字或 IP）哈希成一个环上的位置：

```text
环（顺时针）：  0 ────── A ────── B ────── C ────── 2^32
                       ↑          ↑          ↑
                    hash("A")  hash("B")  hash("C")
```

key 也一样：`hash(key)` 得到环上的一个位置，然后**顺时针找离它最近的第一个节点**，这个节点就负责这个 key。

```text
key1 的位置落在 A 和 B 之间
    -> 顺时针找到 B
    -> key1 归 B 负责
```

### 5.2 节点增减：只影响局部

关键来了。假设新增一个节点 D，`hash("D")` 落在 B 和 C 之间：

```text
原来（3 节点）：  0 ── A ── B ── C ── 2^32
                          ↑ key1 归 B

新增 D 后：       0 ── A ── B ── D ── C ── 2^32
                          ↑     ↑ key1 现在归 D
                          B     D 接管了 B 到 D 之间的 key
```

**只有"落在 B 和 D 之间"的 key 会从 B 迁移到 D，其他 key 完全不动。** 对比取模的 75% 重映射，一致性哈希在 3 台加 1 台时，理论上只有约 1/4 的 key 迁移（新节点 D 从它顺时针方向的下一个节点 C 那里，接管了约 1/4 的环空间）。

```text
取模 3->4：约 75% 的 key 搬家
一致性哈希 3->4：约 25% 的 key 搬家
```

**这就是"一致性"的含义：节点增减时，映射关系尽量保持一致，只有局部受影响。**

### 5.3 虚拟节点：解决数据倾斜

一致性哈希有个隐患：**节点少时，节点在环上的位置可能很不均匀**。

```text
假设只有 2 个节点，它们哈希后的位置恰好离得很近：
    -> 环上 90% 的 key 都落到其中一个节点
    -> 另一个节点几乎没数据（数据倾斜）
```

解决方法是**虚拟节点（Virtual Node）**：每个真实节点，不再只占环上的一个位置，而是用多个虚拟位置（比如 `hash("A#0")`、`hash("A#1")`、`hash("A#2")`）：

```text
真实节点 A  -> 虚拟位置 A#0、A#1、A#2（三个点分散在环上）
真实节点 B  -> 虚拟位置 B#0、B#1、B#2
```

这样每个真实节点在环上有多个、且分散的虚拟点，key 落到这些虚拟点后，最终都算到对应的真实节点头上。**虚拟节点让数据分布更均匀，是生产上一致性哈希的标配。**

### 5.4 一句话总结

> 一致性哈希 = 哈希环 + 顺时针找最近节点 + 虚拟节点。它把"节点增减"的影响从"全局重排"缩小到"局部迁移"。

## 6. 一致性哈希的用途

一致性哈希不是只能做负载均衡，它在"数据分片"里更常见：

| 用途 | 场景 | 为什么用它 |
| --- | --- | --- |
| 缓存分片 | 多台 Redis 分片存 key | 扩缩容时少失效，避免缓存雪崩 |
| 数据库分片 | 按用户 ID 分库分表 | 扩库时少迁移数据 |
| 负载均衡 | 有状态请求路由（同一用户总到同一实例） | 粘性路由，且扩缩容影响小 |

> 区分一个易混点：**负载均衡算法（轮询/加权/最小连接）解决"请求怎么分"，一致性哈希解决"key 怎么稳定地落到节点"。** 一致性哈希可以作为一种特殊的负载均衡策略（尤其是有状态/需要粘性的场景），但它更本质的身份是"分片策略"。

## 7. 运行课程代码

这一节用两个最小实验，分别验证"负载均衡算法"和"取模 vs 一致性哈希的重映射对比"。只需要 Python 标准库。

把下面的代码保存为 `code/distributed/lesson03_load_balancing.py`：

```python
# code/distributed/lesson03_load_balancing.py
# 演示负载均衡算法，以及取模 vs 一致性哈希在扩缩容时的重映射对比。
#  # 后是注释，实际执行时不输入。

import hashlib
import random


def hash_key(key: str) -> int:
    """把 key 映射到 [0, 2**32) 的整数。

    用 MD5 而不是内建 hash()：内建 hash() 对字符串每次运行结果不同
    （受 PYTHONHASHSEED 影响），MD5 保证结果确定、可复现。
    """
    return int(hashlib.md5(key.encode()).hexdigest(), 16) % (2 ** 32)


def round_robin(nodes, i):
    """轮询：第 i 个请求分给 nodes[i % len(nodes)]。"""
    return nodes[i % len(nodes)]


class ConsistentHash:
    """简化版一致性哈希：哈希环 + 虚拟节点。"""

    def __init__(self, nodes, virtual_copies=100):
        self.nodes = nodes
        self.ring = {}  # 环上位置 -> 真实节点
        for node in nodes:
            for i in range(virtual_copies):
                # 每个真实节点在环上占 100 个虚拟位置（node#0 ... node#99）
                pos = hash_key(f"{node}#{i}")
                self.ring[pos] = node

    def get_node(self, key: str) -> str:
        """key 顺时针找环上最近的节点。"""
        if not self.ring:
            return ""
        h = hash_key(key)
        for pos in sorted(self.ring.keys()):
            if h <= pos:
                return self.ring[pos]  # 第一个 >= h 的位置
        return self.ring[sorted(self.ring.keys())[0]]  # 越过环尾，回到环头


if __name__ == "__main__":
    # 实验一：轮询分配结果
    print("实验一：轮询，6 个请求分给 3 个实例")
    nodes = ["A", "B", "C"]
    for i in range(6):
        print(f"  请求 {i} -> 实例 {round_robin(nodes, i)}")

    # 实验二：取模 vs 一致性哈希，3 节点扩到 4 节点的重映射比例
    keys = [f"user_{i}" for i in range(10000)]
    print("\n实验二：3 节点扩到 4 节点，重映射比例对比")

    mod_before = {k: hash_key(k) % 3 for k in keys}
    mod_after = {k: hash_key(k) % 4 for k in keys}
    mod_moved = sum(1 for k in keys if mod_before[k] != mod_after[k])
    print(f"  取模       : {mod_moved / len(keys):.1%} 的 key 换了节点")

    ch3 = ConsistentHash(["A", "B", "C"])
    ch4 = ConsistentHash(["A", "B", "C", "D"])
    ch_moved = sum(1 for k in keys if ch3.get_node(k) != ch4.get_node(k))
    print(f"  一致性哈希 : {ch_moved / len(keys):.1%} 的 key 换了节点")
```

运行：

```bash
python code/distributed/lesson03_load_balancing.py
```

观察输出：

```text
实验一：轮询，6 个请求分给 3 个实例
  请求 0 -> 实例 A
  请求 1 -> 实例 B
  请求 2 -> 实例 C
  请求 3 -> 实例 A
  请求 4 -> 实例 B
  请求 5 -> 实例 C

实验二：3 节点扩到 4 节点，重映射比例对比
  取模       : 75.0% 的 key 换了节点
  一致性哈希 : 25.1% 的 key 换了节点
```

**结论：取模扩一个节点，75% 的 key 全部搬家；一致性哈希只搬约 25%。** 这就是一致性哈希存在的意义——把"节点增减"的代价从"全局重排"降到了"局部迁移"。

> 示例说明：这里没有真实网络，负载均衡和分片都是**用代码模拟**的，但"取模导致大量重映射""一致性哈希只影响局部"是真实的算法行为。真实系统里，一致性哈希用于 Redis 分片、分库分表时，遵循的就是同样的原理。

## 10. 面试高频考点

- **四种负载均衡算法**：轮询 / 随机 / 加权轮询 / 最小连接，能说清各自适用场景（性能一致 vs 性能不均 vs 耗时差异大）。
- **取模 vs 一致性哈希**：取模的致命问题是"节点数一变全局重排"；一致性哈希把影响缩小到局部。
- **一致性哈希三要素**：哈希环、顺时针找最近节点、虚拟节点。
- **虚拟节点**：解决节点少时的数据倾斜。
- **常见追问**：
  - "为什么取模扩缩容会大量失效？"（映射结果和节点总数强绑定。）
  - "一致性哈希就完美吗？"（不是，节点少会倾斜，所以要虚拟节点；它仍可能局部不均。）
  - "Redis 分片 / 分库分表为什么用一致性哈希？"（扩缩容少迁移、少失效，防雪崩。）
