# 第7课:分布式一致性与业务操作

前面几课讲的超时、重试、限流、熔断，都是"调用"层面的可靠性。这一课回到"数据"层面：一个业务操作横跨数据库、缓存、消息系统时，怎么保证一致性。核心结论是——**单库事务跨不出去，跨服务只能靠"最终一致 + 补偿 + 幂等"**，以及异步任务靠"状态机 + 租约"来保证可靠。

这一课是机制课，内容较重，重点是建立四个心智模型：

1. 单库事务有边界，跨服务没有"一个事务管到底"这回事；
2. 分布式事务方案（2PC/TCC/Saga/本地消息表）是在"强一致"和"最终一致"之间做取舍；
3. 异步任务靠"状态机 + 租约"来追踪和恢复，否则任务会永远卡在 running；
4. 恢复重跑必须配幂等，因为"崩溃"无法通知任何人。

**学习目标：**

1. 能说明单库事务的边界，解释为什么跨服务不能共享本地事务；
2. 能对比 2PC、TCC、Saga、本地消息表四种分布式事务方案的取舍；
3. 能解释 Outbox Pattern 和补偿任务的基本思路；
4. 能画出任务状态机（queued / running / succeeded / failed）；
5. 能解释任务为什么可能永久停留在 running，以及租约超时、心跳、扫描如何恢复；
6. 能说明恢复重跑为什么必须配幂等，以及外部副作用的处理；
7. 能区分库存/余额（强一致）和展示数据（最终一致）的场景差异。

## 1. 单库事务的边界

先明确单库事务能做什么、不能做什么。

### 1.1 单库事务：一次操作内部的原子性

```text
下单 = 写订单表 + 写订单明细表 + 扣库存表
    -> 单库事务保证：这三步要么全成功、要么全回滚（ACID 的原子性）
```

这是数据库第 9 课的内容：事务把多个写操作变成一个"原子单元"。

### 1.2 边界：只在同一个数据库内有效

```text
单库事务的边界 = 一个数据库实例
    -> 跨库、跨 Redis、跨消息系统、跨服务，事务就管不到了
```

```text
写 MySQL（订单库） + 发 Redis + 发消息队列 + 调模型服务
    -> 这些不在一个数据库里
    -> 没有一个"事务"能一起回滚它们
```

这就是单库事务的边界：**它只管一个库内部，跨出去就失效。**

## 2. 跨服务不能共享事务

### 2.1 为什么

事务是数据库引擎内部维护的（锁、undo log、redo log），它只能管"自己这个库"里的数据。跨服务的操作，是**两个独立进程、两个独立数据库**，它们之间没有共享的"事务上下文"：

```text
服务 A 的事务提交了（订单写成功）
    -> 服务 A 调用服务 B（发通知）
    -> 服务 B 失败了
    -> 服务 A 的事务已经提交，无法"跨服务回滚"
```

### 2.2 后果

```text
本地事务提交成功，下游调用失败
    -> 状态不一致：订单写了，但通知没发出去
```

这是分布式系统里最典型的"跨服务一致性问题"。它的解法不是"找一个更强大的事务"，而是**接受最终一致，用补偿去修正**（第 3、4 节）。

## 3. 分布式事务方案

既然没有"一个事务管到底"，业界就发明了几种"分布式事务"方案。它们本质上是在**强一致**和**最终一致**之间做取舍。这一节只做概念级对比，不写完整协议。

### 3.1 2PC（两阶段提交）

```text
阶段一 prepare：协调者问所有参与者"你们能不能提交？"
    -> 所有参与者都回答"能"
阶段二 commit：协调者让所有参与者一起提交
    -> 有一个回答"不能"，就全部回滚
```

**强一致**，看起来完美，但代价很大：

- **阻塞**：prepare 阶段，参与者要锁住资源等协调者通知；
- **单点**：协调者挂了，整个事务卡住；
- **性能差**：多次网络往返。

实际生产很少用，只在一致性要求极高、并发很低的场景（如某些金融核心系统）。

### 3.2 TCC（Try-Confirm-Cancel）

把业务操作拆成三个阶段，由**业务自己实现**：

```text
Try     ：预留资源（冻结库存、冻结余额）
Confirm ：确认，真正执行
Cancel  ：取消，释放预留
```

```text
下单扣库存：
    Try    -> 冻结 1 件库存
    Confirm -> 真正扣掉 1 件
    Cancel  -> 释放冻结的 1 件
```

比 2PC 好的是"预留"不阻塞，但**业务侵入大**——每个操作都要写 Try/Confirm/Cancel 三套逻辑。适合资金、库存这类"有预留语义"的场景。

### 3.3 Saga

把长事务拆成**多个本地事务**，每个本地事务配一个**补偿操作**，失败时逆序补偿：

```text
Saga：A -> B -> C（三步，各自是独立的本地事务）
    -> C 失败
    -> 逆序补偿：补偿 C -> 补偿 B -> 补偿 A
```

```text
下单 -> 扣库存 -> 扣款
    -> 扣款失败
    -> 补偿：恢复库存 -> 取消订单
```

**最终一致**，适合长流程、跨多个服务的场景。关键是"每个步骤都要有对应的补偿逻辑"。

### 3.4 本地消息表

业务操作和"发消息"放在**同一个本地事务**里，靠消息表保证可靠：

```text
本地事务：
    1. 写业务表（下单）
    2. 写消息表（outbox，记录"要发的消息"）
    -> 一起提交
后台进程：
    读消息表，发送消息，发送成功标记已发送
```

**最终一致**，实现简单，是工程上最常用、最推荐的方案。它保证"业务成功"和"消息发送"不丢——消息先落库，再异步发。

### 3.5 一张对比表（面试直接口述）

| 方案 | 一致性 | 代价 | 适用场景 |
| --- | --- | --- | --- |
| 2PC | 强一致 | 阻塞、性能差、协调者单点 | 一致性要求极高、低并发（少用） |
| TCC | 强一致（预留） | 业务侵入大、实现复杂 | 资金、库存等有预留语义 |
| Saga | 最终一致 | 每步要写补偿 | 长流程、跨多个服务 |
| 本地消息表 | 最终一致 | 维护消息表 + 后台发送 | 异步解耦、可靠消息（最常用） |

> 面试要点：不要背四种方案的名字，要能说清"强一致 vs 最终一致、代价、什么时候用哪个"。多数业务选**最终一致 + 本地消息表**。

## 4. Outbox 与补偿

### 4.1 Outbox Pattern（发件箱模式）

本地消息表方案的正式名字是 **Outbox Pattern**：

```text
业务表 + outbox 表，同一个事务写入
    -> 后台读 outbox 表，逐条发送消息
    -> 发送成功，标记/删除
    -> 发送失败，保留，重试
```

它解决的核心问题是：**"业务成功"和"消息发送"这两个动作，怎么保证不丢消息。**

```text
反例：先写业务，再直接发消息
    -> 业务提交了，发消息失败 -> 消息丢了
正解：业务和消息一起落库（outbox），再异步发 -> 消息不丢
```

### 4.2 补偿任务

最终一致靠的不是"回滚"，而是**补偿**：

```text
补偿 = 再执行一个反向操作，抵消之前的影响
    -> 下单成功、扣款失败：补偿就是"取消订单"
    -> 不是"把数据库回滚到之前的状态"，而是"再做一步让它回到业务上正确"
```

```text
回滚：撤销（像没发生过）
补偿：抵消（做一个反向操作，但可能有痕迹）
```

## 5. 任务状态机

异步任务（Worker 后台处理）要可靠，第一步是**把任务状态显式地记录成状态机**。

### 5.1 四个基本状态

```text
queued ──> running ──> succeeded
              └──────> failed
```

| 状态 | 含义 |
| --- | --- |
| queued | 任务已创建，等待被领取 |
| running | 某个 Worker 正在处理 |
| succeeded | 处理成功 |
| failed | 处理失败（可重试或进死信） |

### 5.2 为什么必须持久化状态

```text
进程崩溃后，如果状态只在内存里
    -> 你不知道哪些任务处理完了、哪些处理到一半
    -> 无法恢复
```

状态落库后，即使 Worker 崩溃，重启后也能从数据库读到"哪些任务还在 running / queued"，继续处理。

## 6. 任务执行租约

状态机解决了"追踪"，但还有一个致命问题：**Worker 崩溃时，任务会永远卡在 running**。

### 6.1 问题：崩溃无法通知任何人

```text
Worker 领取任务 -> 状态改成 running
    -> Worker 执行业务成功
    -> Worker 在"更新状态为 succeeded"之前崩溃
    -> 任务永远停留在 running，没人再处理它
```

**崩溃是"无声"的**——Worker 不会优雅地说一句"我要死了，任务还给你"。所以必须有机制，能发现"这个 running 的 Worker 其实已经死了"。

### 6.2 租约（Lease）

**租约**：任务被领取时，设置一个过期时间。这个过期时间就是"这个 Worker 负责这个任务的期限"。

```text
Worker 领取任务：
    -> 状态 = running
    -> 租约过期时间 = now + 30 秒（"我保证 30 秒内处理完"）
```

### 6.3 心跳续约

任务处理时间长于租约时，Worker 要**定期续租**：

```text
Worker 还在处理，每隔 10 秒续一次租约
    -> 租约过期时间往后延
    -> 证明"我还活着"
```

### 6.4 超时扫描与重新领取

后台一个"扫描器"定期检查：

```text
扫描器发现：某个任务状态 = running，且租约已过期
    -> 判定：原 Worker 已经死了（否则它会续租）
    -> 把这个任务重新放回 queued，让别的 Worker 领取
```

```text
租约超时 -> 重新领取 -> 重跑
```

这就是"任务为什么不会永远卡在 running"的完整答案：**租约 + 心跳 + 超时扫描**。

## 7. 恢复重跑与幂等

租约过期重新领取后，任务会被**重跑**。但这里有个陷阱：

### 7.1 重跑可能重复执行

```text
Worker A 领取任务，业务其实已经执行成功了（比如已经扣款了）
    -> 但还没更新状态，就崩溃了
    -> 租约过期，Worker B 重新领取
    -> Worker B 重跑 -> 又扣了一次款！
```

### 7.2 重跑必须配幂等

```text
恢复重跑的前提：业务操作是幂等的（或用幂等键去重）
    -> Worker B 重跑时，发现"这个任务的业务其实已经执行过了"
    -> 跳过重复执行，直接标记成功
```

### 7.3 无法安全重放的外部副作用

有些副作用**不能重放**：

```text
发邮件：重跑会发两次邮件
扣款：重跑会扣两次款
调第三方：重跑会调两次
```

处理原则：

```text
1. 能幂等的，用幂等键去重（扣款用 request_id 去重）；
2. 不能幂等的，先落库记录"已执行"，重跑时检查记录，跳过；
3. 实在无法避免重放的，把它放到"能重试且幂等"的环节之后。
```

## 8. 一致性的场景差异

不是所有数据都需要强一致。按"错了的代价"区分：

| 数据类型 | 一致性要求 | 例子 | 为什么 |
| --- | --- | --- | --- |
| 库存、余额 | 强一致 | 不能超卖、不能透支 | 错了就是资损 |
| 订单状态 | 较强一致 | 已支付 / 未支付 | 影响业务流转 |
| 展示数据 | 最终一致 | 点赞数、浏览量 | 差几个无所谓 |

```text
库存：100 件，不能卖出 101 件 -> 强一致（条件更新、乐观锁，见 database 第 11 课）
点赞数：显示 1000 还是 1003 -> 最终一致即可
```

**判断标准：数据错了，代价是什么？代价大就强一致，代价小就最终一致。**

## 9. 运行课程代码

这一节用一个最小场景，演示"任务卡在 running → 租约超时 → 重新领取 → 幂等拦截"的完整流程。只需要 Python 标准库。

把下面的代码保存为 `code/distributed/lesson07_task_lease.py`：

```python
# code/distributed/lesson07_task_lease.py
# 演示任务租约：Worker 崩溃导致任务卡在 running，租约超时后恢复，幂等防重复。
#  # 后是注释，实际执行时不输入。

import time

# 任务表（用字典模拟）：task_id -> {status, lease_expire}
tasks = {"task_1": {"status": "queued", "lease_expire": 0.0}}

# 幂等：记录"业务是否已经真正执行过"（比如是否已经扣款）
business_done = set()


def worker_a_crashes():
    """模拟 Worker A：领取任务、执行业务，但在更新状态前崩溃。"""
    tasks["task_1"]["status"] = "running"
    tasks["task_1"]["lease_expire"] = time.time() + 3  # 租约 3 秒
    business_done.add("task_1")  # 业务其实已经执行了（比如已经扣款了）
    print("[Worker A] 领取 task_1，执行业务成功（已扣款）")
    print("[Worker A] 在更新任务状态前崩溃！task_1 卡在 running")
    # 注意：这里没有把 status 更新成 succeeded，模拟崩溃


def scan_and_reclaim(now):
    """超时扫描：发现租约过期的 running 任务，重新放回可领取。"""
    for task_id, task in tasks.items():
        if task["status"] == "running" and now > task["lease_expire"]:
            print(f"[超时扫描] {task_id} 租约过期，判定原 Worker 已死，重新可领取")
            task["status"] = "queued"
            return task_id
    return None


def worker_b_reclaim(task_id):
    """模拟 Worker B：重新领取并重跑，靠幂等避免重复执行。"""
    if task_id in business_done:
        print(f"[Worker B] {task_id} 业务已执行过（幂等拦截），直接标记成功")
    else:
        business_done.add(task_id)
        print(f"[Worker B] {task_id} 首次执行业务")
    tasks[task_id]["status"] = "succeeded"
    print(f"[Worker B] {task_id} -> succeeded")


if __name__ == "__main__":
    worker_a_crashes()
    print()
    time.sleep(3.5)  # 等待租约（3 秒）过期
    task_id = scan_and_reclaim(time.time())
    if task_id:
        worker_b_reclaim(task_id)
```

运行：

```bash
python code/distributed/lesson07_task_lease.py
```

观察输出：

```text
[Worker A] 领取 task_1，执行业务成功（已扣款）
[Worker A] 在更新任务状态前崩溃！task_1 卡在 running

[超时扫描] task_1 租约过期，判定原 Worker 已死，重新可领取
[Worker B] task_1 业务已执行过（幂等拦截），直接标记成功
[Worker B] task_1 -> succeeded
```

**结论：Worker A 崩溃导致 task_1 卡在 running；3 秒后租约过期，超时扫描判定 A 已死、重新领取；Worker B 重跑时靠幂等拦截，发现业务已执行过，跳过重复扣款，直接标记成功。** 这就是"任务状态持久化 + 租约 + 幂等"三者配合，保证长任务可靠追踪与恢复的完整机制。

> 示例说明：Worker A"崩溃"是**模拟**的（没有真实 kill 进程），但"租约过期判定 Worker 死亡""重跑时用幂等拦截避免重复执行"是真实的任务调度逻辑。真实框架（如 Celery、分布式任务队列）的租约/超时恢复就是这个模型。

## 12. 面试高频考点

- **单库事务的边界**：事务管一个库内部，跨服务没有共享事务。
- **分布式事务对比**：2PC（强一致、阻塞、单点）、TCC（预留、业务侵入）、Saga（补偿、长流程）、本地消息表（最终一致、最常用）。
- **Outbox / 补偿**：业务和消息同事务落库，后台发送；最终一致靠补偿。
- **任务租约三件套**：租约（过期时间）+ 心跳（续租）+ 超时扫描（重新领取），解决"任务卡在 running"。
- **恢复重跑 vs 幂等**：重跑必须配幂等，否则重复扣款。
- **一致性场景差异**：库存/余额强一致，展示数据最终一致，判断标准是"错了的代价"。
- **常见追问**：
  - "跨服务怎么保证一致性？"（没有强事务，用最终一致 + Outbox/补偿 + 幂等。）
  - "任务一直 running 怎么办？"（租约过期 + 超时扫描重新领取，重跑配幂等。）
