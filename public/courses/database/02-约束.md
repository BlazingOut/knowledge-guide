# 数据库约束

> 《02-表结构、数据类型》解决了表和字段的类型。这一课解决另一件事：哪些规则应该由数据库强制保证？
>
> 主键拒绝重复，唯一约束拒绝重复，外键拒绝“指向不存在的用户”，CHECK 拒绝越界值。本课用 `users` 和 `orders` 两张表把约束讲清楚。
>
> 本课只讲约束本身；数据的增删改在第 4 课，事务和锁在第 9~11 课。

**学习目标：**

1. 能区分主键、唯一约束、`NOT NULL`、`DEFAULT`、外键、`CHECK` 各自保证什么；
2. 能说清代理主键和业务主键的区别，以及为什么通常选代理主键；
3. 能用 `users` 和 `orders` 两张表讲清外键的引用完整性：插入、删除、更新时数据库分别拒绝什么；
4. 能说清 `ON DELETE` / `ON UPDATE` 的 `RESTRICT`、`CASCADE`、`SET NULL` 怎么选；
5. 能说明数据库约束与应用校验如何分工。

## 一、这一课要解决什么问题

上一课把字段类型选对了，数据库仍然无法保证业务规则：

```text
email 可能重复
必填字段可能被写成 NULL
订单可能指向不存在的用户
价格可能是负数
```

这些规则由**约束（constraint）**强制。一句话定义：

> 约束是数据库在写入时强制执行的规则，拒绝不合法的数据。

本课用两张表贯穿：`users`（用户主表）和 `orders`（订单表）。订单通过 `user_id` 指向用户，主键、唯一约束、外键都用这张关系演示。

## 二、主键 PRIMARY KEY

上一课建表时见过 `PRIMARY KEY (id)`，它的机制是：

```text
主键：唯一标识一行，一张表只能有一个，不能为 NULL
```

- 单字段主键：`PRIMARY KEY (id)`；
- 多个字段共同作为主键叫**联合主键**：`PRIMARY KEY (user_id, tenant_id)`；
- 主键列通常是自增 `id`（`AUTO_INCREMENT` 在《02-表结构、数据类型》的数值类型讲过）。

**代理主键（surrogate key）** 是数据库生成、与业务无关的编号，如自增 `id`；**业务主键（natural key）** 是业务上本身就唯一的值，如邮箱、订单号。邮箱、手机号可能随业务变化、受外部系统影响，所以通常用稳定的代理主键，业务字段用唯一约束保证不重复（下一节）。

## 三、唯一约束 UNIQUE

```text
唯一约束：保证字段或字段组合不重复，一张表可以有多个
```

```sql
CREATE TABLE users (
    id BIGINT NOT NULL AUTO_INCREMENT,
    email VARCHAR(255) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_users_email (email)
) ENGINE = InnoDB;
```

字段组合不能重复时使用联合唯一约束：

```sql
UNIQUE KEY uk_user_tenant (user_id, tenant_id)
```

主键和唯一约束的区别（面试常问）：

| 对比 | 主键 | 唯一约束 |
|---|---|---|
| 数量 | 一张表只能有一个 | 一张表可以有多个 |
| NULL | 不允许 | 允许（MySQL 中可存在多个 NULL） |
| 用途 | 唯一标识一行 | 保证某个字段或组合不重复 |

## 四、NOT NULL 和 DEFAULT

```sql
status VARCHAR(20) NOT NULL DEFAULT 'pending',
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
```

- `NOT NULL`：该列不允许保存 NULL；
- `DEFAULT 值`：插入时不提供该列，则使用默认值。

插入时不提供字段，数据库使用默认值；显式写入 `NULL` 则是另一回事：

```sql
-- 使用默认值
INSERT INTO orders (user_id, total_amount)
VALUES (1, 99.00);

-- 显式写 NULL；NOT NULL 字段通常会报错
INSERT INTO orders (user_id, status, total_amount)
VALUES (1, NULL, 99.00);
```

默认值适合表达自然的初始状态，例如订单默认为 `pending`。不要用空字符串默认值掩盖调用方漏传参数。

## 五、外键 FOREIGN KEY：两张表讲引用完整性

订单的 `user_id` 应该指向真实存在的用户。先建用户表（被引用，父表）：

```sql
CREATE TABLE users (
    id BIGINT NOT NULL AUTO_INCREMENT,
    email VARCHAR(255) NOT NULL,
    PRIMARY KEY (id)
) ENGINE = InnoDB;
```

再建订单表（引用，子表）：

```sql
CREATE TABLE orders (
    id BIGINT NOT NULL AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    total_amount DECIMAL(12, 2) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT fk_orders_user
        FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE = InnoDB;
```

**外键（foreign key）** 由数据库保证引用完整性，强制三件事：

| 操作 | 数据库行为 |
|---|---|
| 插入订单时 `user_id` 指向不存在的用户 | 拒绝插入，防止“孤儿订单” |
| 删除仍被订单引用的用户 | 按 `ON DELETE` 策略处理，默认拒绝 |
| 修改 `users.id` 且订单引用它 | 按 `ON UPDATE` 策略处理 |

例如插入一个不存在的用户 ID：

```sql
INSERT INTO orders (user_id, total_amount)
VALUES (999, 99.00);
```

会得到外键约束失败的错误：`Cannot add or update a child row: a foreign key constraint fails`——订单没有指向真实存在的用户，数据库拒绝写入。

`ON DELETE` / `ON UPDATE` 的常见选项：

| 选项 | 含义 | 说明 |
|---|---|---|
| `RESTRICT` | 存在引用时拒绝父表操作 | 默认行为，最安全 |
| `CASCADE` | 父记录变化时自动处理子记录 | 删除用户会连带删除订单，慎用 |
| `SET NULL` | 父记录删除后把子字段设为 NULL | 要求子字段允许 NULL |
| `NO ACTION` | 和 `RESTRICT` 相同 | 标准 SQL 的说法 |

示例：

```sql
ON DELETE RESTRICT
ON UPDATE CASCADE
```

什么时候用外键？单库业务可以考虑使用；复杂分布式系统可能由应用和数据治理流程保证关系。重点是明确责任边界，不能两边都不保证。

## 六、CHECK 约束

MySQL 8 可以使用 `CHECK` 拒绝明显不合法的值：

```sql
CREATE TABLE products (
    id BIGINT NOT NULL AUTO_INCREMENT,
    price DECIMAL(12, 2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    CONSTRAINT chk_products_price CHECK (price >= 0),
    CONSTRAINT chk_products_stock CHECK (stock >= 0)
) ENGINE = InnoDB;
```

`CHECK` 能拒绝明显不合法的数据（价格不能为负），但不能替代事务和复杂业务逻辑。库存扣减是否安全，还要结合并发控制（第 10、11 课）。

## 七、数据库约束与应用校验的分工

多个应用、脚本和人工操作都可能写入数据库。明显的唯一性、非空性和引用关系应尽量由数据库保证，应用校验负责业务规则：

```text
数据库约束：拒绝重复、缺失、悬空引用、越界值
应用校验：业务规则，如“订单金额要大于运费”这类组合判断
```

原则：**能在数据库层表达的完整性规则就交给数据库**，应用校验做业务规则；不能两边都不保证。

## 八、完整的业务表设计

下面的示例把《02-表结构、数据类型》的类型和本课的约束串起来：

```sql
CREATE DATABASE IF NOT EXISTS mysql_course
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

USE mysql_course;

CREATE TABLE users (
    id BIGINT NOT NULL AUTO_INCREMENT,
    email VARCHAR(255) NOT NULL,
    nickname VARCHAR(100) NOT NULL,
    phone VARCHAR(30) NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_users_email (email)
) ENGINE = InnoDB;

CREATE TABLE products (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(12, 2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT chk_products_price CHECK (price >= 0),
    CONSTRAINT chk_products_stock CHECK (stock >= 0)
) ENGINE = InnoDB;

CREATE TABLE orders (
    id BIGINT NOT NULL AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    order_no VARCHAR(40) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'pending',
    total_amount DECIMAL(12, 2) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_orders_order_no (order_no),
    CONSTRAINT fk_orders_user
        FOREIGN KEY (user_id) REFERENCES users(id),
    CONSTRAINT chk_orders_amount CHECK (total_amount >= 0)
) ENGINE = InnoDB;
```

设计解释：

```text
id：稳定的代理主键
email：业务上不能重复，因此有唯一约束
phone：可以暂时没有，因此允许 NULL
price / total_amount：需要精确计算，因此使用 DECIMAL
stock：不应为负，因此有 CHECK；并发扣减还需要事务
status：有自然的初始值 pending
user_id：外键引用 users.id，避免订单指向不存在的用户
order_no：对外的业务订单号，用唯一约束保证不重复，不替代内部主键
```

## 九、常见错误

### 1. 用业务字段直接作为主键

邮箱、手机号、订单号可能变化，也可能受多租户和外部系统影响。通常使用内部主键，再给业务字段添加唯一约束。

### 2. 只依赖应用检查，不设置数据库约束

多个应用、脚本和人工操作都可能写入数据库。明显的唯一性、非空性和引用关系应尽量由数据库保证。

### 3. 误以为 UNIQUE 列不能有多个 NULL

MySQL 中唯一约束允许多个 NULL（NULL 之间不相等）。如果业务要求“邮箱要么唯一、要么缺失”，不能只靠唯一约束，需要结合其他手段。

### 4. 外键 CASCADE 用得随意

`ON DELETE CASCADE` 删除父记录会连带删除子记录，批量清理时可能一次删掉远超预期的数据。默认用 `RESTRICT`，需要级联时明确说明业务含义。

### 5. 把 CHECK 当成并发控制

`CHECK (stock >= 0)` 只拒绝明显非法值，不能阻止两个事务同时把库存扣成负数。并发正确性要靠事务和锁（第 9~11 课）。

## 十、面试回答模板

### 题目：主键和唯一索引有什么区别？

> 主键用于唯一标识表中的一行，一张表通常只有一个主键，主键列不能为 NULL；唯一索引用于保证某个字段或字段组合不重复，一张表可以有多个唯一索引，且允许 NULL。实际设计中常用稳定 ID 作为主键，再给邮箱、订单号等业务字段建立唯一约束。

### 题目：外键生产环境一定要使用吗？

> 外键用于保证引用完整性，例如订单的 user_id 必须指向存在的用户。它能防止孤儿数据，但也会增加迁移、批量导入和分库分表的复杂度。单库业务可以让数据库保证关系；复杂系统也可以由应用负责，但必须明确责任边界。

### 题目：代理主键和业务主键怎么选？

> 代理主键是数据库生成、与业务无关的编号（如自增 id），稳定、简短，适合做主键；业务主键是业务上本来就唯一的值（如邮箱、订单号），可能随业务变化、受外部系统影响。通常用稳定的代理主键，业务字段用唯一约束保证不重复。

### 题目：ON DELETE CASCADE 有什么风险？

> CASCADE 会在删除父记录时自动删除子记录，批量清理时可能一次删除远超预期的数据，还可能让多个表之间形成连锁删除。默认应该用 RESTRICT 显式拒绝，需要级联时必须明确业务含义并评估影响范围。
