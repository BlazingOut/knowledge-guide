# 第2课:表结构、数据类型

> 第一课讲了 MySQL 的连接、会话、数据库和存储引擎。这一课落到表和字段：如何创建、查看和修改表，每个字段应该使用什么类型？
>
> 主键、外键、`CHECK` 等约束规则拆到下一篇《02-约束》，本课先解决表和字段类型。

## 一、这一课要解决什么问题

如果把所有字段都定义成字符串，虽然容易开始，但数据库无法很好地帮助我们保证数据正确：

```text
price 可能被写成无法计算的文本
created_at 可能出现格式不一致的日期
age 可能被写成 'twenty' 这种无法排序的值
```

合理的字段设计应该把业务含义表达出来：

```text
字段含义
    -> 选择合适的数据类型
    -> 规定是否允许 NULL、设置默认值
    -> 添加主键、唯一约束、外键等约束
    -> 由数据库拒绝明显不合法的数据
```

最后一步的“约束”（主键、唯一、外键、`CHECK`）在下一篇《02-约束》展开，本课只认识它们在建表语句中的位置。

## 二、创建和查看表

### 1. 建表语句的结构

第 1 课只讲了数据库这一层，本课开始建表。`CREATE TABLE` 的常用结构：

```sql
CREATE TABLE [IF NOT EXISTS] 表名 (
    字段名 数据类型 [NOT NULL] [DEFAULT 默认值] [AUTO_INCREMENT],
    ...,
    [PRIMARY KEY (字段)],
    [UNIQUE KEY 名称 (字段)],
    [CONSTRAINT 名称 FOREIGN KEY (字段) REFERENCES 表(字段)],
    [CONSTRAINT 名称 CHECK (条件)]
) ENGINE = InnoDB;
```

建表语句由三部分组成：

| 部分 | 作用 | 说明 |
|---|---|---|
| 表名 | 表的名称 | 先 `USE` 选定数据库，或写 `库名.表名` |
| 字段定义 | 每列的属性 | 数据类型、是否 `NOT NULL`、默认值、自增 |
| 约束与引擎 | 表的规则 | 主键、唯一、外键、CHECK（机制见《02-约束》）；`ENGINE` 选引擎 |

字段定义里出现的修饰词，先给一句话定义，详细机制在对应小节：

| 修饰词 / 关键字 | 一句话定义 | 详细介绍 |
|---|---|---|
| `NOT NULL` | 该列不允许保存 NULL | 见《02-约束》 |
| `NULL` | 该列允许保存 NULL（“NULL”指没有值；列默认可空，写出是显式声明） | 见“NULL、空字符串和零” |
| `DEFAULT 值` | 插入时不提供该列，则使用默认值 | 见《02-约束》 |
| `AUTO_INCREMENT` | 自增：插入时数据库自动生成递增编号，通常用于主键 | 见“数值类型” |
| `PRIMARY KEY` | 主键：唯一标识一行，一张表只能有一个，不能为 NULL | 见《02-约束》 |

一个最小示例：

```sql
CREATE TABLE products (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(200) NOT NULL,
    PRIMARY KEY (id)
) ENGINE = InnoDB;
```

其中 `ENGINE = InnoDB` 是第 1 课讲的存储引擎概念在这里落地：每张表选定自己的引擎，不写时用服务器默认（MySQL 8 默认 InnoDB）。正式项目建议明确写出引擎、字符集和关键约束，避免依赖环境默认配置造成差异。

### 2. 查看当前数据库中的表

```sql
SHOW TABLES;
SHOW TABLES FROM shop;
```

第一行查看当前会话所在数据库的表，第二行查看指定数据库的表。

### 3. 查看字段结构

```sql
DESCRIBE users;
SHOW COLUMNS FROM users;
```

两者等价，输出一张字段清单：

```text
Field       Type          Null  Key  Default            Extra
id          bigint        NO    PRI  NULL               auto_increment
email       varchar(255)  NO         NULL
nickname    varchar(100)  NO         NULL
created_at  datetime      NO         CURRENT_TIMESTAMP
```

| 列 | 含义 |
|---|---|
| `Field` | 字段名称 |
| `Type` | 数据类型 |
| `Null` | 是否允许 `NULL` |
| `Key` | 是否参与主键或索引（`PRI` 表示主键） |
| `Default` | 默认值 |
| `Extra` | 额外属性，例如 `auto_increment` |

### 4. 查看完整建表语句

```sql
SHOW CREATE TABLE users;
```

它返回 MySQL 当前实际保存的完整建表定义，比 `DESCRIBE` 更全：字段、主键和索引、存储引擎、字符集、排序规则、表注释。排查"代码里的建表语句"和"数据库实际结构"不一致时，`SHOW CREATE TABLE` 最可靠。

## 三、修改表结构

### 1. 添加字段

```sql
ALTER TABLE users
ADD COLUMN phone VARCHAR(30) NULL;
```

`ADD COLUMN` 修改的是表结构，不是给已有数据增加一条记录。这里的 `VARCHAR(30) NULL` 表示新列允许为空：手机号可以暂时没有。`NULL` 表示“没有值”，和 `NOT NULL`（不允许为空）相对，两者的完整讨论见“NULL、空字符串和零”一节。

### 2. 修改字段定义

```sql
ALTER TABLE users
MODIFY COLUMN nickname VARCHAR(120) NOT NULL;
```

修改字段时要小心：已有数据不符合新定义时操作可能失败；修改导致截断或转换时可能造成数据问题。

### 3. 修改字段名称

MySQL 8 中可以用：

```sql
ALTER TABLE users
RENAME COLUMN nickname TO display_name;
```

字段重命名不止影响数据库，还会影响应用 SQL、ORM 映射、报表查询、索引和约束引用、数据同步任务。修改表结构前要搜索代码和调用方，而不是只验证 SQL 能否执行。

### 4. 删除字段

```sql
ALTER TABLE users
DROP COLUMN phone;
```

删除字段可能造成数据丢失，也可能破坏应用读取。生产环境通常采用"先停止使用—确认无读写—再删除"的步骤。

### 5. 修改表名和删除表

```sql
RENAME TABLE orders TO user_orders;
DROP TABLE user_orders;
```

表名修改会影响应用 SQL、权限、监控和备份脚本；`DROP TABLE` 删除表和数据，是破坏性操作。

边界：`ALTER TABLE` 成功不代表业务没有影响。大表上的 `ALTER TABLE` 可能涉及锁、临时表和线上变更风险，第 15 课会展开。修改表结构前，把"谁在读、谁在写、谁在同步"检查清楚，比执行 SQL 本身更重要。

## 四、表名、字段名与关键字命名

表名和字段名建议使用**小写字母加下划线**的蛇形命名，例如 `users`、`order_items`、`created_at`。命名要点：

- 表名用复数名词，字段名用单数名词，表达一致；
- 字段名能看出含义：`user_id` 而不是 `uid` 或 `id2`；
- 不要用 MySQL 保留字直接做表名或字段名。`ORDER`、`GROUP`、`SELECT` 都是关键字，直接写会报语法错误：

```sql
-- 错误：ORDER 是关键字
CREATE TABLE order (...);

-- 正确：改名
CREATE TABLE orders (...);
```

- 确实需要用特殊名称时，可以用反引号包裹：

```sql
CREATE TABLE `select` (id BIGINT PRIMARY KEY);
```

反引号能解决语法冲突，但会带来持续的维护成本，正式项目优先"改名"而不是"加反引号"。

## 五、数值类型

### 1. 整数类型

常见整数类型包括：

| 类型 | 存储空间 | 取值范围 | 典型用途 |
|---|---:|---|---|
| `TINYINT` | 1 字节 | -128 ~ 127 | 状态、标记 |
| `SMALLINT` | 2 字节 | -32768 ~ 32767 | 较小范围的数量 |
| `INT` | 4 字节 | 约 -21 亿 ~ 21 亿 | 普通数量 |
| `BIGINT` | 8 字节 | 极大范围 | 用户 ID、订单 ID |

面试常问：用户 ID 为什么用 `BIGINT` 而不是 `INT`？`INT` 上限约 21 亿，对增长很快的业务表不够安全，且建成后扩类型代价大，所以 ID 列习惯直接选 `BIGINT`。

示例：

```sql
CREATE TABLE products (
    id BIGINT NOT NULL AUTO_INCREMENT,
    stock INT NOT NULL,
    is_enabled TINYINT NOT NULL DEFAULT 1,
    PRIMARY KEY (id)
) ENGINE = InnoDB;
```

如果字段不应该保存负数，可以使用 `UNSIGNED`：

```sql
stock INT UNSIGNED NOT NULL DEFAULT 0
```

但 `UNSIGNED` 只能限制取值范围，不能代替并发控制。两个事务仍可能同时读取并扣减库存，后续课程会用条件更新和锁解决这个问题。

### 2. 自增主键

**自增（`AUTO_INCREMENT`）**：插入时不提供该列的值，数据库自动生成一个比现有值更大的编号，通常配合主键使用，形成“自增主键”。声明方式是把主键列标记为 `AUTO_INCREMENT`：

```sql
id BIGINT NOT NULL AUTO_INCREMENT
```

“比现有值更大”是指比当前表中该列已有的最大值更大，这个判断由 MySQL 为每张表维护的**内部计数器**完成：插入时取计数器当前值分配给新行，再把计数器加一。

- 空表第一次插入，分配的值从 `1` 开始（默认起始值）；
- 表中已有最大值为 `5` 时，下一条分配 `6`；
- 计数器不会因为删除最大行而自动回退；`TRUNCATE TABLE` 清空整张表才会把它重置回 `1`。

插入时可以省略 `id`：

```sql
INSERT INTO users (email)
VALUES ('alice@example.com');
```

自增值只保证“生成的编号越来越大”，不保证连续、不保证反映创建时间，也不保证事务回滚后复用——分配给回滚事务的值不会被收回，所以会出现空洞。不要把自增 ID 当成连续的业务订单号。

### 3. 金额使用 `DECIMAL`

金额通常使用定点数：

```sql
total_amount DECIMAL(12, 2) NOT NULL
```

`DECIMAL(12, 2)` 表示总共最多 12 位数字，其中小数点后 2 位。金额不推荐使用 `FLOAT` 或 `DOUBLE`，因为浮点数采用二进制近似表示，连续计算可能出现误差。

```text
金额：DECIMAL
允许近似的测量数据或科学计算：FLOAT / DOUBLE
```

`DECIMAL` 只解决存储精度，退款、扣款、货币单位和并发一致性仍需要业务规则与事务保证。

如果应用使用 JavaScript，还要注意 `BIGINT` 可能超过 `Number` 的安全整数范围。可以让驱动返回字符串、使用 `BigInt`，或在 JSON 中以字符串传输 ID。

## 六、字符串类型

### 1. `CHAR`、`VARCHAR` 和 `TEXT`

三种类型按“长度是否固定”区分，声明里的 `n` 表示允许的**字符数**（不是字节数）：

```text
CHAR(n)：定长字符串，固定占满 n 个字符，不足部分补空格
VARCHAR(n)：变长字符串，最多 n 个字符，按实际内容占用空间
TEXT：变长字符串，没有 n，用于较长文本
```

`VARCHAR(n)` 里的 `n` 是**上限**而不是固定占用：`VARCHAR(255)` 存 `'abc'`，只占用 3 个字符的空间；`CHAR(255)` 则固定占用 255 个字符的空间（不足补空格）。字符数不等于字节数：`utf8mb4` 下大部分汉字占 3 字节，但 `VARCHAR(100)` 仍允许存 100 个字符。

`CHAR` 和 `VARCHAR` 最容易混淆，它们的存储方式不同：

| 对比 | `CHAR(n)` | `VARCHAR(n)` |
|---|---|---|
| 存储方式 | 固定占用 n 个字符的空间，不足部分补空格 | 只占用实际长度，另加 1~2 字节记录长度 |
| 空间 | 固定、浪费较多 | 更省空间 |
| 速度 | 长度固定，处理较快 | 长度可变，略慢 |
| 典型用途 | 长度固定的值：状态码、哈希值等 | 长度不定的业务字符串：邮箱、昵称、地址 |

面试常问：**什么时候用 `CHAR` 而不是 `VARCHAR`？** 判断标准是值本身长度是否固定且格式统一——定长的状态码、订单号、哈希值适合 `CHAR`；长度变化的业务字段用 `VARCHAR` 更省空间。

常见业务字段通常使用 `VARCHAR`：

```sql
email VARCHAR(255) NOT NULL,
phone VARCHAR(30),
status VARCHAR(20) NOT NULL
```

`TEXT` 用于较长文本，但它在默认值、索引、排序和查询设计方面有更多限制，邮箱、状态、手机号和用户名等字段应优先选择明确长度的 `VARCHAR`。不要把“不确定长度”当成用 `TEXT` 的理由。

### 2. 字符集和排序规则

**字符集（charset）** 决定字符如何编码和保存，**排序规则（collation）** 决定字符如何比较和排序。表可以继承数据库的默认值，也可以像第 1 课建库那样在建表时显式指定：

```sql
CREATE TABLE users (
    id BIGINT NOT NULL AUTO_INCREMENT,
    nickname VARCHAR(100) NOT NULL,
    PRIMARY KEY (id)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci;
```

常见字符集：

| 字符集 | 含义 | 说明 |
|---|---|---|
| `utf8mb4` | 完整的 UTF-8 编码 | 支持全部 Unicode 字符，包括 emoji；正式项目首选 |
| `utf8` / `utf8mb3` | 旧的 UTF-8 实现 | 最多 3 字节，遇到生僻字或 emoji 会报错或截断 |
| `latin1` | 单字节字符集 | 只能表示西欧字符，存中文会出现乱码 |
| `gbk` | 简体中文字符集 | 中文兼容性好，但字符集混杂时容易出问题 |

MySQL 8 的默认字符集是 `utf8mb4`。**名字叫 `utf8` 的字符集并不是完整的 UTF-8**，这是历史遗留：MySQL 的 `utf8` 最多 3 字节，`utf8mb4` 才是完整的 4 字节实现。

排序规则决定字符串怎么比较、是否区分大小写。常见选项：

| 排序规则 | 含义 | 说明 |
|---|---|---|
| `utf8mb4_0900_ai_ci` | 不区分重音、不区分大小写 | MySQL 8 默认，业务通常首选 |
| `utf8mb4_general_ci` | 不区分大小写，比较宽松 | 旧版本常见默认 |
| `utf8mb4_unicode_ci` | 按 Unicode 规则比较，不区分大小写 | 比 general 更符合标准 |
| `utf8mb4_bin` | 按字节二进制比较 | 区分大小写、区分重音，适合精确匹配 |

后缀拆解：`ai` 表示不区分重音（accent insensitive），`ci` 表示不区分大小写（case insensitive），`bin` 表示二进制比较。排序规则直接影响比较结果和唯一性判断：在 `ci` 下 `'A'` 和 `'a'` 算同一个值，在 `bin` 下算两个。因此邮箱、用户名等字段是否区分大小写要结合业务决定，选错会在比较和唯一约束上出现意外行为。

## 七、日期和时间类型

日期时间类型按“保存的精度”区分：`DATE` 只保存日期，`TIME` 只保存时间，`DATETIME` 保存日期和时间，`TIMESTAMP` 保存时间戳并按会话时区转换：

| 类型 | 保存内容 | 范围 | 适合场景 |
|---|---|---|---|
| `DATE` | 日期 | `1000-01-01` ~ `9999-12-31` | 生日、账期等只有日期的值 |
| `TIME` | 时间 | 约 `-838:59:59` ~ `838:59:59` | 营业时间等只有时间的值 |
| `DATETIME` | 日期和时间 | `1000-01-01 00:00:00` ~ `9999-12-31 23:59:59` | 业务日期时间 |
| `TIMESTAMP` | 日期和时间 | `1970-01-01 00:00:01` ~ `2038-01-19` | 时间戳语义或自动转换的值 |

面试最常见的对比是 `DATETIME` 和 `TIMESTAMP`：

| 对比 | `DATETIME` | `TIMESTAMP` |
|---|---|---|
| 存储 | 8 字节，范围到 9999 年 | 4 字节，范围到 2038 年 |
| 时区 | 保存字面值，不做时区转换 | 按会话时区自动转换 |
| 典型用途 | 业务时间，如订单创建时间 | 系统级时间戳 |

`TIMESTAMP` 会按会话时区转成 UTC 存储、读回再转回，`DATETIME` 存什么就是什么。跨时区系统如果全部用 `DATETIME` 保存“本地时间”，不同时区看到的含义会不一致；常见做法是数据库和服务内部统一使用 UTC，展示时再按用户时区转换。

订单通常需要完整时间：

```sql
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
```

查询某一天的数据，推荐使用左闭右开范围：

```sql
SELECT *
FROM orders
WHERE created_at >= '2026-01-01 00:00:00'
  AND created_at <  '2026-01-02 00:00:00';
```

不要把结束时间写死成 `23:59:59`，因为字段可能包含更高精度的时间部分。左闭右开也便于连续拼接时间区间。

自动更新时间的经典写法是 `created_at` / `updated_at` 组合：

```sql
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP
```

这段用到了两个语法：

| 语法 | 含义 | 触发时机 |
|---|---|---|
| `DEFAULT CURRENT_TIMESTAMP` | 插入时不提供该列，默认值是“插入那一刻的时间” | 只在 INSERT 时 |
| `ON UPDATE CURRENT_TIMESTAMP` | 该行被 UPDATE 时，自动把该列刷新为“更新那一刻的时间” | 每次 UPDATE 影响该行时 |

合起来就是最常见的模式：`created_at` 只在插入时写入一次，`updated_at` 每次修改自动刷新，应用代码里不需要手动赋值。MySQL 8 中 `DATETIME` 和 `TIMESTAMP` 都支持这两个语法。

## 八、`NULL`、空字符串和零

```text
NULL：没有值、未知或不适用
''：长度为 0 的字符串
0：数值零
```

错误写法：

```sql
WHERE phone = NULL
```

正确写法：

```sql
WHERE phone IS NULL
```

`NULL` 表示未知，和其他值比较通常不会得到 TRUE。字段是否允许 `NULL` 应由业务含义决定：注册时必填的邮箱使用 `NOT NULL`，可以稍后补充的手机号可以允许 `NULL`。

## 九、回顾：为什么字段类型重要

学完前面各节，再看本课开头的问题就有答案了。数据类型不仅限制输入格式，还会影响存储空间、比较和排序、算术计算、索引大小以及应用程序读取后的类型。例如，下面两个字段都可能表示年龄：

```sql
age VARCHAR(10)
age INT UNSIGNED
```

使用 `VARCHAR` 时，数据库可能保存 `'18'`、`'twenty'`、`'-1'` 和空字符串；使用整数类型时，数据库能够按数字比较，并拒绝一部分不符合类型的输入（见“数值类型”）。

字段设计可以按这个顺序走一遍：

```text
字段含义
    -> 选择合适的数据类型
    -> 规定是否允许 NULL、设置默认值
    -> 添加主键、唯一约束、外键（机制见《02-约束》）
```

约束负责的“拒绝重复、拒绝悬空引用、拒绝越界值”由《02-约束》展开；本课要记住的是：字段类型决定数据库如何看待这条数据。

## 十、常见错误

### 1. 所有字段都使用 `VARCHAR`

这样会丢失数据库对数值、日期和范围的理解，也容易导致比较、排序和索引行为不符合预期。

### 2. 金额使用 `FLOAT`

浮点数适合近似计算，不适合作为需要精确结算的金额类型。金额通常使用 `DECIMAL`，并明确货币单位和小数位。

### 3. 把空字符串当成 NULL

`WHERE phone = ''` 不能匹配 `NULL`。判断没有值要使用 `IS NULL`。

### 4. 把 `AUTO_INCREMENT` 当成连续编号

回滚、并发插入和批量操作都可能让自增值出现间隙。它的职责是生成主键，不是生成连续业务序号。

## 十二、面试回答模板

### 题目：金额为什么使用 DECIMAL，而不是 FLOAT？

> `FLOAT` 和 `DOUBLE` 是近似浮点数，部分十进制小数无法精确表示，连续计算可能出现误差。金额需要可控的十进制精度，所以通常使用 `DECIMAL`，并根据业务确定总位数和小数位。`DECIMAL` 只能解决存储精度，扣款、退款和并发一致性还需要事务和业务规则保证。

### 题目：NULL 和空字符串有什么区别？

> NULL 表示没有值、未知或不适用，空字符串是长度为零的字符串，二者业务含义和 SQL 判断方式不同。判断 NULL 要使用 `IS NULL`，不能使用 `= NULL`。字段是否允许 NULL 应由业务含义决定。

### 题目：CHAR 和 VARCHAR 有什么区别？

> CHAR 是定长字符串，固定占用 n 个字符的空间，不足部分补空格；VARCHAR 是变长字符串，只占用实际长度，另加 1~2 字节记录长度。长度固定、格式统一的值（如状态码、哈希值）适合 CHAR；长度不定的业务字符串（如邮箱、昵称）用 VARCHAR 更省空间。

### 题目：DATETIME 和 TIMESTAMP 有什么区别？

> DATETIME 保存字面日期时间，范围到 9999 年，不做时区转换；TIMESTAMP 按会话时区转成 UTC 存储、读回再转回，范围到 2038 年。业务时间通常用 DATETIME，并约定库内统一存 UTC；需要自动时区转换的系统级时间戳适合 TIMESTAMP。
