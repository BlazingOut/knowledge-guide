# 第13课:业务并发控制：下单、库存与账户

> 前两课分别学习了事务、隔离级别、MVCC 和锁。这一课把这些机制放进真实业务：两个人同时买最后一件商品、两个请求同时扣款、同一个请求重复提交时，如何保证结果正确。
>
> 本课完整可执行示例见 `code/database/11-concurrency-business.sql`。涉及并发的部分需要多个独立数据库会话，课文中的代码片段用于解释方案，实验时严格记录两个会话的操作顺序。

**学习目标：**

1. 能解释"先查库存再更新"为什么会超卖；
2. 能用条件更新和影响行数实现基础扣库存；
3. 能用 `SELECT ... FOR UPDATE` 设计悲观锁方案；
4. 能用版本号设计乐观锁方案；
5. 能说出三种方案各自的适用场景和代价；
6. 能设计下单、扣款的事务边界，解释幂等键和有限重试；
7. 能通过统一访问顺序降低死锁概率。

## 一、业务并发问题：超卖、重复扣款与重复提交

假设商品库存为 1，同时来了两个购买请求。

如果应用这样处理：

```text
请求 A：SELECT stock，读到 1
请求 B：SELECT stock，读到 1
请求 A：应用计算 1 - 1 = 0
请求 B：应用计算 1 - 1 = 0
请求 A：UPDATE stock = 0
请求 B：UPDATE stock = 0
```

数据库最后看到库存是 0，但实际可能创建了两笔订单。这就是超卖：库存字段的最终值看起来没有明显错误，业务事实却已经错误。

并发控制要保证的不只是“最终数字不为负”，还要保证：

```text
库存扣减和订单创建的关系正确
同一份库存不能被成功消费两次
重复请求不会重复扣款或重复下单
失败时不会只完成半个业务流程
```

## 二、方案一：当前读加悲观锁

**悲观锁（pessimistic lock）**：假设冲突可能发生，在修改前先锁住目标记录。做法是在事务中用当前读（`SELECT ... FOR UPDATE`）锁住商品行，再检查、修改、提交：

```sql
START TRANSACTION;

SELECT stock
FROM products
WHERE id = 1
FOR UPDATE;

-- 应用检查 stock > 0

UPDATE products
SET stock = stock - 1
WHERE id = 1;

INSERT INTO orders (user_id, order_no, total_amount)
VALUES (1, 'ORD-LOCK-001', 199.00);

COMMIT;
```

两个请求同时执行时：

```text
事务 A：FOR UPDATE 锁住商品 1
事务 B：FOR UPDATE 等待 A
事务 A：扣减库存、创建订单、提交
事务 B：读取最新库存 0，判断不足并回滚
```

### 1. 悲观锁适合什么场景

适合：

- 热点库存；
- 账户余额；
- 冲突概率较高的更新；
- 必须读取最新值后再做复杂判断的流程。

代价是：

- 需要等待锁；
- 事务持锁时间越长，并发越差；
- 访问顺序不一致可能造成死锁；
- 热点行可能成为吞吐瓶颈。

事务中不要在 `FOR UPDATE` 后调用远程服务或等待用户操作，否则锁会被持有很久。

## 三、方案二：带条件的原子更新

**条件更新（conditional update）**：把"检查条件"和"修改"放进同一条 SQL，由数据库原子地完成。例如检查 `stock > 0` 的同时扣减：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 1
  AND stock > 0;
```

然后检查影响行数：

```text
影响行数 = 1：扣减成功
影响行数 = 0：库存不足或商品不存在
```

这条 SQL 的关键是：

```text
判断 stock > 0
    和
执行 stock = stock - 1
```

由数据库在同一个原子更新中完成，而不是让应用读取后再计算。

### 1. 为什么它能避免简单超卖

`UPDATE` 属于当前读（第 12 课），会对命中的行加锁。两个请求同时执行时：

```text
请求 A：条件成立，stock 1 -> 0，影响 1 行
请求 B：等 A 提交后重新判断，stock > 0 不成立，影响 0 行
```

最终只有一个请求扣减成功——协调由数据库的锁和条件判断完成，应用只需要检查影响行数。

### 2. 条件更新的边界

条件更新很适合简单的库存或余额判断，但它不自动解决整个下单流程：

- 订单插入是否和库存扣减属于同一个事务；
- 失败后是否回滚库存；
- 重试是否会重复创建订单；
- 价格是否需要保存下单时快照；
- 订单号是否具有唯一约束。

如果库存扣减成功后订单插入失败，就需要事务把库存修改回滚，或者设计补偿流程。

### 3. 实验：两个会话同时购买最后一件商品

初始 `stock = 1`。会话 A 先执行条件更新，暂不提交：

```sql
START TRANSACTION;
UPDATE products
SET stock = stock - 1
WHERE id = 1
  AND stock > 0;
-- 影响 1 行，暂不提交
```

会话 B 执行同一条条件更新：

```sql
START TRANSACTION;
UPDATE products
SET stock = stock - 1
WHERE id = 1
  AND stock > 0;
-- 此时 B 等待 A 释放锁
```

会话 A 提交：

```sql
COMMIT;
```

B 的 UPDATE 继续执行，重新判断条件后影响 0 行，应用据此判断库存不足。用同样的方式可以验证另外两种方案：悲观锁方案里 B 卡在 `FOR UPDATE` 等待；乐观锁方案里 B 的 UPDATE 因版本号不匹配影响 0 行。核心都是验证"只有符合条件的操作成功"。

## 四、方案三：版本号乐观锁

**乐观锁（optimistic lock）**：假设冲突不常发生，读取时不提前加锁，更新时检查版本是否仍然是原来的值，如果被其他事务改过就拒绝本次更新。

表中增加版本号：

```sql
ALTER TABLE products
ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
```

应用先读取：

```text
stock = 10
version = 7
```

更新时带上旧版本：

```sql
UPDATE products
SET stock = stock - 1,
    version = version + 1
WHERE id = 1
  AND version = 7
  AND stock > 0;
```

判断影响行数：

```text
影响行数 = 1：版本匹配，更新成功
影响行数 = 0：版本已被其他事务修改，或者库存不足
```

如果影响行数为 0，应用可以重新读取并重试，也可以直接提示冲突。

### 1. 乐观锁适合什么场景

适合：

- 写冲突较少；
- 读多写少；
- 不希望长时间持有数据库锁；
- 可以接受冲突后重试或提示用户。

代价是：

- 冲突时需要重新读取和重试；
- 高冲突场景可能不断失败；
- 重试必须有次数上限；
- 应用必须正确处理影响行数。

## 五、三种方案如何选择

不要简单回答“乐观锁更好”或“悲观锁更安全”：

```text
冲突少、重试成本可接受 -> 乐观锁或条件更新
冲突多、必须先读取最新值 -> 悲观锁
逻辑简单，只需扣减条件 -> 条件更新
复杂业务判断和多步修改 -> 当前读 + 事务
```

三种方案对照：

| 方案 | 核心思路 | 适合 | 主要代价 |
|---|---|---|---|
| 悲观锁（FOR UPDATE） | 修改前先锁住记录 | 冲突多、必须读最新值做复杂判断 | 等待锁，持锁时间越长并发越差 |
| 条件更新（UPDATE ... WHERE stock > 0） | 检查与修改在同一条 SQL 原子完成 | 逻辑简单的扣减、扣款 | 不能承载复杂多步判断 |
| 版本号乐观锁 | 更新时校验版本未被其他事务修改 | 冲突少、读多写少 | 冲突时需要重试或提示失败 |

选择时还要考虑：

- 热点记录的并发量；
- 事务持续时间；
- 失败重试的成本；
- 是否允许短暂冲突；
- 是否需要严格的操作顺序；
- 业务能否做到幂等。

## 六、下单事务的边界

一个简化的下单流程：

```text
校验请求和幂等键
    -> 开启事务
    -> 检查并扣减库存
    -> 创建订单
    -> 创建订单明细
    -> 提交事务
```

数据库事务中应该包含真正需要原子性的数据库操作：

```sql
START TRANSACTION;

UPDATE products
SET stock = stock - 1
WHERE id = 1
  AND stock > 0;

-- 应用检查影响行数

INSERT INTO orders (user_id, order_no, status, total_amount)
VALUES (1, 'ORD-001', 'pending', 199.00);

-- 还可以插入 order_items

COMMIT;
```

不要在事务中执行：

- 调用支付平台；
- 调用库存之外的远程服务；
- 发送无法撤回的消息；
- 等待用户确认；
- 大量无关查询。

如果业务需要在数据库提交后发送消息，应考虑事务消息、Outbox 等更完整的可靠投递方案，本课只建立事务边界意识。

## 七、账户扣款

账户余额不能只依赖应用读取：

```text
错误流程：读取余额 -> 应用判断 -> 应用计算 -> 写回余额
```

可以使用条件更新：

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 1
  AND balance >= 100;
```

影响行数为 1 表示扣款成功，0 表示余额不足或账户不存在。

如果还需要写入支付记录：

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1
  AND balance >= 100;

-- 检查影响行数

INSERT INTO account_transactions (account_id, amount, type)
VALUES (1, 100, 'debit');

COMMIT;
```

必须保证账户余额变化和流水记录的事务关系，否则可能出现余额扣了但流水不存在，或流水存在但余额未扣的情况。

## 八、幂等和重复请求

数据库事务解决一次业务操作的原子性，但网络重试可能让同一个请求到达多次：

```text
客户端发送下单请求
    -> 服务端已经提交
    -> 网络超时，客户端没有收到响应
    -> 客户端重试同一个请求
```

如果没有幂等设计，可能创建两笔订单。**幂等（idempotent）**：同一个操作执行多次和执行一次的效果相同。**幂等键（idempotency key）**：客户端为一次业务操作生成的唯一标识，服务端用它识别"这是同一次操作的重试，不是新操作"。

常见做法是给请求设置业务幂等键：

```sql
CREATE TABLE order_requests (
    id BIGINT NOT NULL AUTO_INCREMENT,
    request_id VARCHAR(64) NOT NULL,
    order_id BIGINT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_requests_request_id (request_id)
) ENGINE = InnoDB;
```

同一个 `request_id` 只能成功登记一次。重复请求收到唯一键冲突后，应查询第一次请求的结果并返回，而不是再次执行扣库存。

幂等设计通常由几部分共同组成：

```text
业务请求 ID 唯一约束
    -> 事务中的状态记录
    -> 数据库条件更新
    -> 重试次数和退避
    -> 可查询的最终结果
```

## 九、死锁与业务访问顺序

转账或批量扣库存时，如果不同事务访问资源的顺序不同，可能产生死锁：

```text
事务 A：先锁账户 1，再锁账户 2
事务 B：先锁账户 2，再锁账户 1
```

降低风险的方法是统一顺序，例如按照账户 ID 从小到大加锁：

```text
先锁 id 较小的账户
再锁 id 较大的账户
```

即使统一了顺序，也不能保证复杂系统永远没有死锁。应用仍应捕获死锁错误并进行有限、幂等重试。

## 十、常见错误

- 先 SELECT，再由应用计算，最后 UPDATE；
- 只判断库存最终是否为负，不检查订单数量；
- 条件更新成功后，订单插入失败却不回滚；
- 在持锁事务中调用远程服务；
- 发生冲突后无限重试；
- 没有给业务订单号或请求 ID 加唯一约束；
- 把数据库事务误认为跨服务、跨消息队列的分布式事务；
- 不同业务流程以相反顺序访问相同资源。

## 十一、面试回答模板

### 题目：如何避免库存超卖？

> 简单场景可以使用带条件的原子更新：`UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0`，再根据影响行数判断是否成功。需要读取最新库存进行复杂判断时，在事务中使用 `SELECT ... FOR UPDATE`。也可以通过版本号实现乐观锁。无论选择哪种方式，库存扣减、订单创建和订单明细都要设计正确的事务边界，并处理幂等和重试。

### 题目：乐观锁和悲观锁怎么选？

> 冲突较少、读多写少且可以接受重试时，使用版本号或条件更新的乐观方案；冲突频繁、必须读取最新值并连续执行多步修改时，使用当前读和悲观锁。选择还要结合热点程度、事务长度、重试成本和业务幂等性，不能只比较锁本身。

### 题目：为什么扣库存成功后还要检查影响行数？

> 条件更新即使语句执行没有报错，也可能因为库存不足或记录不存在而影响 0 行。影响行数是业务判断扣减是否真正成功的依据。如果不检查就继续创建订单，可能产生没有库存保障的订单。

### 题目：如何避免重复扣款或重复下单？

> 网络重试会让同一个请求到达多次，所以要给请求设计幂等键：客户端生成唯一 request_id，服务端在带唯一约束的幂等表里登记；重复请求触发唯一键冲突时，查询第一次请求的结果并返回，而不是再次执行扣款。配合影响行数判断和事务边界，保证余额扣减、流水记录和结果返回一致。重试必须有次数上限、带退避，并且每次重试都携带同一个幂等键。
