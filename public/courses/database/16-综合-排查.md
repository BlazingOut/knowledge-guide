# 综合-排查：常见故障与排查方法

> 前面 12 课学的是"正常情况下的 MySQL"：怎么写、怎么查、怎么优化、怎么加锁。这一篇讲"出问题时怎么办"：线上变慢、卡住、连接不上，怎么从现象一步步定位到证据。
>
> 排查不是背命令，而是建立"现象 -> 证据 -> 原因 -> 验证"的闭环。本篇按故障类型组织，每类都标明串联的前课知识点。只读排查示例见 `code/database/16-online-troubleshooting.sql`。

**学习目标：**

1. 能按"确认范围 -> 收集只读证据 -> 缩小 -> 处理 -> 验证"的流程排查线上异常；
2. 能排查连接失败和连接数耗尽（串联第 1 课连接池）；
3. 能区分长事务、锁等待和死锁，并给出定位步骤（串联第 9、10 课）；
4. 能排查慢查询和执行计划变化（串联第 8 课）；
5. 能处理磁盘空间不足（串联第 14、15 课）；
6. 能说明 MDL 和大表 DDL 的线上风险（串联第 2 课 ALTER）。

## 一、通用排查流程

遇到数据库异常，先建立现象和范围，不要上来就 kill 连接或改配置：

```text
确认影响范围
    -> 判断是连接、性能、锁、复制还是数据问题
    -> 收集只读证据
    -> 缩小到具体 SQL、事务或资源
    -> 采取可回滚的处理
    -> 验证恢复并记录原因
```

常用只读检查：

```sql
SHOW PROCESSLIST;
SHOW FULL PROCESSLIST;
SHOW GLOBAL STATUS;
SHOW GLOBAL VARIABLES;
SHOW ENGINE INNODB STATUS;
```

具体线上权限和监控系统可能不同。排查时不要一上来就 kill 连接、删日志或修改全局配置。

## 二、连接失败和连接数耗尽

（串联第 1 课：连接池、账号权限）

### 1. 连接失败

按层次检查：

```text
网络是否可达
    -> 主机和端口是否正确
    -> MySQL 服务是否运行
    -> 账号密码是否正确
    -> 账号来源是否被允许
    -> 数据库是否存在
    -> 连接池配置是否正确
```

不要看到"连接失败"就判断是数据库挂了——也可能是应用配置、网络策略或连接池耗尽。第 1 课讲过连接池的作用和"不是越大越好"，这里就是它的线上版。

### 2. 连接数耗尽

查看连接相关配置和状态：

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
```

常见原因：连接池配置过大、应用实例数量增加后总连接数超限、连接泄漏、长事务长期占用连接、慢 SQL 导致连接迟迟不能归还。

提高 `max_connections` 不是唯一解决方案：连接数增大也会增加数据库内存和调度压力，应该先查清连接来源和生命周期（第 15 课监控指标）。

## 三、长事务、锁等待与死锁

（串联第 9 课事务/隔离级别、第 10 课 MVCC/锁）

### 1. 长事务

长事务可能同时带来：

- 锁持有时间长；
- undo log 无法及时清理（第 12 课讲过 undo 的清理依赖）；
- 其他事务等待；
- 连接池可用连接减少。

排查时要关联事务、线程、业务请求和最后一次提交时间，而不是只看一条慢 SQL。

### 2. 锁等待

可以结合：

```sql
SHOW PROCESSLIST;

SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
```

重点确认：谁持有锁、谁在等待、等待哪张表和哪棵索引、事务开始多久、是否因为缺少索引扩大了锁范围（第 10 课讲过锁范围和索引的关系）、是否可以安全结束阻塞事务。

### 3. 死锁

最近一次死锁信息：

```sql
SHOW ENGINE INNODB STATUS;
```

解决重点不是永远消灭死锁（第 10 课讲过死锁是互相等待的必然产物），而是：统一访问顺序、缩短事务、补充合适索引、捕获错误并有限重试、重试必须保证幂等（第 11 课）。

## 四、慢查询与执行计划变化

（串联第 8 课 EXPLAIN）

SQL 变慢时，先拿到真实 SQL、参数和执行计划：

```sql
EXPLAIN
SELECT id, order_no, created_at
FROM orders
WHERE user_id = 1
  AND status = 'paid'
ORDER BY created_at DESC
LIMIT 20;
```

比较历史上正常的计划和当前计划，关注：

- `key` 是否变化；
- `type` 是否从索引访问变为全表扫描；
- `rows` 是否明显增加；
- 是否出现额外排序或临时表；
- 数据量和分布是否变化；
- **是否其实是在等待锁，而不是执行计划慢**——先排除锁（本节三），再做查询优化。

优化后要同时验证：返回结果是否正确、平均耗时和尾延迟是否改善、写入成本是否增加、是否影响其他查询、新索引是否需要长期维护。

## 五、磁盘空间不足

（串联第 14 课归档、第 15 课监控与容量）

按"发现 -> 定位 -> 处理 -> 预防"处理：

```text
发现：磁盘使用率接近阈值（70%~85% 就告警，不是 99% 才处理），或写库开始报错
定位：数据文件、binlog、临时文件、慢查询日志各占多少
处理：归档冷数据（第 14 课）、清理过期 binlog（设保留策略）、扩容磁盘
预防：磁盘使用率告警、binlog 保留期、监控增长率
```

binlog 是常见的"隐形杀手"：写入量大时 binlog 增长快，要设置 `binlog_expire_logs_seconds` 等保留策略。

## 六、DDL、MDL 和大表变更

（串联第 2 课 ALTER TABLE、第 9 课长事务）

### 1. 什么是 MDL

元数据锁（MDL）保护表结构和访问之间的一致性：

```text
查询或事务正在使用表
    -> 表结构变更需要获得相应的元数据锁
    -> 如果前面有长事务，ALTER TABLE 可能等待
```

DDL 一旦排队，还可能让后续请求继续排队，形成线上阻塞扩大。

### 2. 大表加字段或索引

执行 `ALTER TABLE` 前需要考虑：表大小、MySQL 版本、DDL 算法、是否需要复制到临时表、MDL 等待、从库回放影响、回滚和恢复方案。

在线 DDL 可以降低部分变更的影响，但不等于所有变更都无锁、无成本。线上大表变更应先在接近真实数据规模的环境验证（第 14 课的归档也是先让表变小）。

## 七、分库分表只作边界认识

当单库单表无法满足容量、吞吐或隔离需求时，可能考虑读写分离、分库分表或分片。但它们会带来：

- 跨库事务复杂；
- JOIN 受限；
- 分页和排序复杂；
- 全局唯一 ID 设计；
- 数据迁移和扩容成本；
- 运维和排障复杂度。

分库分表不是索引优化的替代品。应先确认单表索引、SQL、归档（第 14 课）、硬件和查询模式已经合理，再评估架构扩展。

## 八、常见错误自查清单

- 发现连接数高就盲目调大 `max_connections`；
- 直接 kill 连接而不判断事务是否会造成业务影响；
- 只看 SQL 耗时，不区分执行慢和锁等待；
- 长事务阻塞 DDL 时直接重启数据库；
- 大表加索引前没有评估 MDL、复制和回滚；
- 用 `SHOW PROCESSLIST` 看到一条 SQL 就立刻杀掉，没有确认阻塞关系；
- 磁盘快满才处理，而不是设告警和保留策略。

## 十、面试回答模板

### 题目：线上 SQL 慢如何排查？

> 先拿真实 SQL、参数和执行计划，比较历史正常计划和当前计划：key 是否变化、type 是否从索引变成全表扫描、rows 是否增加、是否出现 filesort。同时要区分是执行计划慢还是在等锁——先看 SHOW PROCESSLIST 和锁等待，再做查询优化。优化后验证结果、耗时和写入成本。

### 题目：长事务有什么影响？

> 长事务持有锁的时间长，会让其他事务等待；占用连接不释放，减少连接池可用连接；undo log 无法及时清理；如果遇到 DDL，还会让 ALTER TABLE 等待 MDL，并让后续请求排队扩大阻塞。排查时要关联事务、线程和最后提交时间，而不是只看一条 SQL。

### 题目：MDL 是什么？

> 元数据锁用于保护表结构和访问之间的一致性。查询或事务正在使用表时，结构变更要获得相应的元数据锁；前面有长事务时，ALTER TABLE 可能一直等待，并让后续请求排队扩大阻塞。所以大表变更要评估长事务、DDL 算法，选择低峰期执行。

### 题目：线上执行 ALTER TABLE 需要注意什么？

> 要评估表大小、MySQL 版本、DDL 算法、元数据锁、长事务、主从复制和回滚方案。即使是在线 DDL，也不代表完全没有锁和资源消耗。应先在接近真实规模的环境验证，并选择低峰期和可观测的变更流程。

### 题目：磁盘空间不足怎么处理？

> 先定位谁占的空间：数据文件、binlog、临时文件还是日志；再按情况处理——归档冷数据、清理过期 binlog（并设保留策略）、扩容磁盘；最后设置磁盘使用率告警和监控增长率，避免再次打满。
