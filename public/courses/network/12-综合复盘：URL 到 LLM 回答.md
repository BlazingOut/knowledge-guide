# 第12课:综合复盘：URL 到 LLM 回答

## 本课范围

本课把网络课程的知识串成一次完整请求：

```text
客户端输入 URL
  -> DNS 解析
  -> 建立 TCP 连接
  -> TLS 握手
  -> 发送 HTTP 请求
  -> 反向代理或网关
  -> 后端服务
  -> 调用上游 LLM API
  -> 上游返回结果
  -> 后端返回或流式转发
  -> 客户端收到响应
```

课程代码只在本机启动两个 HTTP 服务，模拟：

```text
客户端 -> 网关服务 -> 上游服务
```

不访问公网，不需要真实模型 API Key，也不实现真实 DNS 和 TLS 握手。前面课程已经分别学习过这些机制，本课重点是串联、定位和解释。

## 学习目标

完成本课后，你应当能够：

- 从分层角度解释一次 HTTP 请求的完整路径；
- 区分客户端、网关、后端和上游模型服务的职责；
- 说明每一层可能出现的故障和现象；
- 用端口、日志、`curl` 和连接状态定位问题；
- 解释 `502`、`504`、连接拒绝和请求超时的区别；
- 画出一次 LLM API 调用的请求链路。

## 1. 完整请求链路

用户访问：

```text
https://api.example.test/chat
```

可以拆成下面的步骤。

### 第一步：解析 URL

客户端先拆分：

```text
协议：https
主机：api.example.test
路径：/chat
```

不同部分决定后续处理方式：

- `https`：需要 TLS；
- 主机名：需要 DNS 解析；
- `/chat`：由 HTTP 服务进行路由。

### 第二步：DNS 解析

客户端查询主机名对应的 IP：

```text
api.example.test
  -> DNS
  -> 203.0.113.10
```

解析结果可能来自：

- 浏览器缓存；
- 操作系统缓存；
- hosts 文件；
- 本地 DNS；
- 递归 DNS；
- 权威 DNS。

DNS 只负责把名字解析成地址，不负责确认目标端口上的 HTTP 服务一定正常。

### 第三步：选择路由和建立 TCP

操作系统根据目标 IP 查询路由，找到下一跳和网卡。HTTPS 默认连接 TCP 443 端口：

```text
客户端临时端口 -> 203.0.113.10:443
```

TCP 三次握手完成后，双方拥有一个可靠的字节流连接。

如果这里失败，HTTP 请求还没有发送，常见现象包括：

- `Connection refused`；
- `Connection timed out`；
- `No route to host`。

### 第四步：TLS 握手

HTTPS 在 TCP 连接上继续进行 TLS 握手：

```text
客户端 -> ClientHello
服务端 -> ServerHello、证书
客户端 -> 验证证书并完成密钥协商
双方   -> 使用对称密钥加密通信
```

TLS 阶段主要解决：

- 服务端身份验证；
- 机密性；
- 完整性。

如果证书域名不匹配、证书过期或信任链不完整，TCP 可能已经连接成功，但 HTTPS 仍然失败。

### 第五步：发送 HTTP 请求

TLS 建立后，客户端发送加密的 HTTP 请求：

```http
POST /chat HTTP/1.1
Host: api.example.test
Content-Type: application/json
Authorization: Bearer ...

{"message":"你好"}
```

服务端处理后返回状态码、响应头和响应体。

## 2. 加入网关和后端

真实部署中，公网地址通常不是应用进程直接监听的地址：

```text
客户端
  -> DNS
  -> 反向代理 / API 网关
  -> 后端服务
  -> 数据库或上游服务
```

网关可能负责：

- TLS 终止；
- 根据域名和路径路由；
- 认证；
- 限流；
- 请求体大小限制；
- 负载均衡；
- 超时；
- 日志和追踪。

因此客户端看到的 `502` 或 `504` 不一定来自后端应用本身，也可能是网关生成的。

## 3. 后端再次调用 LLM API

后端调用模型服务时，会重新经历一条网络链路：

```text
后端服务
  -> DNS 解析模型域名
  -> 建立 TCP
  -> TLS 握手
  -> 发送模型 HTTP 请求
  -> 模型服务处理
  -> 返回 JSON 或流式结果
```

所以一次用户请求可能包含两段独立的网络调用：

```text
客户端 -> 业务 API
业务 API -> LLM API
```

第一段成功不代表第二段一定成功。

后端需要把上游结果转换成自己的 API 契约：

```text
上游超时       -> 业务 API 返回 504
上游连接失败   -> 业务 API 返回 502
上游限流       -> 业务 API 返回 429 或统一错误
上游返回内容   -> 转换成自己的响应结构
```

## 4. 流式返回的完整路径

如果模型服务使用流式输出，链路变成：

```text
模型生成片段
  -> 上游返回片段
  -> 后端读取片段
  -> 后端立即转发
  -> 网关转发
  -> 客户端逐段显示
```

任何一层缓冲，都可能让客户端无法及时看到片段：

- 上游客户端没有使用流式读取；
- 后端等待完整结果才返回；
- 代理缓冲响应；
- 网关空闲超时；
- 客户端自身缓冲输出。

因此流式问题不能只看最后的 HTTP 状态码，要检查每一段是否实际产生和转发数据。

## 5. 课程示例

示例文件：

```text
code/network/12-end-to-end.py
```

示例启动两个本机 HTTP 服务：

```text
上游服务：127.0.0.1:9101
网关服务：127.0.0.1:9100
```

调用链：

```text
客户端 -> POST 127.0.0.1:9100/chat
       -> 网关转发到 127.0.0.1:9101/answer
       -> 上游返回 JSON
       -> 网关把响应转发给客户端
```

代码使用标准库：

- `http.server`：启动本地 HTTP 服务；
- `http.client`：发起 HTTP 请求；
- `threading`：同时运行网关和上游；
- `json`：编码和解析请求体。

## 7. 故障注入与排查

### 7.1 网关端口没有监听

停止程序后执行：

```bash
curl -v http://127.0.0.1:9100/chat
```

此时客户端无法建立 TCP 连接。排查重点是：

```bash
ss -lnt
```

Windows：

```powershell
Get-NetTCPConnection -LocalPort 9100
```

### 7.2 上游服务不可用

可以修改示例中的上游端口，使网关连接一个没有监听的端口，然后重新启动网关：

```text
网关 -> 上游连接失败
```

客户端会收到 `502`。这里 TCP 失败发生在网关到上游的链路，不是客户端到网关的链路。

### 7.3 路径错误

调用错误路径：

```bash
curl -v -X POST http://127.0.0.1:9100/wrong \
  -H "Content-Type: application/json" \
  -d '{"message":"你好"}'
```

网关进程仍然正常，端口也在监听，但 HTTP 路由不存在，因此返回 `404`。

这说明：

```text
TCP 能连接 != HTTP 路径一定正确
```

### 7.4 请求体格式错误

发送不是 JSON 的请求：

```bash
curl -v -X POST http://127.0.0.1:9100/chat \
  -H "Content-Type: application/json" \
  -d 'not-json'
```

示例代码会在解析请求体时失败。真实服务应在 HTTP 层或框架层处理输入校验，并返回稳定的 `400` 或 `422`，不要让异常直接暴露给客户端。

## 8. 一张故障定位表

| 现象 | 可能位置 | 第一批检查 |
| --- | --- | --- |
| 域名无法解析 | DNS | `dig`、`nslookup` |
| 连接被拒绝 | 目标端口没有监听或主动拒绝 | `ss`、`lsof` |
| 连接超时 | 路由、防火墙、代理或服务无响应 | `ip route`、`ping`、`curl` |
| TLS 验证失败 | 证书、域名或信任链 | `curl -v` |
| 返回 404 | HTTP 方法或路径错误 | `curl -v` |
| 返回 401/403 | 认证或授权 | 请求头和服务日志 |
| 返回 502 | 网关无法获得有效上游响应 | 网关到上游的连接日志 |
| 返回 504 | 网关等待上游超时 | 分段超时和上游耗时 |
| 状态码 200 但内容不完整 | 响应、代理或客户端读取 | 流式日志和响应头 |

## 9. 课程总结

一次请求不是一个函数调用，而是一条跨层链路：

```text
应用
  -> HTTP
  -> TLS
  -> TCP
  -> IP
  -> 链路
```

调用上游模型时，后端又成为新的客户端，重新经历：

```text
DNS -> TCP -> TLS -> HTTP -> 模型服务
```

排错时要先定位失败发生在哪一段，再选择对应工具。不要因为最终看到的是 `502`，就直接认为业务代码报错；也不要因为 `ping` 通，就认为应用接口一定正常。

## 11. 面试高频考点

### 11.1 输入 URL 后发生了什么？

建议按顺序回答：

```text
解析 URL
  -> DNS 获取 IP
  -> 根据路由选择下一跳
  -> TCP 三次握手
  -> HTTPS 进行 TLS 握手
  -> 发送 HTTP 请求
  -> 代理或网关转发
  -> 后端处理
  -> 可能继续调用数据库或上游 LLM
  -> 返回 HTTP 响应
  -> TCP/TLS/连接按协议保持或关闭
```

重点不是背出所有细节，而是说明每一步解决什么问题。

### 11.2 如何排查线上接口超时？

先判断客户端到网关是否建立连接，再逐段检查：

```text
客户端 -> 网关
网关 -> 后端
后端 -> 数据库或上游
```

结合连接超时、读取超时、总超时和服务端耗时日志定位。不要只增加总超时，否则可能掩盖真正的慢点。

### 11.3 为什么后端服务调用模型服务时要重新关注网络？

因为后端是新的 HTTP 客户端。它有自己的 DNS、代理、TLS、连接池、超时和重试配置。用户到后端成功，不代表后端到模型服务成功。

### 11.4 为什么错误状态码不能单独说明根因？

同一个 `502` 可能来自不同网关、不同上游连接阶段或应用主动转换。状态码只能提供分类线索，还需要结合请求链路、网关日志、后端日志和上游响应判断根因。

## 12. 综合练习

完成一个本机最小转发服务，要求：

1. 启动一个上游 HTTP 服务；
2. 启动一个网关服务；
3. 网关接收 JSON 请求并转发到上游；
4. 网关把上游状态码和响应体返回给客户端；
5. 为连接失败设置超时；
6. 记录客户端、网关和上游三段日志；
7. 人为制造错误地址、错误路径和上游停止三种故障；
8. 使用第 11 课的命令写出每种故障的定位过程。

完成后，应能用一张图说明：

```text
客户端 -> 网关 -> 上游服务
```

并在每条箭头旁写出可能失败的环节。
