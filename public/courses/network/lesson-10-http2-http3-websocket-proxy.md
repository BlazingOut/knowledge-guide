# 第十课：HTTP/2、HTTP/3、WebSocket 与代理网关

## 本课范围

前面已经学习了 HTTP/1.1、HTTPS、连接保持和流式响应。本课继续回答三个工程问题：

1. HTTP/2 和 HTTP/3 为什么要改变 HTTP 的传输方式？
2. WebSocket 和普通 HTTP 到底是什么关系？
3. 一个请求经过代理、负载均衡和网关时，谁负责什么？

本课以理解协议和工程角色为主，终端命令只用于观察本机或公开的课程服务，不编写额外 Python 代码。

本课不深入：

- HTTP/2 和 HTTP/3 的完整帧字段；
- QUIC 的拥塞控制源码；
- WebSocket 子协议和复杂聊天室实现；
- Nginx、Envoy 等代理软件的完整配置；
- Kubernetes Ingress 和云厂商网关；
- 生产环境的完整限流、熔断和服务治理系统。

## 学习目标

完成本课后，你应当能够：

- 说明 HTTP/1.1、HTTP/2 和 HTTP/3 的主要差异；
- 解释队头阻塞在不同层次上的含义；
- 说明 HTTP/2 多路复用和头部压缩解决什么问题；
- 解释 HTTP/3、QUIC 和 UDP 的关系；
- 区分 HTTP、WebSocket、正向代理和反向代理；
- 画出客户端、网关、后端和上游 LLM API 的调用链；
- 说明代理场景下超时、重试和流式响应为什么容易出问题。

## 1. HTTP/1.1 的限制

### 1.1 持久连接减少了重复握手

HTTP/1.0 中，一个请求可能对应一个 TCP 连接。HTTP/1.1 默认支持持久连接：

```text
建立 TCP 连接
  -> 请求 1 / 响应 1
  -> 请求 2 / 响应 2
  -> 请求 3 / 响应 3
  -> 关闭连接
```

这样可以减少 TCP 和 TLS 握手的次数。

### 1.2 管线化并没有成为主流解决方案

HTTP/1.1 曾经设计过管线化：客户端连续发送多个请求，不等待前一个响应。但服务端仍然需要按顺序返回响应，前面的慢响应可能挡住后面的响应。

因此浏览器和客户端通常使用多个 TCP 连接并行请求资源。这能提高吞吐，但会带来：

- 更多连接和握手；
- 更多内核和服务器资源；
- 连接数限制；
- TCP 层队头阻塞仍然存在。

### 1.3 HTTP/1.1 的队头阻塞

在一个 HTTP/1.1 连接中，如果前一个响应没有完成，后续响应可能无法顺利交付：

```text
请求 A -> 响应很慢
请求 B -> 已经准备好，但被 A 挡住
```

这就是应用层顺序造成的队头阻塞。

## 2. HTTP/2：一个连接中的多路复用

### 2.1 请求被拆成帧

HTTP/2 不再把一个完整请求或响应当作连接上的一段连续文本，而是拆成二进制帧。每个请求拥有自己的 Stream ID：

```text
TCP 连接
  -> Stream 1 的帧
  -> Stream 3 的帧
  -> Stream 1 的帧
  -> Stream 5 的帧
  -> Stream 3 的帧
```

不同请求的帧可以交错传输，这就是多路复用。

### 2.2 多路复用解决了什么

HTTP/2 可以在一个 TCP 连接中同时处理多个请求，减少：

- 重复 TCP 连接；
- 重复 TLS 握手；
- 浏览器对同一域名建立大量连接的需求。

请求 B 不必等待请求 A 的完整 HTTP 响应才开始传输自己的帧。

但要注意：HTTP/2 仍然建立在 TCP 之上。如果 TCP 丢失了一个数据包，TCP 需要按顺序恢复字节流，可能导致整个连接上的多个 Stream 一起等待。

这就是 HTTP/2 仍然存在的 TCP 层队头阻塞：

```text
HTTP/2 多个 Stream
        ↓
一个 TCP 字节流
        ↓
某个 TCP 数据包丢失
        ↓
整个连接等待重传
```

HTTP/2 解决了 HTTP/1.1 的请求排列问题，但没有消除 TCP 本身的顺序约束。

### 2.3 头部压缩

HTTP 请求中有很多重复头部，例如：

```text
User-Agent
Authorization
Cookie
Accept
```

HTTP/2 使用 HPACK 压缩头部，并维护双方共享的头部表。重复出现的头部可以用索引表示，减少传输字节。

头部压缩和响应体压缩不是一回事：

| 内容 | 作用 |
| --- | --- |
| HPACK | 压缩 HTTP 头部 |
| gzip、br | 压缩响应体 |

### 2.4 HTTP/2 服务端推送

HTTP/2 曾经支持服务端推送：服务端可以在客户端明确请求之前主动推送资源。但实际使用中缓存判断、资源选择和代理兼容性比较复杂，浏览器支持也发生变化。

面试中知道它的设计目标即可，不要把“HTTP/2 一定会主动推送资源”当成默认行为。

## 3. HTTP/3：基于 QUIC 的 HTTP

### 3.1 QUIC 运行在 UDP 之上

HTTP/3 的关系可以表示为：

```text
HTTP/3
  -> QUIC
      -> UDP
          -> IP
```

QUIC 使用 UDP 作为承载，但它不是“裸 UDP 发送 HTTP”。QUIC 在用户态实现了可靠传输、加密、连接管理和多路复用等能力。

### 3.2 HTTP/3 解决 TCP 层队头阻塞

QUIC 中不同 Stream 有相对独立的传输状态。某个 Stream 的数据包丢失时，通常不会像 TCP 那样阻塞所有 Stream：

```text
QUIC 连接
  -> Stream A：丢包，等待重传
  -> Stream B：继续接收
  -> Stream C：继续接收
```

这降低了一个数据流影响整条连接的范围。

### 3.3 连接迁移

TCP 连接通常与客户端 IP 和端口组合相关。移动设备从 Wi-Fi 切换到蜂窝网络时，IP 可能变化，TCP 连接容易断开。

QUIC 使用连接 ID 管理连接，允许在一定条件下进行连接迁移。这对移动网络和网络切换场景更友好。

### 3.4 QUIC 与 TLS

QUIC 从设计开始就集成 TLS 1.3。HTTP/3 的连接建立不应被理解为：

```text
先建立一个普通 UDP 连接
再额外建立 TLS
```

更准确的理解是：QUIC 的传输建立和加密握手紧密结合，减少建立安全连接所需的往返。

## 4. 三种 HTTP 版本对比

| 项目 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 传输基础 | TCP | TCP | QUIC/UDP |
| 数据形式 | 文本报文 | 二进制帧 | QUIC Stream 中的帧 |
| 多路复用 | 有限，通常依赖多个连接 | 一个 TCP 连接多个 Stream | 一个 QUIC 连接多个 Stream |
| 头部处理 | 重复传输较多 | HPACK | QPACK |
| TCP 队头阻塞 | 存在 | 仍然存在 | 不使用 TCP |
| 部署复杂度 | 最低 | 需要 HTTP/2 支持 | 需要 UDP 和 HTTP/3 支持 |

选择协议不是简单的“版本越高越好”。还需要考虑：

- 客户端支持；
- CDN、代理和网关支持；
- 网络环境；
- 连接数量和延迟；
- 排障工具是否完善。

## 5. WebSocket 与 HTTP 的关系

### 5.1 WebSocket 解决什么问题

普通 HTTP 的典型模式是：

```text
客户端请求 -> 服务端响应
```

WebSocket 建立后，客户端和服务端都可以主动发送消息：

```text
客户端 <-> 长连接 <-> 服务端
```

适合：

- 在线聊天；
- 实时通知；
- 协同编辑；
- 实时仪表盘；
- 游戏状态同步。

### 5.2 WebSocket 握手升级

WebSocket 通常从 HTTP 请求开始。客户端发送带有升级意图的请求：

```http
GET /chat HTTP/1.1
Host: example.test
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
```

服务端同意后返回：

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...
```

返回 `101` 后，连接不再按照普通 HTTP 请求-响应对话，而是进入 WebSocket 帧通信。

### 5.3 WebSocket 不等于 HTTP 流式响应

两者都可以持续传输内容，但模型不同：

| 项目 | HTTP 流式响应/SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | 通常服务端持续返回 | 双向 |
| 建立方式 | 普通 HTTP 请求 | HTTP Upgrade |
| 适合 | 模型输出、日志、事件推送 | 聊天、协作、实时双向状态 |
| 客户端主动发送 | 通常需要另一个 HTTP 请求 | 连接建立后可随时发送 |
| 复杂度 | 较低 | 较高 |

如果只是把大模型生成的内容逐段返回给客户端，SSE 或普通 HTTP 流式响应通常已经足够。需要客户端和服务端持续双向交互时，再考虑 WebSocket。

## 6. 正向代理和反向代理

### 6.1 正向代理

正向代理代表客户端访问目标服务：

```text
客户端 -> 正向代理 -> 目标网站
```

目标网站看到的直接连接方是代理。使用者通常知道自己配置了代理。

常见用途：

- 统一出口；
- 访问控制；
- 缓存；
- 审计；
- 在特定网络环境中转发请求。

### 6.2 反向代理

反向代理代表服务端接收客户端请求：

```text
客户端 -> 反向代理 -> 后端服务
```

客户端通常只知道统一域名，不需要知道后端实例的地址。

常见用途：

- TLS 终止；
- 路由；
- 负载均衡；
- 静态文件服务；
- 限流和访问控制；
- 统一日志；
- WebSocket 和流式连接转发。

## 7. 负载均衡和网关

### 7.1 负载均衡

当后端有多个实例时，负载均衡器选择一个实例处理请求：

```text
                 -> 后端 A
客户端 -> 网关 ->
                 -> 后端 B
```

常见策略：

- 轮询；
- 最少连接；
- 按权重；
- 按客户端或请求特征保持会话。

负载均衡不是简单地“平均分配请求”。还要考虑实例健康状态、长连接、会话状态和请求耗时差异。

### 7.2 网关

网关通常位于客户端和多个后端服务之间，除了转发还可能负责：

- 路径路由；
- 身份认证；
- 限流；
- 请求大小限制；
- 超时；
- 重试；
- 日志和追踪；
- 协议转换。

网关承担的功能越多，排障时越需要明确请求究竟在哪一层失败。

## 8. LLM API 调用中的代理问题

一个 AI 应用调用模型服务时，链路可能是：

```text
客户端
  -> 业务 API
      -> 企业出口代理
          -> 模型服务网关
              -> 模型服务
```

每一层都可能影响：

- DNS 解析；
- TLS 证书；
- 连接超时；
- 读取超时；
- 请求体大小；
- 流式响应是否被缓存；
- 上游错误如何传递；
- 重试是否造成重复请求。

### 8.1 超时要分层

不要只设置一个笼统的“请求超时”。至少要区分：

```text
连接超时：无法建立连接
读取超时：连接建立了，但长时间没有数据
总超时：整个请求允许的最长时间
```

流式模型调用尤其要区分“首段内容超时”和“两个片段之间的读取间隔超时”。

### 8.2 重试要谨慎

网络错误不一定表示服务端没有处理请求。如果客户端在服务端已经接受请求后超时，再次重试可能造成：

- 重复创建任务；
- 重复扣费；
- 重复写入；
- 两条模型生成同时进行。

因此重试需要结合：

- 请求是否幂等；
- 是否有幂等键；
- 错误发生在连接前还是响应中途；
- 上游是否支持请求追踪。

### 8.3 代理可能破坏流式响应

流式响应要求代理及时转发已经收到的数据。如果代理缓存响应，客户端可能一直收不到片段，直到整个响应完成。

因此排查流式接口时要检查：

- `Content-Type`；
- `Cache-Control`；
- 代理是否启用缓冲；
- 空闲连接超时；
- 负载均衡是否支持长连接；
- 客户端是否主动读取响应流。

## 9. 终端观察

以下命令只用于观察自己有权限访问的服务。

查看 curl 是否支持 HTTP/2：

```bash
curl --version
```

查看协议协商结果：

```bash
curl -v --http2 https://example.test/
```

如果目标服务或本机 curl 不支持 HTTP/2，命令会失败或回退，不能据此断言 HTTP/2 不存在。

查看是否使用代理：

```bash
curl -v --proxy http://127.0.0.1:8080 http://127.0.0.1:8000/
```

该命令只适用于本机确实启动了代理的情况。不要把不存在的代理地址当作课程必需环境。

观察重点：

```text
* Connected to ...
> GET / ...
< HTTP/...
< content-type: ...
```

## 11. 面试高频考点

### 11.1 HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

回答应从承载和复用机制展开：

```text
HTTP/1.1：文本报文，复用有限，常用多个 TCP 连接
HTTP/2：TCP 上的二进制帧和多路复用
HTTP/3：QUIC 上的 HTTP，多路复用不依赖 TCP
```

不要只回答“HTTP/3 更快”。实际效果取决于网络、客户端和中间设备支持。

### 11.2 WebSocket 和 HTTP 是什么关系？

WebSocket 通常通过 HTTP Upgrade 建立连接，握手成功后切换为 WebSocket 帧通信。它不是每次消息都重新发送 HTTP 请求，也不是普通 HTTP 响应的简单延长。

### 11.3 正向代理和反向代理如何区分？

看代理代表谁：

```text
正向代理代表客户端访问目标
反向代理代表服务端接收客户端请求
```

### 11.4 为什么流式 LLM 调用需要关注代理？

模型服务可能逐段返回内容，但中间代理可能缓冲、超时或关闭长连接。排查时需要分别确认上游是否生成、网关是否转发、客户端是否读取，而不能只看最终 HTTP 状态码。
