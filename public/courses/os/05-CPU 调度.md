# 第5课:CPU 调度

第 2 课说过，线程是 CPU 调度的基本单位。现实中的问题是：就绪队列里可能同时有几十、几百甚至几万个线程，但一颗 CPU 核心同一时刻只能执行一条指令流。操作系统必须持续回答一个问题：**下一段 CPU 时间交给谁？**

CPU 调度不是简单地“谁先来谁先跑”。交互程序希望快速得到响应，后台任务希望整体尽快完成，实时任务希望在截止时间前运行，而调度器还要控制上下文切换的成本。本课用模拟代码观察几种经典算法，再理解它们背后的权衡。

**学习目标：**

1. 能说明调度器在什么时机做出选择；
2. 能解释上下文切换保存和恢复了什么，以及为什么有成本；
3. 能计算完成时间、等待时间和周转时间；
4. 能比较 FCFS、SJF、时间片轮转、优先级和多级反馈队列；
5. 能解释时间片大小、饥饿、优先级反转和多核亲和性的影响。

## 1. 调度器在解决什么问题

CPU 调度器从**就绪队列**中选择一个可以运行的线程，把 CPU 分给它。阻塞在磁盘、网络或锁上的线程不应进入候选集合，因为即使给它 CPU，它也无法继续推进。

```text
新建 → 就绪队列 → 运行
             ↑      │
             │      ├─ 时间片用完：回到就绪队列
             │      ├─ 等待 IO/锁：进入阻塞
             │      └─ 执行完成：终止
             └────────── IO 完成后重新就绪
```

常见调度时机：

- 当前线程从运行变为阻塞；
- 当前线程主动退出；
- 时间片耗尽；
- 更高优先级线程进入就绪队列；
- 中断或 IO 完成把线程唤醒。

非抢占式调度只在当前任务主动让出 CPU、阻塞或结束时切换；抢占式调度还允许定时器中断打断正在运行的任务。现代通用操作系统通常采用抢占式调度，否则一个死循环线程可能长期霸占 CPU。

## 2. 上下文切换：换人不是瞬间完成的

从线程 A 换到线程 B，内核大致需要：

1. 响应时钟中断或其他调度事件；
2. 保存 A 的程序计数器、通用寄存器、栈指针和调度状态；
3. 更新 A 的状态，把它放回就绪队列或标记为阻塞；
4. 选择 B；
5. 恢复 B 保存的寄存器、程序计数器和内核栈；
6. 必要时切换地址空间和页表，返回用户态继续执行。

这段时间 CPU 在做“换人”，没有执行用户任务，所以是调度开销。进程切换通常比同一进程内线程切换更重，因为可能涉及页表和 TLB；线程共享地址空间，通常不需要完整切换地址空间。

上下文切换也会破坏缓存局部性。即使寄存器已经恢复，B 的数据可能不在 CPU 缓存里，需要重新从更低层级的缓存或内存加载。因此“切换越频繁越灵活”和“切换越少效率越高”之间存在真实权衡。

## 3. 三个时间指标

对一个作业，先区分三个时间：

| 指标 | 公式 | 说明 |
| --- | --- | --- |
| 完成时间 | 作业最后一次运行结束的时刻 | 任务什么时候真正完成 |
| 周转时间 | 完成时间 - 到达时间 | 从提交到完成经历了多久 |
| 等待时间 | 周转时间 - CPU 执行时间 | 在就绪队列里等待了多久 |

例如任务在时间 2 到达，需要运行 5 个时间单位，在时间 12 完成：

```text
周转时间 = 12 - 2 = 10
等待时间 = 10 - 5 = 5
```

平均等待时间体现就绪队列里的排队情况；平均周转时间体现用户从提交任务到拿到结果的整体感受。但实时系统可能更关注最坏响应时间，交互系统可能更关注第一个响应，而不是平均值。

## 4. FCFS：先来先服务

**FCFS（First-Come, First-Served）**按到达顺序运行，通常是非抢占式的。它简单、公平、实现成本低，但会出现**护航效应（convoy effect）**：

```text
长任务 A：████████
短任务 B：        ██
短任务 C：          █
```

如果长任务先到，后面的短任务只能排队。平均等待时间可能很差，交互程序的响应也会变慢。

FCFS 的优点是行为容易预测；缺点是它只看“谁先来”，不看任务长度、优先级和交互需求。磁盘和数据库中的某些队列也会借鉴先来先服务，但现实调度通常会加入更多因素。

## 5. SJF：最短作业优先

**SJF（Shortest Job First）**从当前已经到达的任务中选择运行时间最短的一个。非抢占式 SJF 让当前任务跑完后再选择；抢占式版本叫 SRTF（Shortest Remaining Time First），新来的任务如果剩余时间更短，可以抢占当前任务。

已知每个任务运行时间时，SJF 能得到较低的平均等待时间，因为短任务不会被长任务挡在后面。但它有两个现实问题：

1. 操作系统通常不知道任务还要运行多久，只能通过历史运行时间预测；
2. 长任务可能一直被短任务插队，产生饥饿。

所以实际系统往往使用估计值和优先级，而不是直接获得“真实剩余时间”。

## 6. 时间片轮转：让交互任务轮流响应

**RR（Round Robin）**给每个就绪任务一个固定的时间片。时间片用完后，任务被抢占并放到队列尾部：

```text
时间片 q=2：
A A | B B | C C | A A | B | ...
```

时间片大小决定体验：

- 太大：算法接近 FCFS，短任务和交互请求要等很久；
- 太小：响应更及时，但上下文切换频繁，调度开销上升；
- 合理大小：让交互任务快速获得机会，同时避免换人占用太多 CPU。

RR 的公平性较好，但平均周转时间不一定优于 SJF。它更关注“每个人都能较快获得一小段 CPU”，而不是让某个指标达到最优。

## 7. 优先级调度与优先级反转

优先级调度每次选择优先级最高的就绪任务，可以是抢占式，也可以是非抢占式。高优先级任务能快速响应，但低优先级任务可能饥饿。

更隐蔽的问题是**优先级反转**：

```text
低优先级 L 持有锁
高优先级 H 等待这把锁
中优先级 M 持续运行
```

H 明明比 M 优先级高，却因为等待 L 的锁无法运行；M 又不断抢占 L，结果 H 间接被 M 阻塞。常见解决方法是优先级继承：L 持锁期间临时继承 H 的优先级，尽快释放锁。

## 8. 多级反馈队列：综合响应和吞吐

**多级反馈队列（MLFQ）**把就绪任务放在多个优先级队列中，并根据行为动态调整：

- 新任务先进入高优先级队列，快速获得响应；
- 经常用完整时间片的 CPU 密集任务逐渐降级；
- 很快阻塞等待 IO 的交互任务保留较高优先级；
- 对长期等待的任务周期性提升优先级，避免饥饿。

```text
高优先级：短时间片，优先响应
    ↓ 用满时间片
中优先级：中等时间片
    ↓ 继续占满 CPU
低优先级：长时间片，保证后台吞吐
```

MLFQ 的价值在于不需要提前知道任务类型：通过运行行为估计它是交互型还是 CPU 密集型。它也更复杂，需要处理优先级提升、时间片和公平性参数。面试中回答“为什么多级反馈队列实用”时，应说清它如何综合 SJF 的短任务偏好和 RR 的响应性。

## 9. 课程代码：模拟三种算法

代码位于 `code/os/05-cpu-scheduling.py`，不创建真实线程，也不改变本机调度器，而是在内存中模拟任务到达和 CPU 时间消耗。

```bash
python code/os/05-cpu-scheduling.py
```

代码中的 `Job` 包含：

| 字段 | 含义 |
| --- | --- |
| `name` | 任务名称 |
| `arrival` | 到达就绪队列的时间 |
| `burst` | 需要的 CPU 时间 |
| `priority` | 为后续优先级算法保留 |

`fcfs()`、`sjf()` 和 `round_robin()` 最后都返回同一个 `ScheduleResult`，统一计算完成时间、等待时间和周转时间。这样比较的是算法策略，而不是不同的统计方式。

运行同一批任务后，观察：

- FCFS 的执行顺序受长任务影响；
- SJF 倾向于先完成短任务；
- RR 的执行顺序会随着时间片反复切换；
- 平均等待时间和平均周转时间不一定同时最优。

模拟中的时间单位只是抽象 tick，不等于真实毫秒。真实调度还包括中断、缓存、优先级、CPU 核心数和 IO 阻塞等因素。

## 10. 多核调度与 CPU 亲和性

单核时，调度器在一条就绪队列上选择任务；多核时，需要同时决定“哪个任务”和“放到哪颗核心”。

把线程固定在某颗 CPU 上叫**CPU 亲和性（CPU affinity）**。它可能提高缓存局部性，减少线程在核心之间迁移；但固定过度会导致某颗核心很忙，另一颗核心空闲。调度器通常在缓存局部性和负载均衡之间做权衡。

多核不意味着程序一定线性加速：

- 任务之间有锁或数据依赖；
- 线程数超过核心数，调度和缓存开销增加；
- 任务频繁阻塞；
- 内存带宽成为瓶颈。

这也是第 2 课中“多线程不一定更快”的操作系统层解释。

## 11. 真实场景：AI 应用中的任务分层

一个 AI 应用可能同时存在：

- 处理 HTTP 请求的交互任务；
- 调用模型 API、等待网络返回的 IO 任务；
- 文档切分、分词、向量预处理等 CPU 任务；
- 批量索引和日志压缩等后台任务。

如果所有任务都放入同一个无优先级队列，后台批处理可能拖慢用户请求。工程上通常会分离队列和资源：

```text
高优先级：在线请求
中优先级：模型调用后的后处理
低优先级：批量索引、日志压缩
```

这不是简单地给线程写一个 `priority` 字段，而是要配合线程池大小、队列容量、超时和限流。操作系统调度器只能看到线程，业务层还需要把“用户体验优先”翻译成任务队列策略。

## 14. 面试高频考点

- 调度时机：阻塞、退出、时间片耗尽、更高优先级任务到达、IO 完成。
- 抢占式与非抢占式调度的差别。
- 上下文切换保存寄存器、程序计数器、栈等现场，进程切换还可能涉及页表和 TLB。
- FCFS 简单但有护航效应；SJF 平均等待时间较优但可能造成饥饿且难以准确知道运行时长。
- RR 通过时间片保证响应和公平，时间片大小影响切换开销。
- 优先级反转及优先级继承。
- MLFQ 通过动态调整优先级综合交互响应、CPU 吞吐和饥饿防护。
- 多核调度中的 CPU 亲和性、负载均衡和缓存局部性。
