# 第4课:线程同步：竞态、锁与死锁

第 2 课故意让两条线程同时给一个计数器加一，结果小于预期。第 3 课又说明，共享内存很快，但共享本身不会保证正确性。本课把这个“为什么会错”讲透，再学习如何用同步原语建立正确的执行顺序。

同步的目标不是让所有代码串行，而是只保护必须保持一致的那一小段。锁太少，数据会错；锁太多，并发度下降；加锁顺序不一致，还可能让所有线程互相等待。

**学习目标：**

1. 能从读-改-写交错过程解释竞态条件；
2. 能区分临界区、互斥锁、自旋锁、信号量和条件变量；
3. 能用条件变量实现有界生产者-消费者队列；
4. 能说出死锁的四个必要条件，并给出破坏策略；
5. 能区分死锁、活锁和饥饿，识别锁粒度和异常路径中的常见错误。

## 1. 共享不是同步

线程共享同一个进程的堆和全局变量，所以可以直接修改同一个对象。这是线程轻量高效的原因，也是并发 bug 的来源。

```python
counter += 1
```

看起来是一条语句，实际至少包含：

```text
读取 counter
计算旧值 + 1
把新值写回 counter
```

两个线程可能这样交错：

```text
线程 A：读取 41
线程 B：读取 41
线程 A：写回 42
线程 B：写回 42
```

两条线程都“完成”了自己的操作，但最终只增加了 1。这叫**竞态条件（race condition）**：结果依赖线程交错顺序，而这个顺序不是程序逻辑明确规定的。

GIL 不能替代同步。CPython 同一时刻通常只有一条线程执行 Python 字节码，但 `counter += 1` 由多条字节码组成，线程仍可能在中间切换；更重要的是，其他语言和释放 GIL 的扩展并不受这个限制。正确性必须由程序的同步协议保证。

## 2. 临界区与互斥

**临界区（critical section）**是访问共享状态、且必须保持不可分割的一段代码。互斥要求同一时间最多只有一个线程进入临界区。

```text
进入临界区前 acquire
        ↓
      修改共享状态
        ↓
离开临界区后 release
```

Python 的 `threading.Lock` 是互斥锁：

```python
with lock:
    counter += 1
```

`with` 会在进入时获取锁，在离开时释放锁，即使临界区抛出异常也能释放。不要把 `acquire()` 和 `release()` 分散在多个复杂分支里，否则异常路径很容易导致锁永久不释放。

锁保护的是**共享状态的一致性**，不是保护每一行代码。正确的临界区应尽量小：

```python
with lock:
    item = cache.get(key)

result = slow_network_request(item)

with lock:
    cache[key] = result
```

把网络请求放在锁里，会让所有线程排队等待网络；把真正需要一致性的读写放在锁里，才能同时保证正确性和并发度。

## 3. 互斥锁和自旋锁

互斥锁拿不到时，线程通常进入阻塞或等待状态，让出 CPU；锁释放后，等待线程再被唤醒。

自旋锁拿不到时，线程不睡眠，而是循环检查：

```text
while lock_is_busy:
    continue
```

两者的选择取决于等待时间：

| 机制 | 拿不到锁时 | 适合场景 | 代价 |
| --- | --- | --- | --- |
| 互斥锁 | 阻塞，让出 CPU | 临界区可能较长 | 涉及线程调度和唤醒 |
| 自旋锁 | 忙等，不让出 CPU | 临界区极短、多核环境 | 持锁时间长会白白消耗 CPU |

用户态 Python 代码通常直接使用 `threading.Lock`，不应手写自旋循环。自旋锁是内核和高性能运行时在极短临界区中的优化选择，不是“更快的锁”。

## 4. 信号量和条件变量

### 4.1 信号量：限制并发数量

信号量是一个计数器：`acquire()` 将计数减一，计数为零时等待；`release()` 将计数加一并唤醒等待者。

```python
connections = threading.Semaphore(3)

with connections:
    handle_request()
```

它适合“最多允许几个线程同时使用资源”，例如连接池、文件句柄或并发请求数。二元信号量有时可以实现互斥，但语义上仍是“资源数量为 1”，不是“锁的拥有者”。

### 4.2 条件变量：等待状态变化

条件变量表达的不是“有几个资源”，而是“某个条件什么时候成立”。生产者-消费者是典型例子：

```text
消费者：队列为空 → 等待“非空”
生产者：放入元素 → 通知“非空”
生产者：队列已满 → 等待“非满”
消费者：取走元素 → 通知“非满”
```

等待必须放在 `while` 中，而不是 `if`：

```python
with condition:
    while not buffer:
        condition.wait()
    item = buffer.pop(0)
```

被唤醒只说明“可能有变化”，不保证条件现在仍然成立。多个消费者可能同时醒来，其中一个先拿走最后一个元素，另一个必须重新检查。

Python 的 `queue.Queue` 已经把互斥锁、条件变量和任务计数封装好。工程代码优先使用它；自己实现条件变量是为了理解机制和处理定制缓冲区。

## 5. 生产者-消费者模型

有界队列同时解决两个压力：

- 生产者太快时，队列满，生产者等待，避免无限占用内存；
- 消费者太快时，队列空，消费者等待，避免忙等。

```text
生产者 ── put ──> [有界队列] ── get ──> 消费者
          满则等                 空则等
```

Python 示例：

```python
buffer = queue.Queue(maxsize=3)
buffer.put(task)  # 满时阻塞
task = buffer.get()  # 空时阻塞
try:
    process(task)
finally:
    buffer.task_done()
```

每次 `get()` 都要对应一次 `task_done()`；主线程调用 `join()` 时会等待所有任务都被标记完成。消费者退出通常使用“毒丸”对象，例如 `None`，而不是直接杀线程，因为 Python 没有安全的强制杀线程 API。

## 6. 死锁：所有人都在等别人

**死锁（deadlock）**是多个线程永久等待，系统无法继续推进。经典的四个必要条件必须同时成立：

1. **互斥**：资源同一时间只能被一个线程占用；
2. **持有并等待**：线程拿着资源 A，同时等待资源 B；
3. **不可剥夺**：资源不能被系统强行从持有者手中拿走；
4. **循环等待**：线程形成环：A 等 B，B 等 A，或更长的等待链。

两个线程按相反顺序获取两把锁：

```text
线程 A：持有 lock_a，等待 lock_b
线程 B：持有 lock_b，等待 lock_a
```

`04-thread-sync.py` 中的 `demonstrate_deadlock()` 会故意复现这个状态，并使用 `join(timeout=...)` 防止主线程永久卡住。真正的死锁线程被设置为 daemon，只是为了让演示程序能够退出；生产代码不能靠 daemon 线程解决死锁。

### 6.1 如何破坏死锁条件

| 条件 | 常见破坏策略 |
| --- | --- |
| 互斥 | 尽量使用不可变数据、消息传递或原子结构；不能随意取消必须保护的互斥 |
| 持有并等待 | 一次性申请全部资源，或申请第二个资源前释放第一个 |
| 不可剥夺 | 使用 `acquire(timeout=...)`，超时后释放已有资源并重试 |
| 循环等待 | 为所有锁定义全局顺序，所有线程按同一顺序获取 |

工程中最常用、最容易验证的是**固定加锁顺序**。如果锁有序号，线程永远先获取编号小的锁：

```text
lock_a < lock_b
所有路径都先拿 lock_a，再拿 lock_b
```

即使两个线程都需要两把锁，也不会出现 A 持有 A 等 B、B 持有 B 等 A 的循环。

### 6.2 活锁和饥饿

- **活锁**：线程没有阻塞，持续让步、重试或改变状态，但始终没有完成有效工作；
- **饥饿**：某个线程长期得不到 CPU 或资源，其他线程仍在推进。

死锁是“大家都不动”；活锁是“大家都在动但没有进展”；饥饿是“有人一直轮不到”。三者排查方向不同。

## 7. 锁的工程陷阱

### 7.1 锁内调用慢操作

数据库、网络、磁盘和外部 API 都可能长时间阻塞。把它们放在锁内，会把一个共享状态保护问题变成全局串行瓶颈。

### 7.2 锁的粒度过大或过小

粒度过大，安全但并发度低；粒度过小，性能好但更难证明状态一致。先找出不变量，再决定哪些字段必须一起修改。

### 7.3 异常导致锁不释放

始终优先：

```python
with lock:
    update_state()
```

不要假设临界区不会抛异常。异常、提前返回和取消路径都必须释放资源。

### 7.4 可重入问题

普通 `Lock` 被同一线程重复获取会把自己锁住；`RLock` 允许同一线程重复获取，并记录递归层数。`RLock` 不是默认更好的锁，它通常说明调用层次共享了锁的所有权，需要谨慎确认设计。

## 9. 真实场景：并发更新缓存

假设多个请求线程同时更新一个缓存：

```text
请求线程
  ├─ 读取缓存
  ├─ 缓存未命中，调用后端
  └─ 写回缓存
```

最简单的做法是把整个流程放进一把锁，但这样同一个 key 的请求会阻塞所有其他 key。更好的设计可能是：

- 只保护字典结构，不把后端调用放在全局锁里；
- 按 key 分片，每个分片一把锁；
- 用条件变量让后续请求等待第一个请求填充结果；
- 用队列把刷新任务交给单独 worker。

同步不是“给变量前面加一把锁”这么简单，而是要明确：哪个状态必须一致、谁生产、谁消费、等待什么条件、异常时如何释放资源。

## 12. 面试高频考点

- 竞态条件的根源是共享状态上的非原子读-改-写，而不是“线程数量多”本身。
- `Lock` 保护的是临界区；应使用 `with` 确保异常路径释放锁。
- 互斥锁拿不到时通常阻塞，自旋锁拿不到时持续占用 CPU 检查。
- 信号量用于限制资源数量，条件变量用于等待某个状态变化。
- 生产者-消费者需要有界队列、空/满条件和任务完成通知。
- 死锁四条件：互斥、持有并等待、不可剥夺、循环等待。
- 固定全局加锁顺序是最常见的死锁预防手段。
- 死锁是互相等待，活锁是持续活动但没有进展，饥饿是某个线程长期得不到资源。
- GIL 不提供业务数据结构的一致性保证；跨语言或释放 GIL 的代码更不能依赖它。
