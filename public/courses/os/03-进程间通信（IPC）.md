# 第3课:进程间通信（IPC）

第 2 课里我们看到：进程是资源容器，每个进程拥有独立的虚拟地址空间。这个隔离让一个服务崩溃时不至于直接改坏另一个服务，却也带来一个问题：父进程里的普通变量，子进程为什么看不见？两个 worker 要怎样交换任务和结果？

答案就是**进程间通信（IPC，Inter-Process Communication）**。IPC 不是一种具体 API，而是一组让不同地址空间交换数据、同步状态或发送通知的内核机制。本课先建立选择 IPC 的判断框架，再用 Python 标准库观察管道、消息队列、共享内存和信号。

**学习目标：**

1. 能解释地址空间隔离为什么必然需要 IPC；
2. 能区分管道、消息队列、共享内存、信号量、信号和 Socket；
3. 能说明共享内存为什么快，以及为什么仍然需要同步；
4. 能区分 `SIGINT`、`SIGTERM`、`SIGKILL` 的来源、语义和可捕获性；
5. 能根据数据大小、通信方向、可靠性和是否跨主机选择 IPC 方式。

## 1. 为什么进程之间不能直接传数据

第 2 课里，两个进程即使都写了 `counter += 1`，修改的也是两份不同的地址空间。父进程的地址 `0x1000` 和子进程的地址 `0x1000`，只是**虚拟地址数值碰巧一样**，背后可能映射到完全不同的物理页。

```text
父进程地址空间                     子进程地址空间
counter -> 物理页 A                 counter -> 物理页 B
        读写互不影响                         读写互不影响
```

这种隔离解决了两个问题：

- **安全**：一个进程不能随便读写另一个进程的密码、堆对象或栈；
- **稳定**：一个进程的野指针通常只破坏自己的地址空间。

代价是，进程之间不能像线程那样直接读写同一个 Python list。它们必须通过内核提供的入口交换数据：

```text
进程 A 的用户态内存
        │ write / send / put / signal
        ▼
      内核中的 IPC 对象
        │ read / recv / get / handler
        ▼
进程 B 的用户态内存
```

这里有一个重要边界：`fork` 的写时复制不是持续共享。父子进程刚创建时可能暂时指向同一物理页，但任一方写入后页面就分开了。需要持续共享可写数据时，要明确使用共享内存；需要传递结果时，通常用管道、队列或 Socket。

## 2. 先建立选择 IPC 的四个问题

遇到“两个进程怎么通信”时，不要先背 API，先问四个问题：

1. **传的是什么？** 一小段字节、结构化消息，还是大块数据？
2. **谁和谁通信？** 父子进程、同一台机器上的无关进程，还是不同主机？
3. **通信方向是什么？** 单向流水线、双向请求响应，还是多个生产者和消费者？
4. **一致性怎么保证？** 数据只读，还是多个进程会同时修改？

| 机制 | 数据形态 | 方向 | 典型优点 | 主要限制 | 常见场景 |
| --- | --- | --- | --- | --- | --- |
| 匿名管道 | 字节流 | 通常单向 | 简单，父子进程天然相关 | 没有消息边界，通常只适合亲缘进程 | Shell 管道、父子 worker |
| 命名管道 FIFO | 字节流 | 可约定双向 | 有名字，无亲缘关系也能打开 | 仍是字节流，吞吐和语义有限 | 本机简单进程协作 |
| 消息队列 | 一条条消息 | 可双向 | 保留消息边界，可按类型取 | 有队列容量和序列化成本 | 任务分发、结果回收 |
| 共享内存 | 共享字节区域 | 可双向 | 大数据交换快，避免重复复制 | 必须自己处理同步和一致性 | 图像、数组、缓存 |
| 信号量 | 一个计数器 | 不传业务数据 | 控制资源数量和顺序 | 不能承载业务内容 | 进程同步、限流 |
| 信号 | 一个异步通知 | 通知为主 | 轻量，适合控制进程 | 携带信息少，处理时机异步 | 优雅退出、重载配置 |
| Socket | 字节流或消息 | 通常双向 | 唯一自然支持跨主机 | 协议和连接管理更复杂 | 服务、RPC、跨机器通信 |

速度不能脱离数据大小和使用方式比较。共享内存避免了大块数据在两个用户态缓冲区之间反复复制，通常最快；但小消息用共享内存往往得不偿失，因为初始化、环形队列和同步协议本身也有成本。

## 3. 管道：像水管一样传字节

### 3.1 匿名管道

匿名管道由内核维护一段缓冲区，写端把字节放进去，读端再取出来。`os.pipe()` 返回一对文件描述符：

```python
read_fd, write_fd = os.pipe()
os.write(write_fd, b"hello")
message = os.read(read_fd, 1024)
```

它解决的是“把一段字节从一个进程流向另一个进程”，不是“把一个 Python 对象直接递过去”。`dict`、`list` 等对象必须先序列化成字节；`multiprocessing` 的高层队列会帮你完成这一步。

管道有三个容易被忽略的语义：

- `read` 没有数据时可能阻塞，直到有数据或所有写端关闭；
- `write` 端关闭后，读端读完缓冲区会看到 EOF；
- 管道是**字节流**，一次 `write` 对应几次 `read` 并没有业务层消息边界。

最后一点意味着，如果发送三条消息，接收方可能一次读到三条，也可能读到半条。需要消息边界时，要自己加长度前缀，或者直接使用消息队列。

### 3.2 命名管道 FIFO

匿名管道通常由同一个父进程创建后传给子进程；命名管道在文件系统中有一个名字，两个没有亲缘关系的本机进程也可以通过这个名字打开它。Linux/macOS 可用 `mkfifo` 创建：

```bash
mkfifo course-ipc.fifo
```

Windows 没有同样的 POSIX FIFO 命令，跨平台课程代码不使用它。理解上只需记住：**匿名管道靠继承文件描述符连接，FIFO 靠文件系统名字连接**。

## 4. 消息队列：传递一条条任务

消息队列在管道的字节流之上增加了消息边界。生产者放入一条任务，消费者取出一条完整任务；Python 的 `multiprocessing.Queue` 还会对普通 Python 对象进行序列化。

```python
queue.put({"file": "part-01.bin", "retry": 2})
task = queue.get()
```

`put` 和 `get` 的输入输出及副作用：

| API | 作用 | 输入 / 输出 | 副作用 |
| --- | --- | --- | --- |
| `Queue.put(obj)` | 序列化并放入队列 | 输入任意可序列化对象；默认无返回值 | 队列满时可能阻塞 |
| `Queue.get()` | 取出下一条消息 | 返回反序列化后的对象 | 队列为空时默认阻塞 |
| `Queue.get(timeout=秒)` | 限时取消息 | 超时抛 `queue.Empty` | 不会无限等待 |
| `Process.join()` | 等待生产者退出 | 无返回值 | 防止遗留子进程；不能代替取空队列 |

消息队列的“传值”意味着：子进程修改取出的字典，不会反向修改父进程原来的字典。对象经过序列化和反序列化后，已经是接收方的一份新对象。

它很适合任务分发：

```text
主进程 Queue.put(task)
        ↓
多个 worker Queue.get()
        ↓
worker 完成任务后 Queue.put(result)
        ↓
主进程汇总结果
```

代价是序列化和复制。传一个很大的 NumPy 数组（本课不引入第三方库）时，队列可能比共享内存慢很多。

## 5. 共享内存：快，但只解决了“放在哪里”

### 5.1 `multiprocessing.Value`

`multiprocessing.Value` 在进程之间创建一个共享的、类型受限的值：

```python
counter = mp.Value("i", 0)
counter.value += 1
```

这里的 `counter.value` 不是每个进程自己的普通整数，而是映射到一块进程间共享的内存。一个进程写入后，其他进程可以看到同一位置的变化。

但“共享”不等于“安全”。`counter.value += 1` 仍然是：

```text
读取旧值 → 加一 → 写回新值
```

两个进程可能同时读到 41，最后都写回 42，更新就丢了一次。`Value` 自带的锁可以保护这段读改写：

```python
with counter.get_lock():
    counter.value += 1
```

本课只讲信号量和共享内存的计数语义；锁、条件变量、死锁四条件放到第 4 课详细展开。

### 5.2 为什么共享内存通常最快

队列和管道的典型路径是：

```text
进程 A 用户缓冲区
  → 内核缓冲区
  → 进程 B 用户缓冲区
```

共享内存则让两个进程把同一段物理内存映射到各自地址空间：

```text
进程 A 虚拟地址 ─┐
                 ├─ 同一段物理页
进程 B 虚拟地址 ─┘
```

大块数据可以避免反复复制，所以吞吐很高。但它只解决“数据放在一个大家看得到的位置”，没有解决：

- 谁可以同时写；
- 读者如何知道写入完成；
- 写入一半时读者能不能读取；
- 缓冲区满了生产者怎么办。

这些问题要由信号量、互斥锁、条件变量或自定义环形队列解决。**共享内存负责数据，同步原语负责顺序。**

## 6. 信号量：用计数表示资源数量

信号量（semaphore）不是传输业务数据的容器，而是一个由内核或同步库维护的计数器。经典的两个操作是：

```text
P / wait / acquire：
    计数 > 0 时减一并继续
    计数 = 0 时等待

V / signal / release：
    计数加一
    必要时唤醒等待者
```

假设只有 3 个连接槽位：

```python
slots = mp.Semaphore(3)

slots.acquire()  # 占用一个槽位
try:
    handle_request()
finally:
    slots.release()  # 归还槽位
```

前三个进程可以进入，第四个必须等待。它表达的是“最多允许几个”，而不是“某个线程是否拥有锁”。二元信号量的行为看起来像锁，但第 4 课会进一步区分互斥锁、信号量和条件变量。

使用信号量时，最危险的错误是拿到资源后没有释放。一个 worker 异常退出，可能让槽位永久减少，最后所有任务都阻塞。`try/finally` 不是装饰，而是资源协议的一部分。

## 7. 信号：异步通知，不是数据通道

信号是内核发给进程的异步通知。它适合表达“请退出”“配置变了”“子进程结束了”，不适合传送一段业务对象。

| 信号 | 常见来源 | 默认效果 | 能否捕获/忽略 |
| --- | --- | --- | --- |
| `SIGINT` | 终端按 `Ctrl+C` | 中断前台进程 | 可以 |
| `SIGTERM` | `kill PID`，默认信号 15 | 请求进程优雅退出 | 可以 |
| `SIGKILL` | `kill -9 PID` | 立即杀死进程 | 不能捕获、不能忽略 |

`SIGTERM` 是“请你收尾后退出”，服务可以在处理函数中关闭监听 socket、刷日志、释放临时资源；`SIGKILL` 是内核直接终止进程，程序没有机会执行清理逻辑。因此线上停止服务通常先发 `SIGTERM`，超时仍不退出才使用 `SIGKILL`。

Linux/macOS 中可以观察：

```bash
python code/os/03-ipc.py
# 取消 demo_signal() 的注释后运行，另一个终端执行：
kill -TERM <PID>
```

Windows 的信号模型与 POSIX 不完全相同，`SIGTERM` 的行为由 Python 和 Windows 进程控制机制共同决定；课程代码会避免依赖 Unix 专属的 `os.kill -9` 才能完成主要实验。`Ctrl+C` 在 Windows 终端中仍可用于观察 Python 的中断处理。

## 8. Socket：进程间通信里的“网络接口”

Socket 本质上也是一个文件描述符背后的通信端点。两个本机进程可以通过 Unix domain socket 通信，两个不同主机则通过 TCP/UDP 通信。

```text
同一台机器：Unix domain socket
跨主机：    TCP / UDP socket
```

Socket 的特殊地位在于：其他 IPC 大多默认只解决同一台机器上的问题，Socket 的抽象天然包含地址、连接和协议，因此可以把通信边界扩展到网络。代价是需要处理连接断开、半包、超时、协议版本和身份认证。

不要把“用了 Socket”直接等同于“数据一定可靠”。TCP 提供有序可靠的字节流，但业务消息边界仍然需要应用层协议；UDP 不保证到达和顺序。第 9 课讲 IO 多路复用时，会把 Socket、文件描述符和 `select`/`epoll` 串起来。

## 9. 课程代码：观察复制传值与共享传值

课程代码在 `code/os/03-ipc.py`，只使用 Python 标准库，不需要安装第三方包。Unix 系统直接使用 `os.pipe()`；Windows 的 `spawn` 启动方式不能安全地把原始文件描述符作为普通整数传给子进程，因此示例自动使用语义等价且可传递的 `multiprocessing.Pipe`。

### 9.1 匿名管道

`demo_pipe()` 使用 `os.pipe()` 创建读端和写端。父进程写入 UTF-8 字节，子进程读取后解码。注意父子进程都要关闭自己不用的端点：不关闭多余的写端，读端可能一直等不到 EOF。

`demo_shared_value()` 让两个子进程共同增加一个整数。代码用 `counter.get_lock()` 保护读改写，因此最终应为 `2000`。可以复制一份函数，去掉 `with` 后重新运行，观察竞争导致的结果不稳定。

## 10. 真实场景：多进程下载器怎么选 IPC

假设一个下载器把任务拆给多个进程：

1. 主进程把 URL、目标文件名、重试次数放进消息队列；
2. worker 取出任务，下载到自己的临时文件；
3. worker 把状态、文件路径和错误信息放回结果队列；
4. 主进程统一更新进度和重试策略。

这里使用队列而不是共享 list，是因为任务和结果都是离散消息，队列天然提供边界和阻塞语义。若下载的是大块解码数据，可以把数据放进共享内存，只通过队列传递“共享内存的偏移、长度和状态”，避免复制大对象。

```text
控制面：Queue 传递任务、状态和元数据
数据面：共享内存承载大块数据
同步面：Semaphore / Event 表示可读、可写和资源数量
```

这三层拆分是工程中常见的设计：小消息走控制面，大数据走数据面，顺序和容量由同步面保证。

## 13. 面试高频考点

- 常见 IPC：管道、消息队列、共享内存、信号量、信号、Socket 的机制和适用场景。
- 管道是字节流，消息队列保留消息边界；共享内存速度快但必须配合同步。
- 进程普通变量为什么不能直接共享：地址空间隔离，`fork` 的写时复制也不等于持续共享。
- 共享内存为什么仍然有竞态：读改写不是原子操作，数据和同步是两个问题。
- `SIGTERM` 与 `SIGKILL` 的区别：前者请求程序清理后退出，后者由内核立即终止且不可捕获。
- `SIGINT` 通常来自终端 `Ctrl+C`，`SIGTERM` 通常来自 `kill PID`，不要把信号当成业务消息通道。
- Socket 是可跨主机的 IPC 抽象；TCP 保证字节流可靠有序，但不保证应用层消息边界。
