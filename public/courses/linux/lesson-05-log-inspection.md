# 第五课：日志查看与排查

本课是面试高频课，也回答"服务出问题先看什么"：日志。本课把前三课学的命令用在真实排错上，围绕三个问题展开——日志从哪来、写到哪去；怎么查看和搜索日志；怎么查看"最近的"日志（反向排序）。前置知识：第 2 课 `rg`、第 3 课管道与重定向、第 4 课 `tail`/`less`/`wc`。本课命令示例中，`#` 后是注释，实际执行时不输入。

**学习目标：**

1. 能说出应用日志的三种去向，并解释"服务没日志"时先查什么；
2. 能用 `tail -n` 查看最新日志、`tail -f` 实时跟踪；
3. 能用 `grep` 过滤关键词，并用 `-A`/`-B`/`-C` 查看上下文；
4. 能回答"如何查看最近的日志（反向排序）"，说出 `tail -n`、`tac`、`journalctl -r`、`ls -lt` 各自适用场景；
5. 能用 `journalctl -u`/`-r`/`-xe` 查看 systemd 服务日志，并区分应用日志文件与 systemd 日志；
6. 能解释日志轮转的作用（日志文件为什么不会无限增大）。

## 1. 日志的来源：应用和系统把日志写到哪

日志不是凭空出现的。排错的第一步是知道它**被写到了哪里**。三种常见去向：

1. **应用把 stdout / stderr 重定向到文件**：第 3 课学过 `python app.py > app.log 2>&1`。这是最常见的"服务日志"，路径由启动命令决定。
2. **日志框架直接写文件**：Python 的 `logging`、Java 的 log4j 这类日志库按配置文件把日志写到指定文件。路径由应用配置决定。
3. **系统服务写 `/var/log/`**：操作系统和系统级服务把日志集中写在 `/var/log/` 下：

| 文件 | 内容 |
| --- | --- |
| `/var/log/syslog` 或 `/var/log/messages` | 系统整体日志（发行版不同，文件名不同） |
| `/var/log/auth.log` | 登录和认证记录（了解即可） |
| 应用自己的 `*.log` | 路径由应用决定，不固定 |

**常见误解 → 实际情况**：以为"服务没日志"是代码没写日志。最常见的真实原因反而是**启动命令没做重定向**：应用的 stdout/stderr 直接输出到了启动它的终端，终端一关、输出就没了。排查第一步不是看代码，而是看启动命令里有没有 `> 文件 2>&1`，以及这个文件路径对不对。

## 2. tail：查看最新的日志并实时跟踪

日志文件总是**越往后越新**（新记录追加到末尾），所以"查最新日志"就是"看文件末尾"。

**`tail`** 输出文件末尾的 N 行，第 4 课学过 `-n`；本课再加一个排错神器 `-f`：

**常用形式**

```text
tail [选项] 文件路径
```

| 选项 | 含义 |
| --- | --- |
| `-n N` | 输出末尾 N 行，默认 10 |
| `-f` | 实时跟踪（follow）：文件有新内容写入就立刻显示，`Ctrl+C` 退出 |

```bash
tail -n 100 app.log    # 查看最近 100 行日志
tail -f app.log        # 实时跟踪新增日志；按 Ctrl+C 退出
```

`tail -f` 是排查"正在发生的问题"的标准动作：一边让请求继续打进来，一边在终端看日志实时滚动。

## 3. less：分页浏览大日志文件

日志文件几十万行时，`cat` 会直接刷屏（第 4 课的原因），`tail` 又只能看末尾。**`less`** 分页浏览、可以搜索，适合从头到尾排查大日志：

```bash
less app.log           # 分页浏览；/ERROR 向下搜索，n 跳下一个匹配，q 退出
```

第 4 课已讲过 `less` 的按键，这里只补充它在日志场景的用法：进 `less` 后按 `/` 输入关键词搜索，是所有日志排错的基本操作。

## 4. grep：过滤关键词并查看上下文

日志几万行，你只关心出错的部分。**`grep`** 按关键词过滤行，只输出匹配的行。第 2 课学过的 `rg`（ripgrep）是它的现代替代品，选项含义一致；面试和网上资料常说的 `grep` 就是本课讲的命令。

**常用形式**

```text
grep [选项] 关键词 [文件路径 ...]
```

| 选项 | 含义 |
| --- | --- |
| `-n` | 显示匹配行在文件中的行号 |
| `-i` | 忽略英文大小写 |
| `-r` | 递归搜索目录（`rg` 默认递归，传统 `grep` 必须加 `-r`） |
| `-A N` | 同时输出匹配行**之后**的 N 行（after） |
| `-B N` | 同时输出匹配行**之前**的 N 行（before） |
| `-C N` | 同时输出匹配行前后各 N 行（context） |

```bash
grep -n ERROR app.log                  # 筛出所有含 ERROR 的行，带行号
grep -C 3 'Traceback' app.log          # 看 Traceback 前后各 3 行，还原异常现场
grep -rn 'ERROR' logs/                 # 递归搜索整个 logs 目录
grep -i error app.log | tail -n 20     # 最近 20 条错误（管道是第 3 课学的）
```

面试里"只看报错行不够，要看到错误前后的日志"，答案就是 `-A`/`-B`/`-C`。单看 `-C` 一个选项就够日常用。

## 5. tac 与 ls -lt：反向查看最近的日志

面试题"**如何查看最近的日志（反向排序）**"有四条答案，适用场景不同：

| 方法 | 命令 | 适用场景 |
| --- | --- | --- |
| 看文件末尾 | `tail -n 100 app.log` | 单个日志文件的最新内容（默认顺序） |
| 整个文件反向 | `tac app.log` | 从最新往最旧逐条翻 |
| systemd 日志反向 | `journalctl -r` | systemd 服务（见第 6 节） |
| 找最新日志文件 | `ls -lt /var/log` | 多个日志文件时，按修改时间找最新的那个 |

**`tac`** 是 `cat` 的反向拼写，把整个文件倒过来输出（最后一行在最上面）：

**常用形式**

```text
tac 文件路径
```

日常使用不带参数；输出方向与 `cat` 完全相反。

```bash
tac app.log | head -n 20    # 从最新到最旧，取前 20 行
```

`ls -lt` 里的 `-t` 是第 1 课学的"按修改时间排序"：文件刚被写入，修改时间就更新，所以 `ls -lt /var/log` 最上面就是最近有日志写入的文件：

```bash
ls -lt /var/log | head -n 5    # 最近被修改的 5 个日志文件
```

## 6. journalctl：查看 systemd 服务日志

现代 Linux 发行版（Ubuntu 16.04 之后）用 **systemd** 管理系统服务。systemd 服务不再自己写日志文件，而是把输出交给 **journald** 统一收集、集中存储，用 **`journalctl`** 查看。

**常用形式**

```text
journalctl [选项]
```

| 选项 | 含义 |
| --- | --- |
| `-u 服务名` | 只看指定服务的日志 |
| `-n N` | 只看最近 N 行 |
| `-r` | 反向排序，最新在最上面 |
| `-f` | 实时跟踪 |
| `-xe` | 快速查看最近的错误和提示（`-x` 附解释、`-e` 跳到末尾），日常排查最常用 |

```bash
journalctl -u nginx -n 50    # nginx 服务最近 50 行（服务名换成你自己的）
journalctl -r -u nginx       # 反向：最新在最上面
journalctl -xe               # 直接看最近的错误和上下文
journalctl -f -u nginx       # 实时跟踪某个服务
```

`-xe` 是"服务起不来先跑一条"的命令，也是面试口述的常用答案。注意：`journalctl` 的日志是 journald 集中存储的，不能像文本文件那样直接 `tail`，但它的**输出**可以继续接管道，比如 `journalctl -u nginx | grep ERROR`。

应用日志文件与 systemd 日志的对比：

| 对比项 | 应用日志文件 | systemd 日志 |
| --- | --- | --- |
| 存储 | 应用写的普通文本文件（如 `app.log`） | journald 集中收集 |
| 查看命令 | `tail` / `grep` / `less` | `journalctl -u 服务名` |
| 查看最近 | `tail -n`、`tac` | `journalctl -r` |
| 实时跟踪 | `tail -f` | `journalctl -f` |

本课只讲查看日志，不展开 systemd 的服务管理；如果你的 WSL 发行版没启用 systemd，第 6 节的命令可以只读不练。

## 7. 日志轮转：日志文件为什么不会无限增大

日志不处理会一直涨，最终占满磁盘（第 10 课会讲磁盘排查）。系统用**日志轮转（logrotate）**解决：按时间或大小把当前日志改名归档、压缩旧日志、只保留最近几份，然后让应用继续写新的日志文件。

```text
app.log          # 正在写入的当前日志
  -> 轮转后     app.log.1        # 前一天的日志（未压缩）
  -> 再轮转     app.log.2.gz     # 更早的日志（已压缩，gz 表示压缩过）
```

看到 `app.log.1`、`app.log.2.gz` 这类后缀**不是应用出错**，是轮转留下的旧日志。查"很久之前"的日志要去翻这些归档文件；`tac` 也可以用在归档文件上做反向查看。

## 8. 本课命令速查表

| 命令 | 含义 | 常用参数 |
| --- | --- | --- |
| `tail` | 查看文件末尾（最新日志） | `-n N` 行数；`-f` 实时跟踪 |
| `less` | 分页浏览大日志 | `q` 退出；`/关键词` 搜索 |
| `grep` | 过滤包含关键词的行 | `-n` 行号；`-i` 忽略大小写；`-A`/`-B`/`-C` 上下文；`-r` 递归 |
| `tac` | 整个文件反向输出 | 无常用参数 |
| `ls -lt` | 按修改时间降序列出文件 | `-t` 按时间排序（第 1 课） |
| `journalctl` | 查看 systemd 服务日志 | `-u 服务名`；`-n N`；`-r` 反向；`-f` 跟踪；`-xe` 最近错误 |

## 9. 常见错误

| 常见错误 | 现象 | 正确做法 |
| --- | --- | --- |
| 启动命令没重定向 | 终端有输出，文件不存在或为空 | 启动时写 `> app.log 2>&1` |
| 只看 `tail` 默认 10 行 | 看不到足够多的日志 | 明确写 `tail -n 100` |
| `grep` 不加上下文 | 只看到 ERROR 行，不知道前后发生了什么 | `grep -C 5 'ERROR' app.log` |
| 用 `cat` 看大日志 | 内容瞬间刷屏 | 用 `less` 或 `tail` |
| 把 `app.log.1` 当故障 | 以为日志文件坏了 | 那是轮转的旧日志，正常现象 |
| `journalctl` 里搜不到关键词 | 服务名写错，或日志不归 journald | 核对 `-u 服务名`；或 `journalctl \| grep 关键词` |

## 10. 运行本课命令练习

先生成一个会同时输出正常信息和错误的脚本。把下面的内容保存为 `~/linux-course-tmp/log_demo.py`（用任意文本编辑器），`#` 后是注释，实际输入时不写：

```python
import sys
import time

print("demo service starting")            # 正常输出，走 stdout
for i in range(10):
    if i % 3 == 0:
        print(f"ERROR: request {i} failed", file=sys.stderr)   # 错误输出，走 stderr
    else:
        print(f"INFO: request {i} ok")    # 正常输出，走 stdout
    time.sleep(0.5)
print("demo service stopped")
```

然后在两个终端窗口里依次执行：

```bash
cd ~/linux-course-tmp
python3 log_demo.py > app.log 2>&1        # 正常和错误都进 app.log
wc -l app.log                             # 一共多少行
tail -n 3 app.log                         # 最新的 3 行
grep -n ERROR app.log                     # 出错的是哪些行
grep -C 2 'ERROR' app.log | tail -n 12    # 错误前后各 2 行的上下文
tac app.log | head -n 5                   # 反向：最新在最上面
ls -lt ~/linux-course-tmp                 # 哪个文件最新被修改
```

实时跟踪需要两个终端窗口配合：

```bash
# 终端 A：先启动跟踪
tail -f app.log
# 终端 B：再跑一次脚本并追加输出
cd ~/linux-course-tmp && python3 log_demo.py >> app.log 2>&1
```

观察终端 A 里日志是否逐行实时出现，然后 `Ctrl+C` 结束跟踪。

如果本机启用了 systemd（Ubuntu 发行版），可以再试：

```bash
journalctl -xe | head -n 20    # 看最近的系统错误和提示
```

## 13. 面试高频考点

- **如何查询日志**：按需求选命令——看最新用 `tail -n 100`；实时跟踪用 `tail -f`；过滤关键词用 `grep`（要上下文加 `-C`）；大文件分页用 `less`。口述模板："查最近日志先 `tail -n 100`，要找错误就 `grep -C 5 ERROR`，要看实时写入用 `tail -f`。"
- **如何查看最近的日志（反向排序）**：四条答案。口述模板："单个文件看末尾用 `tail -n`；整个文件从新到旧用 `tac`；systemd 服务用 `journalctl -r`；多个日志文件分不清时用 `ls -lt` 按修改时间找最新的那个。"这是你被问到的那道题的标准答案。
- **如何实时跟踪日志**：`tail -f 文件` 和 `journalctl -f -u 服务名`；排查线上正在发生的问题时，先开跟踪再复现请求。
- **grep 如何带上下文**：`-A`（之后）、`-B`（之前）、`-C`（前后）；面试场景"异常堆栈要看前后日志"，答 `grep -C N 'Traceback' 日志文件`。
- **应用日志 vs systemd 日志**：应用日志是普通文本文件，用 `tail`/`grep` 直接读；systemd 日志由 journald 集中收集，用 `journalctl -u 服务名` 读，反向用 `-r`，实时用 `-f`。两者输出的管道用法相同。
- **服务没日志怎么排查**：先看启动命令有没有 `> 文件 2>&1`；再看文件路径对不对、有没有权限（第 6 课展开）；最后确认进程是不是真的活着（第 8 课展开）。

## 14. 小结与下一课预告

日志的完整排查链是：知道日志去哪（重定向 / `/var/log` / journald）→ 用 `tail` 看最新、`less` 看大文件、`grep` 过滤上下文 → 用 `tac`/`ls -lt`/`journalctl -r` 处理"反向排序"需求 → 理解轮转避免日志占满磁盘。第 3 课的管道和重定向在这里成了主力工具。

下一课进入另一个高频排查场景——**文件权限与用户基础**：`ls -l` 里的权限位怎么读、`755`/`644` 代表什么、`chmod`/`chown` 怎么用，以及 "Permission denied" 怎么定位。
