# 第5课:合并与冲突解决

第二课学习了如何创建分支，第四课学习了如何撤销和恢复修改。本课学习如何把一个分支中的提交合并到另一个分支，以及当两个分支修改了同一部分内容时，如何解决 Git 无法自动判断的冲突。

## 1. 什么是合并

假设有两个分支：

```text
A —— B  --  D    main
       \
        C      feature
```

`main` 和 `feature` 都从提交 B 开始，但之后分别产生了新的提交。合并的目标是把 feature 中的变化纳入 main：

```text
A —— B -- D  ————— M   main
       \     /
        C ——      feature
```

这里 `M` 是合并后的结果。合并不会删除 feature 分支，也不会把两个提交改写成一个；它会在当前分支上创建一个新的结果。

## 2. `git merge` 合并到哪里

执行合并前，先切换到<mark>“接收变化的分支”</mark>：

```bash
git switch main
git merge feature
```

这句话的含义是：把 `feature` 的变化合并到当前所在的 `main`。

`git merge` 的方向不是由命令最后出现的分支决定，而是由当前分支决定。

如果当前在 feature 上执行：

```bash
git merge main
```

含义就是把 main 合并到 feature。

## 3. 合并前的状态

合并会改变当前分支的历史和文件内容，所以执行前要检查：

```bash
git status
git log --oneline --decorate --graph --all
```

如果工作区有未提交修改，Git 可能拒绝合并，也可能把合并结果与未提交修改混在一起。学习和实际开发中，合并前最好先提交、stash，或明确处理这些修改。

## 4. 快进合并

如果 main 在 feature 创建之后没有新的提交：

```text
A —— B        main
       \
        C —— D  feature
```

此时把 feature 合并到 main，main 可以直接从 B 移动到 D：

```text
A —— B —— C —— D  main, feature
```

<mark>这种情况叫 fast-forward（快进）。它没有创建额外的合并提交，因为历史是一条直线。</mark>

执行：

```bash
git switch main
git merge feature
```

## 5. 什么时候会产生合并提交

如果 main 和 feature 都各自有新的提交：

```text
        C —— D   feature
       /
A —— B
       \
        E —— F   main
```

此时 Git 需要把两个方向的历史合并到一起，可能创建一个新的合并提交：

```text
        C —— D   feature
       /       \
A —— B         M   main
       \       /
        E —— F
```

是否创建合并提交取决于历史关系和 Git 的配置。本课先重点理解：合并发生在当前分支上，结果会改变当前分支。

## 6. 什么是冲突

如果两个分支修改了同一个文件的同一段内容，Git 可能无法自动选择应该保留哪一边。此时合并会暂停，这叫 merge conflict。

例如：

```text
共同基础 B：
title = "原来的标题"

main 修改后：
title = "主分支标题"

feature 修改后：
title = "功能分支标题"
```

Git 无法知道最终应该使用“主分支标题”还是“功能分支标题”，所以需要你决定。

注意：不同文件的修改通常可以自动合并；同一文件不同位置的修改也通常可以自动合并。冲突的关键不是“两边都改了文件”，而是“两边改动无法同时成立”。

## 7. 冲突标记

冲突发生后，文件中可能出现：

<pre>&lt;&lt;&lt;&lt;&lt;&lt;&lt; HEAD
main 分支的内容
&equals;&equals;&equals;&equals;&equals;&equals;&equals;
feature 分支的内容
&gt;&gt;&gt;&gt;&gt;&gt;&gt; feature</pre>

三部分分别表示：

- `<<<<<<< HEAD` 到 `=======`：当前分支（main）的一侧；
- `=======` 到 `>>>>>>> feature`：正在合并进来的分支（feature）一侧；
- 两个标记之间的内容是 Git 无法自动选择的候选内容。

这些标记不是代码的一部分。解决冲突时，需要删除标记，并留下最终想要的文本。可以选择：

- 只保留 main 的内容；
- 只保留 feature 的内容；
- 把两边内容组合起来；
- 根据业务规则重新编写内容。

## 8. 完整的冲突解决流程

### 8.1 开始合并

```bash
git switch main
git status
git merge feature
```

### 8.2 查看冲突状态

```bash
git status
git diff
```

`git status` 会告诉你哪些文件处于 `unmerged` 或 `both modified` 状态。`git diff` 可以查看冲突内容。

### 8.3 编辑冲突文件

打开冲突文件，删除 `<<<<<<<`、`=======`、`>>>>>>>` 及不需要的候选内容，留下最终版本。

例如决定组合两边内容后：

```text
title = "主分支与功能分支标题"
```

### 8.4 标记冲突已解决

编辑完成后执行：

```bash
git add conflict.txt
```

这里的 `git add` 不是在普通意义上“顺便保存文件”，而是告诉 Git：我已经处理了这个文件，当前工作区内容可以作为合并结果进入暂存区。

### 8.5 检查并完成合并

```bash
git status
git diff --staged
git commit
```

如果 Git 自动生成合并提交消息，确认后保存并退出编辑器即可。也可以使用：

```bash
git commit -m "Merge feature into main"
```

完成后查看历史：

```bash
git log --oneline --decorate --graph --all
```

## 9. 如果不想继续合并

在冲突解决完成并提交之前，可以取消这次合并：

```bash
git merge --abort
```

它会尽量把当前分支恢复到合并开始前的状态。执行前仍然要确认是否有合并开始前就存在的未提交修改。

## 10. 完整实验

为了明确观察变化，使用单独的冲突实验分支。先确保实验仓库干净：

```bash
cd <本仓库根目录>/code/git/git-state-lab
git status
```

创建两个分支并分别修改同一个文件：

```bash
git switch main
git switch -c merge-main
printf '来自 main 方向\n' > conflict.txt
git add conflict.txt
git commit -m "Add conflict file from main direction"
git switch main
git switch -c merge-feature
printf '来自 feature 方向\n' > conflict.txt
git add conflict.txt
git commit -m "Add conflict file from feature direction"
```

回到主分支并合并：

```bash
git switch main
git merge merge-main
git merge merge-feature
```

如果 `conflict.txt` 在两个分支上都是从不存在变成同名新文件，Git 可能报告“add/add”冲突。打开文件解决冲突：

```text
来自 main 方向
来自 feature 方向
```

修改完成后：

```bash
git add conflict.txt
git diff --staged
git commit -m "Resolve conflict between branches"
git status
```

如果实验仓库的历史状态与命令不完全匹配，不要强行继续；先用 `git status` 查看 Git 当前是否处于合并中。

## 11. 本课小结

```text
git switch main
    选择接收变化的分支

git merge feature
    把 feature 合并到当前的 main

git add <conflicted-file>
    标记冲突文件已经人工解决

git commit
    完成合并提交

git merge --abort
    取消尚未完成的合并
```

## 12. 课后练习

1. 创建两个分支，让它们修改同一个文件的不同位置，观察 Git 如何自动合并。
2. 创建两个分支，让它们修改同一行，观察冲突标记。
3. 解决冲突时只保留一侧内容，再做一次实验组合两侧内容。
4. 用 `git status` 解释冲突文件处于什么状态。
5. 解释为什么合并前要先切换到接收变化的分支。
6. 解释 `git merge --abort` 与 `git restore` 的区别。
