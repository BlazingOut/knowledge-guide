# 第四课：记忆系统：短期、长期与污染控制

第三课的 Observation 会写回上下文，但它只活在当前会话里——第二天用户说"你上次不是说我偏爱晨跑吗"，Agent 什么也记不起来。本课把"记住东西"变成一套系统：会话内的短期窗口、跨会话的长期库、写入门槛和污染控制。不讲：向量数据库与 embedding 的具体实现（RAG 课）、LangGraph 的 checkpointer 持久化机制（LangGraph 第 6 课）、上下文工程（第 5 课，本课只做修剪衔接）、海量会话数据的存储设计（database 课）。

**学习目标：**

1. 能区分短期/长期记忆，说明各自存什么、从哪来、怎么召回；
2. 能设计一份长期记忆条目（事实、来源、置信度、是否审核），并说明为什么"记录"不等于"记忆"；
3. 能解释 Auto Memory 为什么需要阈值、去重、审核，不能无限写入；
4. 能说明向量记忆与结构化记忆各自的适用场景；
5. 能识别并处理一条污染记忆：定位来源 → 回滚 → 修正；
6. 能说出团队共享记忆里哪些走 Git、哪些走数据库。

## 1. 记忆系统解决什么问题：Agent 每轮决策都从空白开始

先看一个真实断裂：

```text
周一  用户：我偏爱晨跑。          Agent 记住了吗？
周二  用户：帮我看看今天要不要跑步。  Agent 还知道"晨跑"吗？
```

答案是不知道。每次 `chat.completions.create` 的 `messages` 都是从零组装，模型不会"记得"上一次请求——它只读你这次塞进去的文本。这就是记忆系统的起点：

```text
模型记不住任何东西 -> 上下文里有什么，它就基于什么决策
                     -> 所以要有一套系统决定"上下文里装什么"
```

先定义：**记忆系统**是决定"哪些历史信息进入模型上下文"的整套机制，包含存储、写入规则、召回和淘汰。它不等于"把聊天记录存下来"——只存不取，等于没存。

## 2. 短期记忆：会话窗口与摘要折叠

**短期记忆**是当前会话内的信息：本轮用户话、助手回复、工具观察、任务状态。它有两个特征：只在本会话有效；受上下文窗口限制。

如果每轮都把全部历史塞进 `messages`，会话到第 20 轮时上下文里全是旧对话，模型既付不起 token 成本，也找不到重点。做法是**窗口 + 摘要折叠**：

```text
messages 达到上限（比如 8 条）
    -> 最老的消息折叠成一条摘要，留在上下文里占一小块
    -> 窗口内的最新消息原样保留
    -> 发给模型 = system + 摘要 + 窗口内消息
```

课程代码的 `SessionBuffer` 就是这个结构，运行后可以看到：

```text
窗口上限 8，实际消息 8 条
摘要： （早前 4 条消息已折叠为摘要：会话开头在讨论本周运动计划）
发给模型的上下文条数：10
```

真实的摘要由模型把旧消息总结成一句话；课程代码用固定文案，让长度变化可观察。判断标准一句：**短期记忆是"够用的最近"，不是"所有的历史"。**

## 3. 长期记忆：跨会话的事实、偏好与摘要

**长期记忆**是跨会话的信息：用户偏好（偏爱晨跑）、事实（本周已跑两次）、摘要（上次聊过什么）。它必须存在外部存储里，需要时被召回到上下文。

一条长期记忆不是一行字符串，而是一个**条目**，课程代码的 `MemoryEntry` 有四个字段：

| 字段           | 含义                                           | 为什么必须有        |
| ------------ | -------------------------------------------- | ------------- |
| `fact`       | 事实内容                                         | 要装进上下文的就是它    |
| `source`     | 来源：user / model_inference / tool_observation | 决定可信度，排查污染的线索 |
| `confidence` | 置信度 0~1                                      | 决定能不能自动写入     |
| `reviewed`   | 是否人工审核                                       | 自动写入的通行证之一    |

长期记忆要有四种能力，缺一不可：

| 能力   | 含义                     | 课程代码             |
| ---- | ---------------------- | ---------------- |
| 写入   | 按规则落库                  | `remember`       |
| 召回   | 按关键词取出相关条目             | `recall`         |
| 过期   | 旧事实被新事实取代或删除           | `revoke` + 冲突处理  |
| 冲突处理 | 同 key 新事实与旧事实不同时，不静默覆盖 | `remember` 的冲突分支 |

为什么"记录"不等于"记忆"：存了二十年聊天记录但从不召回、从不更新，那只是一堆文本文件。**记忆 = 条目 + 生命周期（写、取、改、删）+ 进入上下文的通道。**

## 4. 写入规则与召回注入：模型每次决策看到哪一段

记忆系统有两个方向。**写入**（观察变成记忆）和**召回**（记忆进入上下文），中间隔着一道门槛（第 5 节讲）。

**召回**决定"上下文里装哪一段"。课程代码路径 C 把两种做法放在一起对比——同一个"看这周运动"目标，用二十天的完整聊天记录，和只召回一条相关偏好：

```text
整段塞进：802 字符，40 条消息
摘要注入：11 字符，1 条偏好
```

模型基于同样的决策依据，输入差了一个量级。这就是第三课结尾预告的那句话——**工具结果只是短期记忆的一小块，长期记忆经过召回进入上下文，才是"有记忆"**。

**写入**要回答四个问题，这是面试里"记忆系统要解决哪些核心问题"的答案：

```text
存什么      事实、偏好、摘要，不是流水账
何时写入    用户明确表态、高置信度观察、审核通过后
如何召回    按主题/关键词检索相关条目（向量召回在第 6 节）
如何淘汰    过期、冲突、被用户推翻的事实要能删除
```

## 5. Auto Memory：候选记忆的准入机制

模型推断会源源不断地产生"候选记忆"（比如"用户可能在用番茄钟学习"）。如果全部自动写入，记忆库会堆满猜测，垃圾事实反而把真实偏好淹没。所以自动写入需要准入机制。先纠正一个常见误解：**生产系统不会让模型"给自己打个 0.7 分"来决定写不写**——真实性不是模型自评的标量。真实的准入机制分三层。

### 5.1 主闸门：来源准入（user / 工具观察 / 模型推断）

| 候选来源 | 能否自动写入 | 为什么 |
| --- | --- | --- |
| user 明确声明（"我喜欢晨跑"） | 直接写 | 事实来自用户本人 |
| 工具 / 系统结构化观察 | 直接写 | 来自系统自身的观测，不是模型的猜测 |
| 模型推断（"你大概用番茄钟"） | 不自动写，只进候选 | 推断可能错，且没有可对账的证据 |

这是绝大多数生产系统的做法——ChatGPT / Claude 的记忆开关就是这么分的：**显式记忆（用户让记的）直接存；自动记忆（模型推断的）默认进候选，用户可以查看、关闭、删除**。判断依据是来源，不是分数。

### 5.2 候选怎么进：抽取即结构化，分数只用于排序

模型推断要进候选，输出不是一段散文，而是结构化字段：

```text
statement          "用户可能用番茄钟学习"
statement_type     用户陈述 / 系统观测 / 模型推断
importance         0~1：这条对未来任务的价值（排序和裁剪用）
```

关键点：**`importance` 是"这条记忆值不值得占存储"，不是"这条是真是假"**。真实性靠来源准入判断，价值靠 importance 排序——两个维度分开，面试能说出这个区分就是加分点。分数只决定"排多前、留多久、要不要占存储"，不单独决定"写不写"。同类候选还要**去重**：同一事实的多条候选只保留一条（按 statement 文本或向量相似度归并），否则一条偏好会被记成十条。

### 5.3 验证闭环：事前确认，事后回收

准入规则挡不住"当时判断对了、后来用错了"。所以自动写入还有两个闭环：

```text
事前  用户确认 / 纠正：Agent 回显"我记下了你更爱晨跑，对吗？"
      确认才落库；纠正则更新——"审核"的真实形态是对话内确认，不是后台人工审
事后  badcase 回收：一条记忆被召回后导致错误决策（第 5 课讲可对账输出）
      在 trace 里定位到它 -> 降权或删除
```

### 5.4 冲突与覆盖的真实实现

候选与已有记忆同 key 冲突时，生产系统通常不是"进待审核队列"，而是**版本化 upsert**：新事实覆盖、旧值保留历史（可回滚、可审计），或同 key 多版本按时间 / 来源加权取用。课程代码用"进待审核队列"是简化的安全选择——它防止"一条推断悄悄覆盖用户声明"，方向对；面试里补一句"生产里更常用版本化覆盖 + 保留历史"会更完整。

### 5.5 课程代码的简化与诚实说明

课程代码的 `MemoryEntry.confidence` 是 0~1 标量、`remember` 用 `confidence >= 0.7 且 reviewed` 判断——这是**教学简化**：它把"来源准入"量化成了一个数（user=1.0、工具观察=0.8、模型推断=0.5），把"验证闭环"压成了 `reviewed` 一个布尔。真实系统不依赖"模型自评分数"，按 5.1~5.3 的来源规则 + 抽取分类 + 验证闭环实现。读代码时把 `confidence` 理解成"来源可信度的量化占位"，不要把"模型给自己打分"当成业界做法。

判断标准一句：**自动写入的通行证是"来源可信 + 验证闭环"，不是模型给自己打的分数。** 本课作业会让你把"低置信度 → 进待审核队列"写出来——代码里的 `confidence` 低，对应真实系统里的"来源是模型推断、尚未确认"。

## 6. 向量记忆与结构化记忆：两种存储的取舍

长期记忆的存储有两种主流形态，面试常被放在一起问：

| | 向量记忆 | 结构化记忆（数据库 / Markdown 笔记） |
| --- | --- | --- |
| 召回方式 | 按语义相似度（embedding + 向量检索） | 按规则、条件、关键词精确查 |
| 适合 | 模糊相似召回：凭印象找"上次聊过的类似内容" | 规则、偏好、可人工审阅的事实 |
| 优点 | 表达自由，近似匹配 | 可查询、可审阅、可审计、可回滚 |
| 缺点 | 黑盒，召回内容难解释，实现重 | 需要先建模，表达不了模糊相似 |
| 本课位置 | RAG 课展开 embedding 与向量库 | 本课 `MemoryEntry` 就是它的雏形 |

一句话判断：**要"查得准、能审阅"的偏好与事实走结构化，要"凭感觉找相似"的走向量。** 两者通常共存，不是二选一。

## 7. 记忆污染：错误记忆如何带偏所有决策

记忆先于决策进入上下文（第 1 节那张图），所以**一条错误记忆会让之后每一轮决策都建立在错误前提上**。这就是污染。

污染从哪来？最常见三种：

```text
过期事实      用户上个月不爱运动，这个月开始晨跑——旧条目还在
推断当事实    模型猜"用户不喜欢运动"，被当成确定事实写入
错听错写      用户说"不用番茄钟了"，被记成"用番茄钟"
```

课程代码路径 D 完整演示一次污染事故：

```text
写入：pref:sport = 用户不喜欢运动（来源 model_inference，置信度 0.9，已审核）
模型决策：查看这周运动记录 -> 选了 search_preferences（本该查运动记录）
```

注意关键点：这条记忆**置信度高、也过了审核**，照样带偏——审核只能拦住一部分，拦不住"过期但正确过"的推断。所以污染控制是三件套，不是一道审核：

```text
来源标注   每条记忆带上 source：出问题时先怀疑推断，再怀疑用户声明
审核       高置信推断也要人确认，但承认它不是万能的
可回滚     发现污染 -> 删除条目 -> 写入更正事实（revoke + 重新 remember）
```

定位顺序和第三课的失败定位一致：**先看这次决策上下文里注入了哪条记忆 → 看它的来源和置信度 → 判断是否过期/与现状矛盾 → 回滚并更正。**

## 8. 团队共享记忆：哪些走 Git、哪些走数据库

"记忆"不只有用户偏好——团队也会沉淀共享知识：流程规范、提示词模板、工具使用说明。它们放哪，取决于**谁改、怎么审**：

| 内容 | 放哪 | 为什么 |
| --- | --- | --- |
| 流程规范、提示词模板、配置示例 | Git + Code Review | 要版本、要 diff、要多人评审，改错要能回滚 |
| 用户数据、运行时事实、会话状态 | 数据库 | 高频读写、需要事务和查询，不适合走文件 |
| 大型不常变的参考（文档库） | 知识库 / 向量库 | 只读为主，靠检索取用（RAG 课展开） |

一句话判断：**要"评审才允许改"的走 Git，要"程序随时读写的"走数据库。** 把提示词模板塞进数据库、把用户会话存进 Git，都是选错了生命周期的匹配。

## 9. 常见错误

1. **只存不取**：写了长期库但从不在组装上下文时召回，等于没记忆。判断：上下文里有没有出现过记忆条目。
2. **整段聊天塞进**：没有窗口和摘要，第 20 轮时上下文爆炸（路径 C 的 802 字符对比）。修复：窗口 + 折叠。
3. **无限自动写入**：模型每个推断都落库，记忆库变成猜测堆。修复：阈值 + 审核 + 去重。
4. **冲突直接覆盖**：一条低置信度推断把用户声明的事实悄悄改掉。修复：冲突进待审核队列（作业 `update_fact`）。
5. **只加不删**：过期事实永不纠正，记忆库越来越脏。修复：`revoke` 之外，还要有定期复查过期条目的机制。
6. **污染不追踪来源**：出问题时只能整库清空。修复：每条带 `source`，定位先看来源，回滚单条。

## 11. 课后作业

作业在 `code/ai-agent/ai_agent_lesson04.py` 下半部分，场景是学习资料记忆库（已预置两条记忆）。需要完成两个函数：

1. `recall_top(memory, keyword, top_k)`：按置信度降序返回命中的前 `top_k` 条——召回不能只看"有没有"，要看"最可信的";
2. `update_fact(memory, key, new_fact, source)`：同 key 冲突更新——`source == "user"` 时直接覆盖并返回 `"已更新"`；其余来源返回 `"需要审核，未覆盖"`，**不让一条推断悄悄改掉用户声明的事实**。

```text
召回排序（应把置信度高的放在前面）
用户改口（应覆盖）：已更新
模型猜测（应拒绝覆盖）：需要审核，未覆盖
最终记忆：改用卡片法学习
```

思考：`recall_top` 按置信度排序解决了"召回不相关"还是"召回不够可信"的问题？排序放在召回前还是注入前，效果差在哪？
