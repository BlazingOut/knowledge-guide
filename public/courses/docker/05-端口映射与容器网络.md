# 第5课:端口映射与容器网络

> 外卖系统上线后，用户要访问 `takeout-api`，`takeout-api` 又要访问 Redis 和 MySQL。这三个服务分别在不同容器里，网络路径必须接通。
>
> 这一课解决三条路径：用户怎么访问 app、app 怎么访问 Redis/MySQL、容器怎么访问宿主机。端口映射、服务名、容器内 `localhost`、多个容器都用 6379 为什么不冲突，都会在这一课讲清楚。

命令示例中 `#` 后面的文字是注释，实际执行时不输入。

## 1. 场景：外卖系统的三条网络路径

假设外卖系统已经拆成三个容器：

```text
用户/浏览器
    |
    | 访问 app 的 8000
    v
takeout-api 容器（Python，监听 8000）
    |
    ├── 访问 takeout-redis:6379   -> Redis 容器
    └── 访问 takeout-mysql:3306   -> MySQL 容器
```

对应三条路径：

| 路径 | 谁发起 | 怎么走 |
|---|---|---|
| 用户 -> app | 浏览器、curl | 宿主机端口 -> Docker 转发 -> 容器 8000 |
| app -> Redis/MySQL | app 容器里的进程 | Docker 网络 -> 服务名 -> 目标容器端口 |
| 容器 -> 宿主机 | 容器里的进程 | `host.docker.internal` 等特殊地址 |

本课回答五个问题：

1. 容器里的 8000 和宿主机的 8000 是什么关系？
2. `-p 8080:8000` 中左右两个端口分别是什么？
3. app 为什么不写 `127.0.0.1:6379`，而要写 `takeout-redis:6379`？
4. 多个容器都监听 6379，为什么不会冲突？
5. 容器里的 `localhost` 为什么不是宿主机？

## 2. 容器的网络世界

### 2.1 每个容器有自己的网络命名空间

**网络命名空间**是 Linux 提供的网络隔离环境。每个容器有自己的一套网卡、IP 和端口空间：

```text
宿主机
├── takeout-api 容器网络命名空间
│   └── 8000
├── takeout-redis 容器网络命名空间
│   └── 6379
└── takeout-mysql 容器网络命名空间
    └── 3306
```

所以容器里的 `8000`、`6379`、`3306` 都是**容器内部**的端口，不是宿主机的端口。宿主机默认访问不到它们。

### 2.2 容器 IP 会变，不要写死

容器在 Docker 网络里会分到一个 IP，例如：

```text
takeout-redis  172.18.0.2
takeout-mysql  172.18.0.3
takeout-api    172.18.0.4
```

但这些 IP 在容器重建后可能变化。把 IP 写进代码，下次重建就失效。稳定做法是：

```text
宿主机访问容器 -> 端口映射
容器访问容器   -> 自定义网络 + 服务名
```

## 3. 端口映射：让用户访问 app

### 3.1 没有端口映射时

app 容器在内部监听 8000：

```bash
docker run -d --name takeout-api --network takeout-net takeout-api:1
# 没有 -p，宿主机访问不到 app
```

从宿主机访问：

```bash
curl http://127.0.0.1:8000/
```

结果：

```text
Connection refused
```

但 app 其实还在容器里正常运行，只是宿主机没有门进去。

### 3.2 加上端口映射

```bash
docker run -d --name takeout-api --network takeout-net -p 8080:8000 takeout-api:1
# 宿主机 8080 -> 容器 8000
```

数据路径：

```text
浏览器/curl
    -> 宿主机 127.0.0.1:8080
    -> Docker 转发
    -> takeout-api 容器 8000
    -> app 处理请求
    -> 结果原路返回
```

`-p` 的格式是 **宿主机端口 : 容器端口**：

```text
-p 8080:8000
   左侧 8080：宿主机上的入口
   右侧 8000：容器内部 app 监听的端口
```

这里故意让两侧不同：**8080 是宿主机的门，8000 是容器里的门**。如果写成 `-p 8000:8000`，两个数字相同，容易误以为容器和宿主机共用了同一个端口。

查看映射：

```bash
docker port takeout-api
# 8000/tcp -> 0.0.0.0:8080

docker ps
# PORTS 列会显示 0.0.0.0:8080->8000/tcp
```

### 3.3 只暴露 app，不暴露 MySQL/Redis

生产环境一般只把 app 暴露到公网：

```text
公网开放：
    80/443 或 app 的端口

不开放：
    6379（Redis）
    3306（MySQL）
```

原因：

- 数据库/缓存只需要被 app 访问，不需要被用户直接访问；
- 暴露 3306/6379 会增加攻击面；
- 云服务器安全组和 Docker 端口映射都应该只开放必要的入口。

所以启动 Redis/MySQL 时通常不写 `-p`，只把它们加入 app 所在的网络。

### 3.4 本地调试 Redis

如果确实需要从宿主机调试 Redis，不要绑定到 `0.0.0.0`，只绑定回环地址：

```bash
docker run -d --name takeout-redis-debug --network takeout-net -p 127.0.0.1:6380:6379 redis:7
# 只有本机 127.0.0.1:6380 能访问，局域网其他机器访问不到
```

查看映射：

```bash
docker port takeout-redis-debug
# 6379/tcp -> 127.0.0.1:6380
```

从宿主机测试 TCP：

```bash
python -c "import socket; socket.create_connection(('127.0.0.1', 6380), 3); print('redis host port ok')"
```

这里宿主机用 6380，容器内部仍然是 6379，两者独立。

### 3.5 公网访问的完整链路

假设：

```text
云服务器公网 IP：184.1.0.3
app 容器名：takeout-api
启动参数：-p 8001:8000
```

启动命令：

```bash
docker run -d --name takeout-api --network takeout-net -p 8001:8000 takeout-api:1
# 宿主机 8001 -> 容器 8000
```

完整链路：

```text
用户浏览器
    -> http://184.1.0.3:8001/
    -> 云安全组放行 TCP 8001
    -> 云服务器网卡 8001
    -> Docker 端口发布规则（NAT / 转发）
    -> takeout-net 网络
    -> takeout-api 容器 8000
    -> app 进程处理请求
    -> 响应原路返回
```

几个关键点：

- 公网用户访问的是 **8001**，不是 8000；
- app 容器里仍然监听 **8000**，代码不需要改；
- `8001` 是宿主机端口，`8000` 是容器端口；
- 云安全组必须放行 TCP 8001，否则外部访问会超时；
- app 必须监听 `0.0.0.0:8000`，不能只监听容器内的 `127.0.0.1:8000`，否则 Docker 转发不进去；
- `-p 8001:8000` 默认绑定 `0.0.0.0`；如果只想让本机 Nginx 访问，写 `-p 127.0.0.1:8001:8000`。

在服务器上验证：

```bash
docker ps
# PORTS 列应看到 0.0.0.0:8001->8000/tcp

docker port takeout-api
# 8000/tcp -> 0.0.0.0:8001

curl http://127.0.0.1:8001/
# 在服务器本机验证
```

从你的电脑验证：

```bash
curl http://184.1.0.3:8001/
# 需要云安全组放行 8001
```

app 访问 Redis/MySQL 不走这条公网链路：

```text
takeout-api 容器
    -> takeout-redis:6379   （Docker 内部网络）
    -> takeout-mysql:3306   （Docker 内部网络）
```

Redis/MySQL 不需要发布 6379/3306，也不需要公网 IP。

常见故障：

| 现象 | 可能原因 |
|---|---|
| `Connection refused` | 容器没运行、宿主机 8001 没监听、app 没监听 8000、app 只绑定了容器内 127.0.0.1 |
| 请求超时 | 云安全组/系统防火墙没放行 8001，或公网 IP/EIP 没关联到这台服务器 |
| 404 / 502 | 请求已经到了 app 或反向代理，但路径/上游配置不对 |

生产环境通常再加一层 Nginx：

```text
用户 -> 184.1.0.3:443（HTTPS）
    -> Nginx
    -> takeout-api:8000
```

这时公网只开放 80/443，app 的 8000 不必直接暴露；MySQL/Redis 始终只在内网。

## 4. 容器之间：app 访问 Redis/MySQL

### 4.1 默认 bridge 网络的问题

不指定网络时，容器会加入 Docker 默认 bridge 网络。它们可以通过容器 IP 通信，但：

```text
容器 IP 会变，不能写死
默认 bridge 不提供按容器名自动解析
```

所以 app 里写 `172.18.0.2:6379` 不可靠，写 `127.0.0.1:6379` 更不对——容器里的 `127.0.0.1` 是 app 自己。

### 4.2 自定义网络与服务名

创建一个自定义 bridge 网络：

```bash
docker network create takeout-net
```

把 Redis、MySQL、app 都加入这个网络：

```bash
docker run -d --name takeout-redis --network takeout-net redis:7
# Redis 服务容器；不发布端口

docker run -d --name takeout-mysql --network takeout-net -e MYSQL_ROOT_PASSWORD=example -e MYSQL_DATABASE=takeout -v mysql-data:/var/lib/mysql mysql:8
# MySQL 服务容器；不发布端口，数据挂到 volume

docker run -d --name takeout-api --network takeout-net -p 8080:8000 -e REDIS_HOST=takeout-redis -e MYSQL_HOST=takeout-mysql takeout-api:1
# app 容器；只发布 8080，配置里用服务名
```

在同一个自定义网络里，Docker 提供 DNS 解析：容器可以用**容器名**作为主机名访问另一个容器。

所以 app 的配置是：

```text
REDIS_HOST=takeout-redis
MYSQL_HOST=takeout-mysql
```

对应端口：

```text
Redis: takeout-redis:6379
MySQL: takeout-mysql:3306
```

不是 `127.0.0.1`，也不是容器 IP。

本课示例的 `takeout-api` 还没有实现 Redis/MySQL 客户端，`REDIS_HOST` / `MYSQL_HOST` 先作为配置演示；下面用 Python 的 socket 验证网络和 DNS，第 7 课会把它们接到真实代码。

### 4.3 验证 app 能解析并连接 Redis/MySQL

本课示例 app 还没有真正读写 Redis/MySQL，但可以先验证网络和 DNS：

```bash
docker exec takeout-api python -c "import socket; print(socket.gethostbyname('takeout-redis'))"
# 输出 takeout-redis 的容器 IP

docker exec takeout-api python -c "import socket; socket.create_connection(('takeout-redis', 6379), 3); print('redis tcp ok')"
# 能建立 TCP 连接，说明 DNS 和网络都通

docker exec takeout-api python -c "import socket; socket.create_connection(('takeout-mysql', 3306), 5); print('mysql tcp ok')"
# MySQL 启动完成后，TCP 连接应该成功
```

这里只验证 TCP 连通性，不做 Redis 命令或 MySQL 登录；真实业务代码会使用客户端库。

也可以用临时客户端容器验证：

```bash
docker run --rm --network takeout-net redis:7 redis-cli -h takeout-redis ping
# PONG
```

这条命令拆开看：

| 部分 | 含义 |
|---|---|
| `docker run --rm ... redis:7` | 启动一个临时 Redis 客户端容器 |
| `redis-cli` | Redis 命令行客户端 |
| `-h takeout-redis` | `redis-cli` 的 host 参数：连接 `takeout-redis` 这个主机名 |
| `-p 6379` | 端口参数，这里省略，默认 6379 |
| `ping` | 发给 Redis 的命令 |

`-h` 是 **host**，不是 Docker 的 `docker run -h`（那个是设置容器 hostname）。`redis-cli` 不写 `-h` 时默认连 `127.0.0.1`；在临时客户端容器里，`127.0.0.1` 是客户端自己，找不到 Redis，所以这里必须写 `-h takeout-redis`。

这个临时客户端不必是 Redis 镜像；任何带 `redis-cli` 的镜像都可以。这里用 `redis:7` 只是因为它自带 `redis-cli`。

注意：`redis:7` 默认启动 `redis-server`，但传入 `redis-cli` 后，启动的是客户端进程，不是第二个 Redis 服务端，也不会监听 6379。

### 4.4 为什么多个容器都能监听 6379

每个容器有独立的网络命名空间和 IP：

```text
takeout-redis        172.18.0.2:6379
takeout-redis-debug  172.18.0.5:6379
takeout-api          172.18.0.4:随机源端口 -> takeout-redis:6379
```

6379 是容器内部端口，两个 Redis 容器各自在自己的命名空间里监听 6379，互不冲突。

真正会冲突的是**宿主机端口**：

```bash
docker run -p 6379:6379 redis:7
docker run -p 6379:6379 redis:7
# 第二个失败：宿主机 6379 已被占用
```

这时把左侧宿主机端口改成不同值：

```bash
docker run -p 6380:6379 redis:7
docker run -p 6381:6379 redis:7
```

容器内部的 6379 可以保持不变。

还有两个例外：

- 容器名冲突：同一个网络里不能有两个同名容器，这和端口无关；
- `--network host`：在 Linux 上共享宿主机网络命名空间，容器里的 6379 就是宿主机的 6379，这时会冲突。

## 5. 从容器访问宿主机

容器里的 `localhost` / `127.0.0.1` 指的是**容器自己**，不是你的 Windows 或云服务器。

如果 app 容器需要访问宿主机上的服务，例如本机启动的 mock API，需要先认识几个特殊名字。

### 5.1 参数、例子与写法

三个名字的含义：

| 名称 | 含义 |
|---|---|
| `host.docker.internal` | 访问宿主机的主机名 |
| `--add-host` | `docker run` 参数，往容器 `/etc/hosts` 加记录 |
| `host-gateway` | Docker 特殊值，解析成宿主机网关 IP |

`--add-host` 格式：

```text
--add-host=主机名:地址
```

例子：

```bash
docker run --rm --add-host=host.docker.internal:host-gateway alpine cat /etc/hosts
# 输出里多一行，类似：172.17.0.1 host.docker.internal
```

`host-gateway` 不是真实 IP，Docker 创建容器时会替换成宿主机网关（需要 Docker 20.10+）。

Docker Desktop 通常默认已有 `host.docker.internal`；Linux 上需要显式加 `--add-host=host.docker.internal:host-gateway`。Compose 里对应 `extra_hosts`。

app 要访问宿主机 9000 端口的服务时写：

```text
http://host.docker.internal:9000
```

不要写 `http://localhost:9000`，那是容器自己。这种方式只用于本地调试；生产环境走 Docker 网络或明确的外部地址。

## 6. 网络模式

Docker 常见网络模式：

| 模式 | 含义 | 典型用途 |
|---|---|---|
| `bridge` | 默认模式，容器有独立网络命名空间，通过虚拟网桥通信 | 大多数单机容器 |
| `host` | 容器直接使用宿主机网络，不再有独立端口空间 | 对网络性能敏感、或需要直接使用宿主端口的场景 |
| `none` | 容器没有网络接口 | 完全隔离的批处理任务 |

`host` 模式下不需要 `-p`，容器里的端口就是宿主机的端口，但也更容易和宿主机服务冲突；Docker Desktop 对 host 模式的支持与平台有关，学习阶段优先用 `bridge` + `-p`。

## 7. 环境变量与配置

app 需要知道 Redis/MySQL 在哪里，通常通过环境变量传入：

```bash
docker run -d --name takeout-api --network takeout-net -p 8080:8000 -e REDIS_HOST=takeout-redis -e MYSQL_HOST=takeout-mysql takeout-api:1
# -e 传入环境变量；值必须是服务名，不是 127.0.0.1
```

参数较多时，用 `--env-file`：

```text
# takeout.env
APP_ENV=dev
REDIS_HOST=takeout-redis
MYSQL_HOST=takeout-mysql
```

```bash
docker run -d --name takeout-api --network takeout-net -p 8080:8000 --env-file takeout.env takeout-api:1
```

注意：

- 环境变量会出现在 `docker inspect` 和容器进程环境里，不适合高敏感密钥；
- 数据库密码不要写进镜像，运行时用环境变量、`--env-file` 或 secrets；
- app 镜像里安装 `redis`、`pymysql` 这类**客户端库**，不安装 Redis/MySQL 服务器。

## 8. 环境切换综述

到这一课，切换环境有四种手段：

```text
换 tag       -> 换镜像版本，见第 2 课
换容器       -> 同一个镜像起多个实例，见第 2 课
换宿主机端口 -> 同一个容器换一个对外入口，本课第 3 节
换网络       -> 容器加入不同网络，决定它能和谁通信，本课第 4 节
```

例如同一个 `takeout-api:1` 起两个容器：

```bash
docker run -d --name takeout-api-a --network takeout-net -p 8080:8000 takeout-api:1
docker run -d --name takeout-api-b --network takeout-net -p 8081:8000 takeout-api:1
```

两个 app 容器内部都监听 8000，宿主机分别用 8080/8081 访问，互不冲突。

## 9. 本课命令速查表

| 命令 | 含义 | 参数说明 |
|---|---|---|
| `docker run -p 宿主机:容器 镜像` | 创建容器并发布端口 | 左侧宿主机端口，右侧容器端口 |
| `docker port 容器` | 查看容器端口映射 | — |
| `docker network create 网络名` | 创建自定义 bridge 网络 | — |
| `docker run --network 网络名 镜像` | 让容器加入指定网络 | 同一网络内可用容器名互访 |
| `docker network inspect 网络名` | 查看网络详情 | 可看到容器、子网、网关 |
| `docker network rm 网络名` | 删除网络 | 先移除使用它的容器 |
| `docker run -e KEY=VALUE 镜像` | 传入环境变量 | 可重复使用多个 `-e` |
| `docker run --env-file 文件 镜像` | 从文件读取环境变量 | 每行一个 `KEY=VALUE` |
| `docker run --add-host 名称:地址 镜像` | 向容器 hosts 添加记录 | 常用于 `host.docker.internal:host-gateway` |

## 10. 完整练习：把外卖系统的网络接起来

```bash
# 1. 创建自定义网络
docker network create takeout-net

# 2. 启动 Redis（不发布端口）
docker run -d --name takeout-redis --network takeout-net redis:7

# 3. 启动 MySQL（不发布端口，数据挂 volume）
docker run -d --name takeout-mysql --network takeout-net -e MYSQL_ROOT_PASSWORD=example -e MYSQL_DATABASE=takeout -v mysql-data:/var/lib/mysql mysql:8

# 4. 等 MySQL 可用；第一次启动可能要十几秒，失败就重复执行
docker exec takeout-mysql mysqladmin -uroot -pexample ping

# 5. 启动 app（只发布 8080）
docker run -d --name takeout-api --network takeout-net -p 8080:8000 -e REDIS_HOST=takeout-redis -e MYSQL_HOST=takeout-mysql takeout-api:1

# 6. 从宿主机访问 app
curl http://127.0.0.1:8080/
curl http://127.0.0.1:8080/health

# 7. 查看端口映射
docker port takeout-api

# 8. 验证 app 能解析并连接 Redis/MySQL
docker exec takeout-api python -c "import socket; print(socket.gethostbyname('takeout-redis'))"
docker exec takeout-api python -c "import socket; socket.create_connection(('takeout-redis', 6379), 3); print('redis tcp ok')"
docker exec takeout-api python -c "import socket; socket.create_connection(('takeout-mysql', 3306), 5); print('mysql tcp ok')"

# 9. 用临时客户端访问 Redis
docker run --rm --network takeout-net redis:7 redis-cli -h takeout-redis ping

# 10. 本地调试 Redis：只绑定回环地址
docker run -d --name takeout-redis-debug --network takeout-net -p 127.0.0.1:6380:6379 redis:7
docker port takeout-redis-debug
python -c "import socket; socket.create_connection(('127.0.0.1', 6380), 3); print('redis host port ok')"

# 11. 查看网络中的容器和 IP
docker network inspect takeout-net

# 12. 清理
docker rm -f takeout-api takeout-redis-debug takeout-redis takeout-mysql
docker network rm takeout-net
```

如果 `takeout-api:1` 还没构建：

```bash
docker build -f code/docker/03-app.Dockerfile -t takeout-api:1 code/docker
```

练习结论：

```text
宿主机访问 app：8080 -> Docker 转发 -> 容器 8000
app 访问 Redis：takeout-redis:6379（自定义网络 DNS）
app 访问 MySQL：takeout-mysql:3306（自定义网络 DNS）
容器内部端口可以重复，宿主机端口必须唯一
```

## 11. 常见错误

### 11.1 端口写反了

```text
-p 8000:8080
```

这表示"宿主机 8000 -> 容器 8080"，不是"宿主机 8080 -> 容器 8000"。如果 app 在容器里监听 8000，正确写法是 `-p 8080:8000`。

### 11.2 宿主机端口被占用

```text
Bind for 0.0.0.0:8080 failed: port is already allocated
```

宿主机端口必须唯一。换一个左侧端口，或者删除占用它的旧容器。

### 11.3 app 容器里写 `localhost`

```text
REDIS_HOST=127.0.0.1
MYSQL_HOST=127.0.0.1
```

容器里的 `127.0.0.1` 是 app 自己，不是 Redis/MySQL。正确写法是服务名：

```text
REDIS_HOST=takeout-redis
MYSQL_HOST=takeout-mysql
```

### 11.4 默认 bridge 网络里用容器名访问

默认 bridge 不提供按容器名自动解析。把容器加入自定义网络：

```bash
docker network create takeout-net
docker run --network takeout-net ...
```

### 11.5 用容器 IP 连接

容器 IP 会随重建变化，不适合写死。宿主机访问用端口映射，容器之间访问用服务名。

### 11.6 把 MySQL/Redis 暴露到公网

```bash
docker run -p 3306:3306 mysql:8
docker run -p 6379:6379 redis:7
```

除非确实需要，否则不要这样做。数据库/缓存只给 app 容器访问；本地调试只绑定 `127.0.0.1`。

### 11.7 `--network host` 导致端口冲突

host 模式共享宿主机网络命名空间，容器里的端口就是宿主机端口。两个 host 模式容器都想用 8080 时会冲突。

## 14. 面试高频考点

### 14.1 端口映射是怎么工作的？

> 容器里的服务监听容器内部端口，容器外面的世界默认访问不到。`-p 宿主机端口:容器端口` 把两者连起来，例如 `-p 8080:8000`：发到宿主机 8080 的数据被 Docker 转发到容器的 8000，结果再原路返回。没有映射时，从宿主机连接会 `Connection refused`，但容器里的服务仍在运行。

### 14.2 容器之间怎么通信？

> 把容器加入同一个自定义 bridge 网络，Docker 会提供 DNS 解析，容器可以用容器名作为主机名访问彼此。默认 bridge 网络不提供按容器名自动解析，而且容器 IP 会变化，所以生产上更常用自定义网络或编排系统提供的服务发现。

### 14.3 为什么用服务名而不是容器 IP？

> 容器 IP 会随容器重建变化，写死 IP 很容易失效；服务名由 Docker DNS 解析到当前容器 IP，重建后仍然可用。自定义网络里的容器名就是稳定的服务名。

### 14.4 为什么多个容器可以都监听 6379？

> 每个容器有独立的网络命名空间和 IP，6379 只是容器内部端口；两个容器可以各自在自己的命名空间里监听 6379，客户端通过容器名或 IP 访问。会冲突的是宿主机端口：如果两个容器都用 `-p 6379:6379` 发布到宿主机 6379，第二个就会失败。`--network host` 是例外，它共享宿主机网络命名空间，容器端口就是宿主机端口。

### 14.5 bridge 和 host 网络有什么区别？

> bridge 模式下容器有独立网络命名空间，通过虚拟网桥和端口映射与外界通信；host 模式下容器直接使用宿主机网络，容器端口就是宿主机端口，不需要 `-p`，但更容易发生端口冲突。单机开发通常用 bridge。

### 14.6 `host.docker.internal` 是做什么的？

> 它让容器通过一个固定主机名访问宿主机。容器里的 `localhost` 指的是容器自己，不是宿主机；要调用宿主机上的服务，应使用 `host.docker.internal`。

### 14.7 为什么 MySQL/Redis 不暴露到公网？

> 它们只需要被 app 容器访问，不需要被用户直接访问。暴露 3306/6379 会增加攻击面；正确做法是让它们加入 app 所在的自定义网络，不发布宿主机端口，云服务器安全组也只开放 app 需要的端口。

### 14.8 环境变量和 secret 有什么区别？

> 环境变量适合普通配置，但会出现在 `docker inspect` 和容器进程环境里，不适合高敏感密钥。Secret 通过专门的机制挂载或注入，权限更小，适合密码、Token 等。无论哪种，都不要把密钥写进镜像。
