# 第4课:数据卷与持久化

> 第 3 课把 `takeout-api` 构建成了镜像。真实的外卖系统还要把订单写进 MySQL、把缓存放进 Redis。容器可以随时删除重建，但订单数据不能跟着容器一起消失。
>
> 这一课解决"数据放在哪里"：先看容器可写层为什么会丢数据，再讲 volume、bind mount、权限、备份和恢复。示例继续使用外卖系统的 MySQL 和 Redis。

## 1. 场景：容器删了，订单还在吗

外卖系统的数据分布在两个地方：

```text
takeout-api 容器
    ├── 写订单、查订单 -> mysql 容器（/var/lib/mysql）
    └── 读写缓存/队列 -> redis 容器（/data）
```

如果 MySQL 容器这样启动：

```bash
docker run -d --name mysql mysql:8
# 没有挂载任何数据目录
```

那么订单数据会写在容器自己的可写层里：

```text
mysql 容器
├── 镜像只读层
├── 可写层
│   └── /var/lib/mysql/...   <- 订单数据在这里
└── 删除容器
    -> 可写层一起删除
    -> 订单数据消失
```

镜像本身不会消失，但容器里的数据没了。`docker rm` 删除的是容器，不是镜像；可写层属于容器，所以跟着容器一起删除。

这一课要解决的问题：

```text
怎样把 /var/lib/mysql、/data 放到容器生命周期之外？
volume 和 bind mount 有什么区别？
为什么数据库推荐 named volume？
挂载后权限不对怎么办？
怎样备份和恢复？
```

## 2. 容器可写层与数据卷

### 2.1 容器可写层

先定义"层"：层不是运行状态，也不是一块内存，而是**磁盘上的一组文件系统差异**。可以把它想成一叠透明胶片：

```text
镜像层     = 一张只读的透明胶片，只记录自己新增、修改或删除了哪些文件
容器可写层 = 最上面一张可擦写的透明胶片，记录容器运行时的修改
```

一叠胶片叠加在一起，才是一张完整的图。Docker 把多层文件系统叠加后，容器里的进程看到的是一个完整的 Linux 根目录；底层文件没有被改写，只是被上层补充或遮住。

- **镜像层**：只读，构建时生成，多个容器可以共享；
- **可写层**：每个容器独有，容器运行时写文件进入这里，容器删除就没了；
- **位置**：层在磁盘上，不在内存里；进程的变量、栈、堆才在内存里；
- **状态**：`running` / `exited` 是容器的生命周期状态，层是存储结构，两者不是一回事。

镜像由多个只读层组成。容器启动时，Docker 在镜像上面加一个**可写层**：

```text
容器
├── 可写层（容器自己的修改）
├── 镜像层 3（只读）
├── 镜像层 2（只读）
└── 镜像层 1（只读）
```

容器里的进程写文件时，数据进入可写层。特点：

- 可写层只属于这个容器；
- 删除容器，可写层一起删除；
- 用同一个镜像重新启动一个新容器，得到的是全新的可写层；
- 镜像层不会被容器修改，所以删容器不会删镜像。

观察镜像层和可写层：

```bash
docker history redis:7
# 从下往上看：基础层 -> 安装层 -> ...
# 每一行对应镜像构建时的一层

docker run -d --name layer-demo alpine sleep 300
# 启动一个容器：只读镜像层 + 可写层

docker exec layer-demo sh -c "echo hi > /tmp/demo.txt"
# 在容器里写一个文件，写入可写层

docker diff layer-demo
# A /tmp/demo.txt
# A 表示 added：可写层里多了一个文件

docker rm -f layer-demo
# 可写层随容器删除；镜像层不变
```

`docker commit` 可以把可写层保存成新镜像，但它不适合做数据持久化：镜像会越来越大，数据库文件也不适合反复打包。正式做法是用 volume 或 bind mount。

### 2.2 volume：Docker 管理的持久化目录

**volume** 是 Docker 管理的存储目录，生命周期独立于容器：

```text
容器 A ──挂载──> volume mysql-data <──挂载── 容器 B
```

- volume 由 Docker 创建和管理，默认存放在 Docker 的数据目录里；
- 删除容器不会删除 volume；
- 只有显式 `docker volume rm` 才会删除；
- 适合数据库、Redis 数据、需要长期保留的文件；
- 在 Docker Desktop 上，volume 实际存放在 WSL2 的虚拟磁盘里，不需要你手动找路径。

创建和使用：

```bash
docker volume create mysql-data
# 创建一个 named volume

docker run -d --name mysql -v mysql-data:/var/lib/mysql mysql:8
# 把 volume 挂到容器的 /var/lib/mysql
```

`-v mysql-data:/var/lib/mysql` 中：

```text
mysql-data        -> volume 名字
/var/lib/mysql    -> 容器内路径
```

如果 volume 不存在，`docker run -v` 会自动创建。也可以只写容器路径：

```bash
docker run -d --name redis -v /data redis:7
# 创建一个匿名 volume，名字是随机哈希，不推荐长期使用
```

匿名 volume 也能持久化，但名字不好记，清理时容易误删；正式环境用 named volume。

常用命令：

| 命令 | 含义 |
|---|---|
| `docker volume ls` | 查看所有 volume |
| `docker volume create 名字` | 创建 named volume |
| `docker volume inspect 名字` | 查看挂载点、创建时间等信息 |
| `docker volume rm 名字` | 删除 volume；仍被容器使用时失败 |
| `docker volume prune` | 删除所有未使用的 volume；危险，先确认 |

### 2.3 bind mount：把宿主机目录挂进容器

**bind mount** 直接把宿主机上的一个目录或文件挂到容器里：

```text
宿主机 C:\work\project\...\data
        |
        | bind mount
        v
容器 /var/lib/mysql
```

特点：

- 宿主机路径由你指定；
- 宿主机上的修改会立刻反映到容器里；
- 适合开发时的源码、配置文件、初始化 SQL；
- 宿主机文件权限、UID/GID 会直接影响容器；
- Windows 上把数据库数据目录 bind mount 进 Linux 容器，容易出现权限和文件系统兼容问题。

示例：

```bash
docker run -d --name mysql-bind -e MYSQL_ROOT_PASSWORD=example -v "${PWD}/mysql-data:/var/lib/mysql" mysql:8
# 把当前目录下的 mysql-data 挂到容器的 /var/lib/mysql
```

注意 `-v` 的第一个参数：

```text
mysql-data:/var/lib/mysql           -> named volume（没有斜杠）
${PWD}/mysql-data:/var/lib/mysql    -> bind mount（绝对路径）
C:\data\mysql:/var/lib/mysql        -> bind mount（Windows 绝对路径）
```

`docker run -v` 的 bind mount 要使用绝对路径。写相对路径时，Docker 可能报错，或把它误认为 named volume；不要靠猜，统一用 `${PWD}` 或完整路径。

### 2.4 tmpfs：只放在内存里

**tmpfs** 把数据放在内存里，容器停止就消失：

```bash
docker run --rm --tmpfs /tmp redis:7
```

适合临时文件、缓存；不适合数据库。数据库需要持久化，不用 tmpfs。

### 2.5 三种方式对比

| | named volume | bind mount | tmpfs |
|---|---|---|---|
| 存储位置 | Docker 管理的数据目录 | 宿主机指定路径 | 内存 |
| 生命周期 | 独立于容器，显式删除才消失 | 由宿主机目录决定 | 容器停止即消失 |
| 典型用途 | 数据库、Redis 数据 | 配置、初始化 SQL、开发源码 | 临时文件、缓存 |
| 权限 | Docker/镜像负责初始化 | 宿主机 UID/GID 直接影响 | 内存 |
| 跨平台 | 较好 | Windows/Linux 差异大 | Linux 为主 |
| 数据库推荐 | **推荐** | 不推荐用于数据目录 | 不推荐 |

## 3. 用 volume 持久化 Redis

### 3.1 没有 volume 的情况

启动一个没有挂载的 Redis：

```bash
docker run -d --name redis-no-vol redis:7
# 没有 -v，/data 在容器可写层里
```

写入一条数据，并强制保存到 RDB：

```bash
docker exec -it redis-no-vol redis-cli SET course:persist hello
# 写入一个 key

docker exec -it redis-no-vol redis-cli SAVE
# 立即把内存数据写成 /data/dump.rdb
```

删除容器，再启动一个新的：

```bash
docker rm -f redis-no-vol
# 容器和它的可写层一起删除

docker run -d --name redis-no-vol-2 redis:7
# 新容器，新的可写层

docker exec -it redis-no-vol-2 redis-cli GET course:persist
# 输出 (nil)
```

数据丢了。`SAVE` 只保证数据写进了 `/data/dump.rdb`，但 `/data` 还在旧容器的可写层里，容器删除后一起消失。

### 3.2 加 volume 的情况

创建 named volume，并挂到 Redis 的 `/data`：

```bash
docker volume create redis-data
# 创建 named volume

docker run -d --name redis-vol -v redis-data:/data redis:7
# 把 redis-data 挂到容器的 /data

docker exec -it redis-vol redis-cli SET course:persist hello
# 写入数据

docker exec -it redis-vol redis-cli SAVE
# 写入 /data/dump.rdb，也就是 volume 里
```

删除容器，再用同一个 volume 启动新容器：

```bash
docker rm -f redis-vol
# 容器删除，但 redis-data 还在

docker run -d --name redis-vol-2 -v redis-data:/data redis:7
# 新容器挂同一个 volume

docker exec -it redis-vol-2 redis-cli GET course:persist
# 输出 "hello"
```

数据还在。Redis 启动时会读取 `/data/dump.rdb`，所以新容器能恢复数据。

查看 volume：

```bash
docker volume ls
docker volume inspect redis-data
# Mountpoint 是 Docker 管理的路径；在 Docker Desktop 上位于 WSL2 虚拟磁盘里
```

### 3.3 清理

```bash
docker rm -f redis-vol-2
# 先删除使用 volume 的容器

docker volume rm redis-data
# 再删除 volume；确认数据不再需要
```

如果 volume 仍被容器使用，`docker volume rm` 会失败。先删除容器，再删 volume。

## 4. 用 volume 持久化 MySQL 订单

### 4.1 启动 MySQL：named volume + 初始化 SQL

外卖系统的订单表需要在 MySQL 第一次初始化时创建。示例脚本在 `code/docker/04-init.sql`：

```sql
CREATE DATABASE IF NOT EXISTS takeout;
USE takeout;

CREATE TABLE IF NOT EXISTS orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10, 2) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'created',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO orders (user_id, amount, status)
VALUES (1, 38.50, 'created');
```

启动 MySQL：

```bash
docker run -d --name mysql-vol -e MYSQL_ROOT_PASSWORD=example -e MYSQL_DATABASE=takeout -v mysql-data:/var/lib/mysql --mount type=bind,source="${PWD}/code/docker/04-init.sql",target=/docker-entrypoint-initdb.d/init.sql,readonly mysql:8
# -e MYSQL_ROOT_PASSWORD：root 密码
# -e MYSQL_DATABASE：初始化时创建 takeout 数据库
# -v mysql-data:/var/lib/mysql：订单数据放进 named volume
# --mount type=bind,...：把宿主机上的初始化 SQL 只读挂进容器
```

这条命令同时用了两种挂载：

```text
mysql-data:/var/lib/mysql
    -> named volume，保存订单数据

${PWD}/code/docker/04-init.sql
    -> bind mount，提供初始化脚本
```

等 MySQL 初始化完成：

```bash
docker ps
# 看 mysql-vol 是否 Up

docker logs mysql-vol
# 看初始化日志；第一次启动会执行 04-init.sql

docker exec mysql-vol mysqladmin -uroot -pexample ping
# 返回 "mysqld is alive" 说明服务可用
```

MySQL 第一次启动需要初始化数据目录，可能要等十几秒；`mysqladmin ping` 失败时先看日志，不要立刻删除容器。

### 4.2 验证订单数据

```bash
docker exec -it mysql-vol mysql -uroot -pexample takeout -e "SELECT * FROM orders;"
# 应该看到 04-init.sql 插入的那条订单
```

### 4.3 删除容器，用同一个 volume 重建

```bash
docker rm -f mysql-vol
# 删除容器；mysql-data 还在

docker run -d --name mysql-vol-2 -e MYSQL_ROOT_PASSWORD=example -e MYSQL_DATABASE=takeout -v mysql-data:/var/lib/mysql mysql:8
# 新容器挂同一个 volume；这次不需要再挂初始化 SQL

docker exec mysql-vol-2 mysqladmin -uroot -pexample ping
# 等服务可用

docker exec -it mysql-vol-2 mysql -uroot -pexample takeout -e "SELECT * FROM orders;"
# 订单还在
```

关键点：

- 初始化 SQL 只在**数据目录为空**时执行；
- `mysql-data` 里已经有数据，所以第二次启动不会重新执行 `04-init.sql`；
- 如果第二次启动仍然挂初始化 SQL，也不会重复插入，因为初始化阶段已经跳过；
- 想重新初始化，只能删除 volume（会丢数据）或换一个新的 volume 名字。

### 4.4 named volume 的初始化与权限

第一次把空 volume 挂到 `/var/lib/mysql` 时，Docker 会把镜像里该目录的内容复制到 volume 里，MySQL 初始化时再写入数据。镜像里的 `mysql` 用户通常有正确的属主，所以 named volume 一般不需要你手动改权限。

如果把宿主机空目录 bind mount 到 `/var/lib/mysql`，权限可能不对：

```text
宿主机目录属于 Windows 用户
    -> 容器里的 mysql 用户（通常是 UID 999）无法写入
    -> MySQL 启动失败或报 Permission denied
```

所以数据库数据目录优先用 named volume。bind mount 更适合放初始化 SQL、配置文件这类只读内容。

## 5. 用 bind mount 挂配置和初始化脚本

### 5.1 什么时候用 bind mount

适合：

- 初始化 SQL：`/docker-entrypoint-initdb.d/*.sql`；
- Nginx、Redis、MySQL 的配置文件；
- 开发时把源码挂进容器，修改后立即生效；
- 需要从宿主机直接查看或编辑的文件。

不适合：

- MySQL/Redis 的数据目录（权限和文件系统差异）；
- 需要跨平台可复现的生产数据；
- 需要 Docker 管理生命周期的数据。

### 5.2 `-v` 与 `--mount`

两种写法都能挂载，但语义清晰度不同：

```bash
# 简写：适合日常命令
docker run -v mysql-data:/var/lib/mysql mysql:8

# 显式写法：适合脚本和生产
docker run --mount type=volume,source=mysql-data,target=/var/lib/mysql mysql:8

# bind mount 简写
docker run -v "${PWD}/04-init.sql:/docker-entrypoint-initdb.d/init.sql:ro" mysql:8

# bind mount 显式写法
docker run --mount type=bind,source="${PWD}/04-init.sql",target=/docker-entrypoint-initdb.d/init.sql,readonly mysql:8
```

| 写法 | 特点 |
|---|---|
| `-v` | 简短；源路径不存在时可能自动创建目录；相对路径容易混淆 |
| `--mount` | 参数名明确；源路径不存在时直接报错；更适合脚本 |

`--mount` 的常用参数：

```text
type=volume|bind|tmpfs   挂载类型
source=...               源：volume 名字或宿主机路径
target=...               容器内路径
readonly                 只读
```

### 5.3 Windows 路径与 `${PWD}`

在 PowerShell 中，`${PWD}` 表示当前目录；CMD 里对应的是 `%cd%`：

```powershell
docker run --rm --mount type=bind,source="${PWD}/code/docker/04-init.sql",target=/init.sql,readonly alpine cat /init.sql
# 用当前目录拼出绝对路径；避免相对路径歧义
```

注意：

- bind mount 的 source 最好用绝对路径；
- Windows 路径包含反斜杠，Docker Desktop 会处理，但路径中有空格时要加引号；
- 不要把 `C:\...` 写成容器内路径；容器内路径是 `/...`。

## 6. 备份与恢复

### 6.1 MySQL 逻辑备份

不要直接复制正在运行的 `/var/lib/mysql` 文件：数据库可能正在写，复制出来的文件不一致。

用 `mysqldump` 做逻辑备份：

```bash
docker exec mysql-vol-2 mysqldump -uroot -pexample takeout --result-file=/tmp/takeout.sql
# 在容器里生成 SQL 备份

docker cp mysql-vol-2:/tmp/takeout.sql .\takeout.sql
# 把备份文件复制到宿主机
```

恢复：

```bash
docker cp .\takeout.sql mysql-vol-2:/tmp/takeout.sql
# 把备份文件放回容器

docker exec mysql-vol-2 sh -c "mysql -uroot -pexample takeout < /tmp/takeout.sql"
# 在容器内执行恢复；< 由容器里的 sh 处理
```

恢复前最好先确认目标库和表的状态；生产环境还要考虑备份文件版本、字符集和权限。

### 6.2 volume 原始备份

如果确实要备份整个 volume，先停止数据库，避免文件不一致：

```bash
docker stop mysql-vol-2
# 停止写入

docker run --rm -v mysql-data:/data -v "${PWD}:/backup" alpine tar czf /backup/mysql-data.tar.gz -C /data .
# 用临时 Alpine 容器把 volume 打包到宿主机
```

恢复时只能恢复到空 volume，并且要先停止使用它的容器。原始备份适合整库迁移，不适合日常增量备份。

### 6.3 Redis 持久化

Redis 默认使用 RDB：

```text
/data/dump.rdb   <- Redis 的快照文件
```

常用命令：

```bash
docker exec redis-vol-2 redis-cli SAVE
# 同步保存；数据量大时会阻塞

docker exec redis-vol-2 redis-cli BGSAVE
# 后台保存；返回 Background saving started
```

备份时确认 `dump.rdb` 已经写入 volume，再复制文件。Redis 也支持 AOF，适合更高频率的持久化；本课程只要求知道 RDB 和 AOF 都是把数据写到 `/data`，真正持久化仍要靠 volume。

## 7. 清理与常见错误

### 7.1 删除容器后数据没了

原因：数据写在容器可写层，没有挂 volume。检查 `docker run` 是否有 `-v` 或 `--mount`，以及挂载的容器路径是否正确。

### 7.2 `-v` 路径写错，挂载类型变了

```text
-v mysql-data:/var/lib/mysql          -> named volume，名字是 mysql-data
-v "${PWD}/mysql-data:/var/lib/mysql" -> bind mount，宿主机当前目录下
```

少写斜杠会改变挂载类型；相对路径不可靠，可能报错或被误认为 named volume。bind mount 用绝对路径，并用 `docker inspect 容器` 查看 `Mounts` 字段确认。

### 7.3 MySQL 初始化 SQL 没有执行

`/docker-entrypoint-initdb.d/` 里的脚本只在数据目录为空时执行。如果 `mysql-data` 已经有数据，新增或修改初始化 SQL 不会生效。需要新 volume 才能重新初始化。

### 7.4 `Permission denied`

bind mount 的宿主机目录权限不对，容器里的 mysql/redis 用户无法写入。优先改用 named volume；必须用 bind mount 时，确认目录属主，不要用 `chmod 777` 糊弄。

### 7.5 `docker volume rm` 失败

volume 仍被容器引用。先 `docker rm` 停掉并删除使用它的容器，再删 volume。

### 7.6 `docker compose down -v` 删除了数据

`down -v` 会删除 Compose 文件里声明的 volume。只想停止服务时用 `docker compose down`；确认数据不再需要时才加 `-v`。

### 7.7 直接复制运行中的 MySQL 数据文件

运行中的数据库文件可能处于不一致状态。备份用 `mysqldump`，或先停容器再复制 volume。

## 8. 完整练习

```bash
# 1. Redis：没有 volume，删除容器后数据丢失
docker run -d --name redis-no-vol redis:7
docker exec -it redis-no-vol redis-cli SET course:persist hello
docker exec -it redis-no-vol redis-cli SAVE
docker rm -f redis-no-vol
docker run -d --name redis-no-vol-2 redis:7
docker exec -it redis-no-vol-2 redis-cli GET course:persist
# 预期：(nil)
docker rm -f redis-no-vol-2

# 2. Redis：使用 named volume
docker volume create redis-data
docker run -d --name redis-vol -v redis-data:/data redis:7
docker exec -it redis-vol redis-cli SET course:persist hello
docker exec -it redis-vol redis-cli SAVE
docker rm -f redis-vol
docker run -d --name redis-vol-2 -v redis-data:/data redis:7
```

## 11. 面试高频考点

### 11.1 容器删除后数据为什么丢失？

> 容器启动时在镜像只读层上增加一个可写层，容器写入的文件都在可写层里。删除容器时，可写层一起删除；镜像不受影响。要让数据独立于容器生命周期，需要使用 volume 或 bind mount。

### 11.2 volume 和 bind mount 有什么区别？

> volume 由 Docker 管理，存放在 Docker 的数据目录里，生命周期独立于容器，适合数据库等持久化数据；bind mount 把宿主机上的目录或文件直接挂进容器，适合配置、初始化 SQL 和开发源码，但受宿主机权限和路径影响。数据库数据目录优先用 named volume。

### 11.3 为什么数据库容器必须挂载数据目录？

> 数据库的数据文件在容器内，如果不挂载，数据就在容器可写层里，删除或重建容器会丢失。挂载 volume 后，数据保存在容器生命周期之外，新容器可以继续使用同一份数据。

### 11.4 `-v` 和 `--mount` 有什么区别？

> `-v` 写法简短，但源路径不存在时可能自动创建目录，相对路径和命名 volume 容易混淆；`--mount` 用 `type`、`source`、`target` 明确表达挂载类型，源路径不存在时直接报错，更适合脚本和生产环境。

### 11.5 初始化 SQL 为什么没有执行？

> MySQL 官方镜像只会在数据目录为空、第一次初始化时执行 `/docker-entrypoint-initdb.d/` 下的脚本。如果 volume 里已经有数据，初始化阶段会跳过；要重新执行只能使用新的空 volume，或删除旧 volume（会丢数据）。

### 11.6 bind mount 后为什么会出现 Permission denied？

> bind mount 使用宿主机目录的属主和权限，容器里的 mysql/redis 用户 UID 可能和宿主机用户不一致，无法写入。数据库数据目录优先用 named volume；必须用 bind mount 时要调整目录属主，而不是简单使用 `chmod 777`。

### 11.7 怎样备份 MySQL 容器？

> 使用 `mysqldump` 做逻辑备份，把 SQL 文件写到容器内临时路径，再用 `docker cp` 复制到宿主机；恢复时把 SQL 文件放回容器并用 `mysql` 执行。不要直接复制运行中的 `/var/lib/mysql` 文件，因为可能处于不一致状态。

### 11.8 `docker compose down -v` 有什么风险？

> `down -v` 会删除 Compose 文件中声明的 named volume，数据会丢失。只想停止并删除容器时用 `docker compose down`；确认数据不再需要时才加 `-v`。
