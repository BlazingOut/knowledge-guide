> 第 7 课把外卖系统装进了 Docker，但那是本地开发环境。这一课讲"从本地到生产"的关键环节：镜像怎么交付、怎么保证安全、资源怎么限制、Nginx 怎么接入、容器出问题按什么顺序排查。

## 1. 从本地到生产

第 7 课是本地跑通；生产环境还要多几层：

```text

    -> 云服务器拉取镜像

```

本课按这个链路展开：

## 2. 镜像交付：registry 与 tag

### 2.1 registry 是什么

**registry** 是镜像仓库，用来保存和分发镜像：

```text
Docker Hub        公开的官方仓库，个人可免费使用
云厂商镜像仓库    例如阿里云、腾讯云的私有仓库
自建 registry     例如 Harbor
```

本地构建的镜像要交给云服务器，通常先 push 到 registry，服务器再 pull：

```bash
docker login
# 先登录 registry

docker tag takeout-api:3 你的用户名/takeout-api:1.0.0
# 给镜像打上仓库路径 + 版本号

docker push 你的用户名/takeout-api:1.0.0
# 推送到 registry

docker pull 你的用户名/takeout-api:1.0.0
# 服务器上拉取
```

### 2.2 tag 策略

推荐语义化版本：

```text
takeout-api:1.0.0    具体版本，可复现
takeout-api:1.0      1.0 系列
takeout-api:latest   可变，不推荐用于生产
```

原因：

```text
latest 今天和明天拉到的内容可能不同
出问题时无法确定线上到底跑的是哪个版本
回滚需要精确的版本号
```

生产环境用具体版本或 digest；`latest` 只方便本地开发。

### 2.3 多平台构建（了解即可）

云服务器通常是 linux/amd64。跨平台构建可以用 buildx：

```bash
docker buildx build --platform linux/amd64 --push -t 你的用户名/takeout-api:1.0.0 .
```

本课程不展开；知道"生产镜像要针对服务器架构构建"即可。

## 3. CI 构建与推送

生产镜像不应该在个人电脑上"临时构建、手动推送"，而是交给 CI（持续集成）流水线：

```text
代码推送
    -> CI 检出代码
    -> docker build 构建镜像
    -> 跑测试
    -> 镜像扫描
    -> docker push 到 registry
```

CI 的好处：

- 每次构建环境一致；
- 构建、测试、扫描、推送自动完成；
- 有审计记录，可以回滚到任意版本。

要点：

- 构建一次，测试和部署都用同一个镜像；
- registry 凭据放在 CI 的 secret 里，不写进代码仓库；
- 镜像 tag 用 commit hash 或语义化版本，不用 `latest`。

## 4. 镜像安全与最小权限

### 4.1 扫描

镜像可能带有已知漏洞。用扫描工具检查：

```bash
docker scout cves 你的用户名/takeout-api:1.0.0
# Docker Scout 扫描已知 CVE
```

类似工具还有 Trivy、Snyk、云厂商镜像扫描。扫描结果要结合"是否真的可被利用"判断，不是有 CVE 就一定不能上线。

### 4.2 最小权限

前面第 3 课已经做了非 root。生产还可以更严格：

```bash
docker run --read-only --cap-drop ALL --user app 你的用户名/takeout-api:1.0.0
# --read-only：根文件系统只读
# --cap-drop ALL：去掉容器能力
# --user app：非 root
```

只读文件系统需要给需要写的位置挂 tmpfs 或 volume：

```bash
docker run --read-only --tmpfs /tmp --user app ...
```

原则：

- 尽量用非 root、slim/distroless 基础镜像；
- 不需要的 Linux capability 一律 drop；
- 密钥不写进镜像，运行时注入或使用 secrets；
- 优先用官方维护的镜像。

## 5. 运行策略：资源限制与重启

### 5.1 资源限制

单个容器失控（内存泄漏、死循环）会影响整台服务器。限制资源：

```bash
docker run -d --name takeout-api --memory 512m --cpus 1.0 takeout-api:1
# --memory：内存上限
# --cpus：CPU 配额，1.0 表示一个核
```

Compose 里：

```yaml
services:
  app:
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
```

超过内存上限时，容器会被 OOM 杀掉；这是预期行为，配合重启策略可以自动拉起。

### 5.2 重启策略

```bash
docker run -d --restart unless-stopped ...
```

常用值：

| 策略 | 含义 |
|---|---|
| `no` | 不自动重启 |
| `on-failure` | 非正常退出时重启 |
| `unless-stopped` | 除非手动停止，否则重启（包括开机自启） |
| `always` | 总是重启 |

Compose 里：

```yaml
services:
  app:
    restart: unless-stopped
```

数据库/缓存/API 通常都配 `unless-stopped`。

### 5.3 健康检查

第 3、6 课讲过 `HEALTHCHECK`。生产上健康检查配合重启策略和编排系统，才能实现"挂了自动发现"。

## 6. 日志与磁盘

### 6.1 日志

```bash
docker logs takeout-api
# 看完整日志

docker logs --tail 50 takeout-api
# 看最近 50 行

docker logs --since 10m takeout-api
# 看最近 10 分钟

docker logs -f takeout-api
# 持续跟随
```

Compose：

```bash
docker compose -f code/docker/08-prod-compose.yaml logs -f app
```

默认日志写到 Docker 的 json-file 驱动；生产环境可以换 loki、journald 等，或让应用把日志输出到 stdout 统一收集。

### 6.2 磁盘

```bash
docker system df
# 查看镜像、容器、卷、构建缓存的磁盘占用

docker stats --no-stream
# 看容器 CPU/内存实时占用（--no-stream 只打一次）

docker image prune
# 删除未被容器引用的悬空镜像

docker volume prune
# 删除未被使用的 volume；危险，先确认

docker system prune
# 清理停止的容器、未使用的网络、悬空镜像等；危险，先确认
```

清理原则：

- `prune` 只删"未被使用"的资源；
- 数据库 volume 不能随便删；
- `docker compose down -v` 会删除声明的 volume，和 `prune` 一样要确认。

## 7. Nginx 反向代理

### 7.1 为什么需要 Nginx

生产环境通常不让用户直接访问 app 端口，而是让 Nginx 站在前面：

```text
用户 -> 80/443 -> Nginx -> app:8000
```

Nginx 可以做：

- 反向代理；
- HTTPS 终止；
- 静态文件；
- 负载均衡；
- 限流、缓存、压缩。

正向代理和反向代理的区别：

```text
正向代理：代理客户端，帮客户端访问外部
反向代理：代理服务端，帮服务端接收外部请求
```

### 7.2 在 Compose 里接入 Nginx

`code/docker/08-nginx.conf`：

```nginx
server {
    listen 80;
    server_name _;

    location / {
        proxy_pass http://app:8000;

        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
```

关键点：

- `proxy_pass http://app:8000`：转发到 Compose 里的 service 名 `app`；
- `proxy_set_header`：把原始客户端信息透传给 app；
- `proxy_buffering off`：**流式响应必须关闭缓冲**，否则 SSE 会被 Nginx 攒着，前端很久才收到；
- `proxy_read_timeout 300s`：大模型调用耗时长，默认 60s 容易超时。

生产版 Compose `code/docker/08-prod-compose.yaml` 增加 Nginx：

```yaml
services:
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./08-nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      app:
        condition: service_healthy
```

这样 app 不再直接发布 8000，只通过 Nginx 的 80 对外。

### 7.3 502 和 504

```text
502 Bad Gateway
    -> Nginx 连不上上游，或上游崩溃/端口不对

504 Gateway Timeout
    -> Nginx 连上了上游，但上游在超时时间内没返回
```

排查：

```bash
docker compose -f code/docker/08-prod-compose.yaml ps
docker compose -f code/docker/08-prod-compose.yaml logs app
docker compose -f code/docker/08-prod-compose.yaml logs nginx
```

大模型接口容易 504，所以 Nginx 的 `proxy_read_timeout` 要调大，应用本身也要处理超时。

## 8. 容器排障命令与顺序

常用命令：

| 命令 | 用途 |
|---|---|
| `docker ps -a` | 看容器状态和退出码 |
| `docker logs 容器` | 看启动日志和错误 |
| `docker inspect 容器` | 看配置、网络、挂载、环境变量 |
| `docker exec -it 容器 sh` | 进容器排查 |
| `docker stats` | 看 CPU/内存 |
| `docker events` | 看容器生命周期事件 |

排查顺序：

```text
1. 看状态：docker ps -a，是 Up 还是 Exited？
2. 看日志：docker logs 容器
3. 看配置：docker inspect 容器，检查环境变量、端口、挂载、网络
4. 看资源：docker stats，是否 OOM、CPU 打满、磁盘满
```

典型故障：

```text
容器启动即退出
    -> logs 看退出原因；通常是 CMD 错误或依赖没就绪

端口被占用
    -> ps 找旧容器，或改宿主机端口

服务连不上
    -> inspect 检查网络和 service 名，exec 进容器验证 DNS

OOM 被杀
    -> stats 看内存；调大 memory 或修内存泄漏

磁盘满
    -> system df 看占用；prune 清理未使用资源
```

## 9. WSL2 资源问题（Windows）

前面几课遇到的 `ERROR_NO_SYSTEM_RESOURCES` 就是 WSL2 内存分配问题。

排查和处理：

```powershell
wsl --status
wsl --list --verbose
wsl --shutdown
```

创建 `C:\Users\你的用户名\.wslconfig`：

```ini
[wsl2]
memory=6GB
processors=8
swap=4GB
```

- 16 GB 内存给 WSL 6 GB 比较稳；
- Docker Desktop 的 Resource Saver 会在空闲后暂停后端，恢复时偶尔卡住，可以关闭；
- 内存紧张时关闭一些 IDE/浏览器，或降低 WSL memory；
- 反复卡死时重启 Windows，再重启 Docker Desktop。

## 10. Docker 与 Kubernetes 的边界

Docker Compose 和 Kubernetes 解决的问题不同：

| | Docker Compose | Kubernetes |
|---|---|---|
| 规模 | 单机多容器 | 集群多节点 |
| 调度 | 无 | 自动调度到合适节点 |
| 扩缩容 | `docker compose up --scale` | 声明式副本数，自动扩缩 |
| 滚动发布 | 手动 | 内置滚动更新、回滚 |
| 自愈 | 依赖重启策略 | 自动重建不健康 Pod |
| 服务发现 | Compose 网络 DNS | Service + Ingress |

什么时候用 K8s：

- 需要多台机器、高可用；
- 需要自动扩缩容和滚动发布；
- 有团队和运维能力维护集群。

单机应用先用 Compose 就够；K8s 不是必须的。Docker 学的是容器和镜像，K8s 学的是容器编排，两者是相邻但不同的领域。

## 11. 完整练习

```bash
# 1. 校验生产配置
docker compose -f code/docker/08-prod-compose.yaml config

# 2. 启动：app 不再发布 8000，只有 nginx 发布 80
docker compose -f code/docker/08-prod-compose.yaml up -d --build

# 3. 查看状态
docker compose -f code/docker/08-prod-compose.yaml ps

# 4. 通过 Nginx 访问（注意端口是 80）
curl.exe http://127.0.0.1/
curl.exe http://127.0.0.1/health

# 5. 看 Nginx 和 app 日志
docker compose -f code/docker/08-prod-compose.yaml logs -f nginx

# 6. 看资源占用
docker stats --no-stream

# 7. 模拟 app 故障，观察 Nginx 返回 502
docker compose -f code/docker/08-prod-compose.yaml stop app
curl.exe http://127.0.0.1/
# 预期：502 Bad Gateway 或连接失败

# 8. 恢复 app
docker compose -f code/docker/08-prod-compose.yaml start app
curl.exe http://127.0.0.1/
# 恢复 200

# 9. 查看磁盘占用，谨慎清理
docker system df

# 10. 清理
docker compose -f code/docker/08-prod-compose.yaml down
```

如果 80 端口被占用，把 `08-prod-compose.yaml` 里的 `80:80` 改成 `8080:80`，再访问 `http://127.0.0.1:8080/`。

## 14. 面试高频考点

### 14.1 镜像怎么进入生产环境？

> 本地或 CI 构建镜像，打上语义化版本号，push 到 registry；云服务器 pull 后由 Compose 或编排系统启动。CI 流水线负责构建、测试、扫描和推送，registry 凭据放 secret，镜像用具体版本或 digest，不用 `latest`。

### 14.2 为什么生产环境不用 `latest`？

> `latest` 是可变标签，指向的内容会随上游发布变化，无法确定线上到底跑的哪个版本，出问题难回滚。生产应使用语义化版本或 digest。

### 14.3 容器安全从哪些方面做？

> 使用非 root 用户、slim/distroless 基础镜像、只读文件系统、丢弃不必要的 capabilities、扫描已知漏洞、密钥不入镜像、只用官方或可信镜像。

### 14.4 资源限制怎么配置？

> `docker run --memory 512m --cpus 1.0`，或 Compose 的 `deploy.resources.limits`。限制内存可避免单个容器 OOM 拖垮整机；配合 `--restart unless-stopped` 自动拉起。

### 14.5 Nginx 正向代理和反向代理有什么区别？

> 正向代理代理客户端，帮客户端访问外部资源；反向代理代理服务端，站在公网和 app 之间接收请求并转发。生产部署常用反向代理。

### 14.6 502 和 504 分别说明什么？

> 502 表示 Nginx 连不上上游，或上游崩溃/端口不对；504 表示 Nginx 连上了上游，但上游在超时时间内没有返回。前者查上游是否存活，后者查上游是否卡住并调大超时。

### 14.7 流式响应为什么要关闭 `proxy_buffering`？

> Nginx 默认会缓冲上游响应，SSE 这类流式数据会被攒住，前端迟迟收不到。关闭 `proxy_buffering` 让数据边产生边转发，同时把 `proxy_read_timeout` 调大以适配长连接。

### 14.8 Docker 和 Kubernetes 有什么区别？

> Docker 提供容器和镜像；Compose 在单机上编排多容器；Kubernetes 在集群上调度、扩缩容、滚动发布和自愈。单机应用用 Compose 即可，多机高可用再考虑 K8s。

### 14.9 线上容器排障按什么顺序？

> 先 `docker ps -a` 看状态，再 `docker logs` 看日志，再 `docker inspect` 看配置，最后 `docker stats` 看资源。按"状态 → 日志 → 配置 → 资源"逐层定位。
